## Background, Goals & Scope

### Background

TxHarbor 为交易所、托管平台和 Web3 钱包后台提供可恢复、可审计的链上资产处理能力。第一版保持单部署单链、白名单标准 ERC-20、原生币仅用于 gas，不维护用户余额账本，不承担 KYC、风控审批或冷热钱包调度，不引入 Redis、Kafka 或其他新增基础设施，本地使用 Anvil，Go + PostgreSQL + EVM JSON-RPC。

本规范是 TxHarbor 第 006 号功能规范，目录固定为 `specs/006-reorg-recovery`（本次新建；仓库此前不存在 006–011 的任何规范文件，不复用、不改写编号）。项目章程为 Constitution 1.1.0（`.specify/memory/constitution.md`）。仓库已存在 `specs/001-project-foundation`（工程底座）、`specs/002-chain-indexer`（区块头同步）、`specs/003-event-indexing`（Transfer 原始日志索引）、`specs/004-deposit-detection`（充值识别）、`specs/005-confirmation-tracking`（确认数跟踪）。

**阅读对象**：本规格面向操作员（执行恢复与对账）、审计者（追溯分叉证据与状态转换）与下游阶段设计者（007–011）。链上术语含义见 Key Entities（canonical = 索引当前认可的链上记录；Orphaned = 因所在分叉失效而不再 canonical 的观察；checkpoint = 指向已保存区块的恢复点；共同祖先 = 新旧分叉最后一个共同区块）；技术载体（表结构、锁、算法）一律留给 plan，上游技术引用仅出现在溯源说明中。

前置依赖核验结论（2026-09-14，基于 `origin/main`  tip `a73e31b`，即 PR #7 `005-confirmation-tracking` 合并点）：

- **002 已交付**：按高度连续同步并持久化区块头（含 `chain_id`、`number`、`hash`、`parent_hash`、canonical 标记）；checkpoint 为指向已保存区块的（高度，哈希）二元组；哈希不一致（相邻父子断裂、已存哈希与链上不一致、停机期间 checkpoint 对应块变化）时持久化暂停并重启有效，暂停只能由人工处理或后续重组恢复流程解除，解除后必须重验 checkpoint；多实例经持久层协调；canonical 仅表示索引当前认可的链上记录，不代表已达确认深度或终局不可逆（002 spec FR-04/FR-12，Session 2026-09-12）。
- **003 已交付**：白名单标准 ERC-20 Transfer 原始日志持久化，去重身份为 `chain_id + block_hash + tx_hash + log_index`，高度不替代 `block_hash`；日志扫描拥有独立于 002 的 checkpoint（`start_block`、`config_hash`、`next_block`，按 `chain_id` 隔离）；结果数达到 provider 已确认单次上限按完整性可疑处理；链视图异常时持久化异常信号并停止推进，不自动回退游标、不删除历史；提交服从 002 链级暂停（003 spec FR-03/FR-14/FR-16，Session 2026-09-13）。
- **004 已交付**：从 canonical 日志识别转入受监控地址的充值，每条来源日志最多一条观察，初始状态 Pending，金额为最小单位整数；独立于 003 的充值处理进度（下一待处理位置）；暂停与结构性缺口信号按归属分层恢复（仅服从上游暂停由上游解除后自动继续，自身暂停须运维显式解除并重验，涉回退的一律由 006 负责，006 不可用时保持暂停）；收缩性配置变更仅向前生效、历史保留；暂停合并语义为累积式 8 行为（保留 `pause_id`、`revision` +1、不降级、不覆盖、相同原因幂等、失权 worker 不成因），见 004 spec Clarifications 2026-09-13 与 T029（004 spec FR-06/FR-12）。
- **005 已交付（规格与实现均已合并至 `origin/main`，生产门禁 T000-P 仍开放）**：确认数公式 `max(0, canonical_tip - block_number + 1)`，`canonical_tip` 取自本地连续校验过的 canonical 链头；阈值 N≥1、必填无默认值、链级单值（v1），同一部署所管链任一时刻只有一个有效确认策略版本；切换后旧版本计算结果不得提交，新阈值从切换点起适用于所有尚未确认的 Pending，提高或降低阈值均不撤销/改写已有 Confirmed，保留首次确认时间及当时阈值、策略版本与确认依据；确认提交受三行暂停（`deposit_pause` / `indexer_pause` / `log_pause` 中链视图信号）与三组版本（链视图版本、策略版本、充值状态版本）约束，失配即回滚；Confirmed 仅表示达到项目确认策略，不代表不可撤销，不等于上游入账；已 Confirmed 行的后续重组撤销一律由 006 负责（005 spec FR-03/FR-07/FR-08/FR-09，Session 2026-09-14）。
- **005 实现完成证据状态**：`origin/main` 包含 005 规格、计划、任务、迁移与实现合并提交；按本次指令，006 规划不代表 005 实现、回归、验收或合并门禁已经通过，缺少的完成证据记为待核验实现（见 Assumptions），不阻塞规格编写，不顺带修复或推进 005 实现。

### Goals

- 检测到已证实的分叉后，持久化恢复状态并暂停该链的确认推进与后续新提款广播，阻止基于失效链视图产生新的有效结果。
- 在配置最大深度内以后缀回退方式寻找共同祖先，将旧分叉区块与日志标记为非 canonical，使受影响的 Pending 和 Confirmed 充值转为 Orphaned 并回退相关处理进度，保留旧分叉数据与状态转换审计。
- 从共同祖先之后重新索引、重新识别充值并重新计算确认，恢复阶段与位置持久化，进程崩溃后可续跑，重复执行幂等。
- 用持久化版本约束隔离旧 worker，其延迟结果不得在恢复版本变化后提交。
- 超过最大深度或无法确认共同祖先时保持暂停并要求对账，不忽略、不跳过、不盲目追到新链头。

### Non-Goals / Out of Scope

- 002/003/004/005 已锁定行为的重定义。本规范只引用上游契约，不修改其语义。
- 具体数据库结构、锁顺序、索引设计与实现算法（留给 plan）。
- 新的提款业务表、服务或完整提款状态机设计（007–011 的职责；006 只记录供其承接的契约，见 Downstream Handoff）。
- 确认阈值变更语义的重裁决（沿用 005 已确认约束；重组失效不等同阈值变更）。
- 余额账本、KYC、风控审批、冷热钱包调度。
- 引入 Redis、Kafka、Kubernetes 或其他新增基础设施。
- 生产 provider 选型（T000-P 保持 open，不在本规范中关闭）。

### Explicit assumptions

- 单部署单链：同一时间只跟踪一条配置链；多恢复执行者指同一链的多个相同部署副本竞争，而非多链调度。
- 高度不能单独代表区块身份；区块身份至少包含高度与哈希，日志及充值身份继承含 `block_hash` 的上游身份，不把 `tx_hash` 或高度单独作为分叉去重依据。
- Confirmed 仅表示达到配置确认深度，可能因重组失效，不等于上游入账（沿用 005）。
- 不能仅依靠内存锁、唯一键或重试保证恢复一致性；并发与恢复正确性必须由持久层保证。
- 本地验证以 Anvil 为权威链数据源；不依赖公网测试网；不代表生产就绪（T000-P 保持 open）。
- 005 实现、回归、验收的未取证据标为待核验，不阻塞规格编写；006 实现前置条件保留（见 FR-25）。
- 重试退避的具体参数、批次大小、轮询间隔、请求超时由 plan 阶段确定并给出理由；本规范只锁定行为语义。

### Session 2026-09-14 (Round 2)

- Q: 最大恢复深度如何定义、边界与非法值如何处理、变更何时以何种程序生效？ → A（Q1 A + 补充）：旧链头指本次恢复建立时持久化绑定的、已连续校验的旧 canonical 链头；深度 = 该链头高度 − 共同祖先高度，不用远端新链头或变化中的本地链头计算；恰达上限允许自动恢复（闭区间）；配置必填、无默认值，缺失/零/负数/非整数/超支持表示范围拒绝启动；无业务上限，表示与安全运算留给 plan；变更须受控授权、原子生效并审计，非法或失败变更保持原配置有效；进行中的恢复绑定当时配置版本，不因变更扩大自动恢复权限；扩大上限、重划恢复批次或重启均不得绕过人工对账暂停。
- Q: 允许深度内、证据完整、完成判据全成立的自动恢复是否需人工复核？ → A（Q2a A）：可自动解除本次恢复暂停，无需人工复核，全程审计；只能解除本次恢复原因，其他独立暂停仍有效；解除时重验恢复版本与完成条件，不用过期检查结果。
- Q: 对账路径谁有权解除、最低证据是什么？ → A（Q2b B 修正版）：沿用既有授权操作者，不新增角色/双人审批；保留身份、搜索范围、原因、审计、原子性及独立暂停要求；增加受影响观察与确认结果的完整处置清单；"定性"指每条受影响记录的来源身份、当前有效性、历史确认依据和处置结果均已确定且可追溯，不要求新链充值全部重 Confirm，合法 Pending 可保留，达阈值后由 005 后续处理；区分"授权进入受控修复/继续恢复"与"验证完成后解除暂停"两步；授权继续恢复不等于解除确认/签名/广播暂停；无法确认祖先、无法建立可信重建依据或仍有未解释不一致时保持暂停；涉提款时结果未知仍保留待对账语义，不新建付款意图解决。
- Q: 恢复期间操作矩阵？ → A（Q3 B 修改版）：确认推进暂停（完成后按 005 门禁继续）；新提款广播、同字节重播、费用替换广播全部暂停（本次批准的 006 约束）；普通区块/日志索引与普通充值识别在恢复暂停生效后停止提交常规结果（取消未失效区间例外）；恢复专用索引/重放/识别允许，受恢复版本、已验证依据与明确范围约束，继承历史配置语义，不得绕过独立暂停；事务划分留 plan，不要求单事务；提款请求接收允许认证授权校验后的幂等持久化（仅接收）；nonce/新签名/费用替换签名暂停；只读查询须表达恢复状态与有效性，无可信数据时返回不可用/未知；对账写入允许受控人工处置与恢复流程程序化写入（均审计，不得触发被暂停外部动作或绕过完成门禁）。暂停前已发出的外部请求保留结果未知并继续查询取证，不视为失败重付。
- Q: 同一旧 block_hash 再次成为 canonical 时旧 Orphaned 行的状态转换？ → A（Q4 A）：复用原观察，不新建重复观察；仅当前有效恢复流程在重验区块、日志绑定及历史识别条件后可将 Orphaned 转回 Pending，证据缺失/不一致不恢复并沿异常规则处置；曾为 Confirmed 也须先回 Pending，再由 005 按当前有效策略与完整门禁重确认，恢复期间仍禁确认推进；旧确认依据仅作历史证据，当前状态与历史确认记录可区分；每次转换审计恢复版本/重验依据/时间，重复执行幂等，旧 worker 不得覆盖新状态；再次失效/恢复完整保留历史；不同 block_hash 仍沿新观察与历史关联规则，不混淆。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 浅重组下暂停、失效与重放（Priority: P1）

操作员运行中的单链发生浅重组，同时影响 Pending 和 Confirmed 充值；系统检测到分叉后持久化恢复状态并暂停该链确认，祖先之前的数据保持有效，受影响充值转为 Orphaned 后从祖先后重放并重新计算确认，完成后恢复正常处理。

**Why this priority**: 核心价值；没有"暂停—失效—重放—恢复"的完整闭环，重组必然留下永久错误的确认或静默丢弃的充值。

**Independent Test**: 在 Anvil 上构造短分叉（旧分叉含一条 Pending 充值与一条 Confirmed 充值，祖先之前另有一条 Confirmed 充值），观察暂停、Orphaned 转换、祖先前数据有效、重放后再确认，全程可从持久化状态追溯。

**Acceptance Scenarios**:

1. **Given** 本地 canonical 链已含 Pending 充值 P 与 Confirmed 充值 C，且存在共同祖先 A（A 之前另有 Confirmed 充值 K），**When** 链上出现以 A 为祖先的替代分叉且旧分叉高度仍在最大深度内，**Then** 系统持久化恢复状态并暂停该链确认，P 与 C 转为 Orphaned，K 保持 Confirmed 且其确认依据不变。
2. **Given** 恢复已完成祖先搜索并失效旧分叉数据，**When** 从 A 之后重新索引与识别，**Then** 新链上仍存在的充值按 004/005 语义重新生成观察并重新满足完整条件后确认，不复用旧确认依据；新链上不存在的充值保持 Orphaned 并保留审计。
3. **Given** 恢复尚未完成，**When** 查询充值或确认状态，**Then** 返回结果必须表达数据有效性与恢复状态，不得把未完成恢复的混合视图作为完整有效结果。

---

### User Story 2 — 替代分叉形态各异仍不漏不错（Priority: P1）

替代分叉可能无日志、含新充值、含同一交易重新上链（含日志索引变化或内容不同），或旧区块稍后再次成为 canonical；系统对每种形态都不漏处理、不错误合并历史。

**Why this priority**: 分叉形态决定身份判定；按 `tx_hash` 合并或按高度去重会掩盖分叉历史并制造错误确认。

**Independent Test**: 分别构造无日志分叉、新充值分叉、同交易重上链（索引变化 / 内容不同）、旧块回摆四种场景，观察观察身份、关联与确认行为。

**Acceptance Scenarios**:

1. **Given** 替代分叉在受影响区间无日志，**When** 恢复重放该区间，**Then** 该区间推进为合法空处理，不生成充值，不停滞。
2. **Given** 替代分叉含新充值 N（旧分叉无），**When** 恢复重放覆盖 N，**Then** N 按 004 语义生成新观察（新来源身份）并按 005 条件确认，与旧分叉历史无合并。
3. **Given** 同一交易在新链重新上链但日志索引变化或内容不同，**When** 恢复处理，**Then** 按新来源身份生成新观察并关联到同一交易的重上链历史，旧观察保持 Orphaned 不被合并或删除。
4. **Given** 同一旧区块哈希再次成为 canonical 且其上旧观察为 Orphaned，**When** 当前有效恢复流程重验（区块、日志绑定、历史识别条件）通过，**Then** 原观察转回 Pending（不新建观察，审计重验依据），后续按 005 门禁重新确认；重验失败则保持 Orphaned 并沿异常规则处置；每次转换均审计，重复执行不重复转换。

---

### User Story 3 — 进度各异与合法空区间下正确回退重放（Priority: P1）

区块、日志、充值、确认四类进度可能各不相同，扫描起点与合法空区间各异；回退与重放必须不漏处理、不错误向前推进。

**Why this priority**: 四类进度天然错位；回退位置算错即漏扫或重复确认。

**Independent Test**: 构造日志进度落后于区块进度、充值进度落后于日志进度、区间合法空三种错位，分别触发恢复并核对重放覆盖。

**Acceptance Scenarios**:

1. **Given** 日志进度落后于区块进度，**When** 恢复回退，**Then** 回退位置覆盖两类进度的最小受影响点，重放不漏任一类已失效区间。
2. **Given** 扫描起点晚于共同祖先（祖先早于起点），**When** 恢复处理，**Then** 不要求补扫起点之前历史，回退下界为扫描起点，重放从该下界之后开始。
3. **Given** 受影响区间含合法空日志区间，**When** 重放，**Then** 空区间正常推进，不记为缺失，不停滞。

---

### User Story 4 — 重复触发、并发与旧 worker 不破坏一致性（Priority: P1）

恢复可能被重复触发、多个执行者并发竞争、旧扫描/识别/确认 worker 延迟返回；系统依据持久状态续跑，最多一次有效推进，旧结果不得提交。

**Why this priority**: 与主流程同等重要；并发与延迟提交是生产常态，恢复期间的错误提交不可逆。

**Independent Test**: 重复触发恢复、双执行者并发推进、旧确认 worker 在版本变化后延迟提交，观察单次有效推进与旧结果拒绝。

**Acceptance Scenarios**:

1. **Given** 恢复进行中，**When** 再次触发恢复（相同分叉证据），**Then** 不创建冲突的新恢复实例，并发收敛到同一持久恢复状态，阶段位置不回退、不分叉。
2. **Given** 两个恢复执行者并发推进同一阶段位置，**When** 双方提交，**Then** 至多一个有效推进，另一个安全失败并重读后继续。
3. **Given** 旧扫描/识别/确认 worker 在恢复版本变化后延迟返回，**When** 其尝试提交，**Then** 提交被拒绝，不产生新的有效充值或确认；恢复不能只关闭确认循环而允许旧 worker 重建有效充值。

---

### User Story 5 — 竞争与崩溃下可续跑（Priority: P2）

确认提交与恢复启动可能竞争，确认策略切换与恢复可能竞争；恢复可在每个持久阶段崩溃并重启续跑；提交响应丢失后可定性再决策。

**Why this priority**: 没有持久阶段与版本门禁，"检查时正确"会在竞争与崩溃下变成"提交时错误"。

**Independent Test**: 在确认提交临界点启动恢复、在策略切换 pending 时启动恢复、在恢复各持久阶段之间 kill 进程、丢弃提交响应后重启，观察门禁与续跑。

**Acceptance Scenarios**:

1. **Given** 确认候选已读取但恢复启动先落地，**When** 旧确认尝试提交，**Then** 提交失败，不产生状态转换，调用方重读后重新决策。
2. **Given** 确认策略切换与恢复并发，**When** 双方推进，**Then** 旧策略版本计算的确认结果不得在切换后提交，恢复不改写策略版本链，双方按版本门禁串行化。
3. **Given** 恢复在任一持久阶段之间崩溃，**When** 重启，**Then** 从持久阶段与位置续跑，不重做已提交阶段，不跳过未完成阶段；提交响应丢失时先重读持久状态再定性。

---

### User Story 6 — 深重组与证据不足时保持暂停对账（Priority: P2）

重组深度超过最大深度、共同祖先不可得、RPC 不可用或返回不一致证据时，系统保持暂停并要求对账，不自动解除，不盲目追到新链头。

**Why this priority**: 自动恢复越过证据边界会把不可验证的结果当作有效；正确做法是停下来等人看。

**Independent Test**: 构造超深分叉、无祖先分叉、RPC 中断、节点落后、互相矛盾的 RPC 响应，观察暂停保持与对账信号。

**Acceptance Scenarios**:

1. **Given** 分叉深度超过配置最大深度或在最大深度内找不到共同祖先，**When** 恢复搜索结束，**Then** 保持暂停并记录对账信号（含已搜索范围、证据、原因），不追到新链头，不标记完成。
2. **Given** RPC 不可用、节点落后或返回互相矛盾的链视图，**When** 恢复需要该证据，**Then** 等待或有界重试，不以证据不足的视图撤销历史结果或解除暂停。
3. **Given** 独立暂停原因（配置漂移、数据异常等）仍然存在，**When** 恢复条件满足，**Then** 不得仅因恢复完成而清除这些独立暂停。

---

### Edge Cases

- 创世附近分叉：祖先搜索下界不得越过扫描起点；起点之前历史不要求补扫。
- 共同祖先恰在最大深度边界：包含在内（闭区间），必须可恢复；超出边界一位即超深。
- 共同祖先超出本地保留范围或早于扫描起点：按不可得处理，保持暂停并要求对账。
- 空日志区间的回退与重放：合法空处理可推进，不记缺失。
- 日志及充值进度落后于区块进度：回退取最小受影响点，重放覆盖全部失效区间。
- 同交易重上链但内容不同：新身份新观察，旧观察 Orphaned 保留，不合并。
- 原区块再次成为 canonical：按新视图重验后确认，历史不断线。
- 恢复期间再次分叉：当前恢复不得错误解除暂停，按新证据续跑或重定祖先。
- 数据库不可用或无法验证当前恢复版本：不得继续产生需要有效链视图授权的结果。
- 暂停与外部副作用竞态：不得声称一次数据库状态检查能撤回已发出的 RPC；已发出的广播按"结果未知先对账"处理（责任见操作矩阵）。暂停生效前已发出的外部请求 MUST 保留结果未知并继续查询、记录证据，MUST NOT 将其视为失败后重新付款；竞态隔离机制留给相应 plan。
- 日志脱敏边界：错误输出保留链、高度、哈希、阶段、错误分类、重试次数等非敏感上下文，凭据与无限制原始数据不得输出。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-01**：系统 MUST 在链上明确返回同高度不同哈希、或相邻父子哈希不衔接、或 checkpoint 核验发现已存哈希与链上不一致时，判定为已证实分叉并启动恢复；RPC 超时、不可用、节点落后或互相矛盾的响应 MUST 按证据不足处理（等待或有界重试），MUST NOT 直接撤销历史结果。
- **FR-02**：启动恢复时系统 MUST 在同一原子边界内持久化恢复状态（含分叉证据：旧链头与新链头身份、检测位置、检测时间）并暂停该链的确认推进、后续新提款广播、同字节重播与费用替换广播（后两者为 Q3 已批准的 006 约束）；暂停在进程重启后 MUST 仍然有效。上述暂停范围 MUST 保留，不得缩小。
- **FR-03**：共同祖先搜索 MUST 在配置最大深度内以后缀回退方式进行；深度定义为被撤销的旧 canonical 后缀块数 = 本次恢复建立时持久化绑定的、已连续校验的旧 canonical 链头高度 − 共同祖先高度，MUST NOT 使用远端新链头或不断变化的本地链头计算；搜索边界为闭区间，恰达上限 MUST 允许自动恢复；可信依据为本地已存区块与链上返回区块的高度与哈希双重一致且父子连续。配置 MUST 必填、无默认值：缺失、零、负数、非整数或超支持表示范围时 MUST 拒绝启动并报配置错误；无业务上限，数值表示、存储与安全运算留给 plan。配置变更 MUST 经受控授权、原子生效并审计；非法或失败的变更 MUST 保持原配置有效。进行中的恢复 MUST 绑定当时的配置版本，MUST NOT 因变更扩大其自动恢复权限；扩大上限、重新划分恢复批次或重启 MUST NOT 绕过人工对账暂停。
- **FR-04**：共同祖先超出本地保留范围、早于扫描起点或在最大深度内不可得时，系统 MUST 保持暂停并记录对账信号（含已搜索范围、双方链头证据、原因分类），MUST NOT 忽略、跳过或盲目追到新链头。
- **FR-05**：确认共同祖先后，系统 MUST 将旧分叉上的区块与日志标记为非 canonical；标记 MUST NOT 删除旧分叉数据，旧数据 MUST 作为历史证据保留。
- **FR-06**：受旧分叉影响的 Pending 和 Confirmed 充值 MUST 转为 Orphaned；共同祖先及之前仍有效的数据 MUST 保持原状态且其确认依据 MUST 不变。转换 MUST 幂等，重复执行 MUST 收敛到同一状态。
- **FR-07**：每次 Orphaned 转换 MUST 保留审计记录（含来源身份、旧区块身份、旧确认依据、转换时间、恢复实例身份）；旧确认依据 MUST 保留为历史证据，MUST NOT 被复用为新链上的确认依据。
- **FR-08**：同一交易在新链重新上链时 MUST 按新来源身份（含新 `block_hash`，以及变化后的日志索引与内容）生成新观察并关联到同一交易的历史线；MUST NOT 仅凭 `tx_hash` 恢复或合并旧观察（不同 `block_hash` 属于不同来源观察，复活规则 MUST NOT 与其混淆）。同一旧 `block_hash` 再次成为 canonical 时 MUST 复用原观察，MUST NOT 新建重复观察；仅允许当前有效恢复流程在重新验证区块、原始日志绑定及历史识别条件后，将 Orphaned 转回 Pending，证据缺失或不一致时 MUST NOT 恢复有效性并沿既有异常处理规则处置。即使旧观察曾为 Confirmed，也 MUST 先回到 Pending，再由 005 按当前有效确认策略和完整门禁重新确认；恢复期间仍禁止确认推进。旧确认依据 MUST 保留为历史证据，MUST NOT 作为本次有效确认依据；当前状态与历史确认记录 MUST 可区分，MUST NOT 使 Pending 被查询方误解为仍已确认。每次 Orphaned → Pending 转换 MUST 记录恢复版本、重验依据、时间与状态转换；重复执行 MUST NOT 重复产生转换，旧 worker MUST NOT 覆盖新状态；再次失效、再次恢复 MUST 完整保留历史。
- **FR-09**：重放 MUST 沿用来源数据产生时适用的资产、白名单、监控地址及其生效范围契约；MUST NOT 静默使用当前配置改写历史识别语义。重放按 004 语义重新识别充值，按 005 语义重新计算确认。
- **FR-10**：新链上的确认 MUST 重新满足 005 全部条件（canonical 归属、链视图有效、未暂停、当前有效策略版本），MUST NOT 复用旧确认依据；仅失效受旧分叉影响的充值，祖先前有效确认 MUST 不被重算或改写。
- **FR-11**：日志及充值进度落后于区块进度时，回退位置 MUST 取各进度的最小受影响点；合法空日志区间 MUST 可重放推进，不记为缺失；重放 MUST NOT 漏处理任一失效区间，MUST NOT 错误向前推进未失效区间。
- **FR-12**：恢复阶段与位置 MUST 在每个持久阶段提交后可观测；进程在任意阶段崩溃后 MUST 从持久阶段与位置续跑，不重做已提交阶段，不跳过未完成阶段；重复执行 MUST 幂等。
- **FR-13**：提交响应丢失后系统 MUST 先重读持久恢复状态再定性（成功 / 未提交 / 未知），MUST NOT 凭内存判断重做或跳过。
- **FR-14**：恢复 MUST 使用持久化版本约束隔离旧 worker：旧扫描、充值识别或确认 worker 即使延迟返回，在恢复版本变化后 MUST NOT 提交旧结果；恢复 MUST NOT 只关闭确认循环而允许旧 worker 重建有效充值。
- **FR-15**：多个恢复执行者竞争时 MUST 至多一个有效推进同一阶段位置；重复触发 MUST 收敛到同一恢复实例，阶段位置 MUST NOT 回退或分叉；协调 MUST 依赖持久层，MUST NOT 只依靠进程内存锁。
- **FR-16**：恢复期间再次分叉或 RPC 持续不一致时，系统 MUST NOT 错误解除暂停；MUST 按最新证据续跑或重定祖先，旧阶段结论 MUST 在重验前失效。
- **FR-17**：解除恢复暂停 MUST NOT 清除配置漂移、数据异常等其他独立暂停原因；数据库不可用或无法验证当前恢复版本时，系统 MUST NOT 继续产生需要有效链视图授权的结果。
- **FR-18**：恢复中查询 MUST 表达数据有效性与恢复状态（进行中 / 已完成 / 暂停对账中，以及结果是否含未完成恢复的混合视图）；MUST NOT 把未完成恢复的混合视图作为完整有效结果返回。对外默认视图 MUST NOT 仅按 tx_hash 合并不同来源观察，MUST NOT 隐藏 Orphaned 历史；同一原始来源身份重复出现 MUST NOT 创建重复观察。
- **FR-19**：恢复完成 MUST 同时满足：共同祖先已确认、旧分叉数据已标记失效、受影响充值已转换、回退位置已持久化、祖先后失效区间已重放且确认已按新链视图重算；"恢复到一致的处理位置"与"追上不断增长的远端链头"MUST 区分：完成判据为前者，MUST NOT 以追上实时链头为完成条件无限等待，也 MUST NOT 在重放未覆盖全部失效区间时提前恢复。
- **FR-20**：确认提交与恢复启动竞争时，恢复落地后旧确认结果 MUST NOT 提交成功；确认策略切换与恢复并发时，旧策略版本结果 MUST NOT 在切换后提交，恢复 MUST NOT 改写策略版本链；提交事务 MUST 在持锁后重读并复核依据，失配即回滚。
- **FR-21**：恢复 MUST 保留旧分叉数据、状态转换审计与重上链关联，使历史观察、确认依据与恢复过程可追溯；审计记录 MUST 包含恢复实例身份、阶段转换、证据引用与操作时间。
- **FR-22**：系统 MUST 提供恢复状态、阶段位置、暂停原因、对账信号的可观察信息；错误信息 MUST 足以定位失败位置和错误类型，但 MUST NOT 泄露敏感凭据或输出无限制的原始数据。
- **FR-23**：恢复完成与对账解除暂停 MUST 分两条路径：(a) 自动路径：允许深度内、证据完整、FR-19 全部完成判据成立时，系统 MUST 可自动解除本次恢复暂停，MUST NOT 要求人工复核，但 MUST 全程审计；自动解除 MUST 只能解除本次恢复原因，配置漂移、数据异常等其他独立暂停原因 MUST 仍然有效；解除时 MUST 重新验证恢复版本与完成条件，MUST NOT 使用过期检查结果。(b) 对账路径：超深、祖先不可得、证据不足或数据不一致进入对账后，解除 MUST 由既有授权操作者执行（不新增角色或双人审批制度），MUST 提供最低证据（双方链头身份、已搜索范围、原因分类、完成判据重验通过记录）并附受影响观察与确认结果的完整处置清单；"定性"MUST 指每条受影响记录的来源身份、当前有效性、历史确认依据和处置结果均已确定且可追溯，MUST NOT 要求所有新链充值已经重新 Confirmed（合法 Pending 可保留，达阈值后由 005 后续处理）。MUST 区分"授权进入受控修复/继续恢复"与"验证修复与恢复完成后解除暂停"两步；人工授权继续恢复 MUST NOT 等于解除确认、签名或广播暂停。无法确认祖先、无法建立可信重建依据或仍有未解释的数据不一致时 MUST 保持暂停；MUST NOT 凭签字直接跳过验证。对账解除 MUST 记录授权操作者、时间、证据引用与原因；失败 MUST 不部分生效；重启 MUST 重验；MUST NOT 清除其他独立暂停原因。涉及后续提款时，结果未知 MUST 保留待对账语义，MUST NOT 通过新建付款意图解决。

### Key Entities *(include if feature involves data)*

- **分叉证据**：旧链头身份（高度 + 哈希）、新链头身份（高度 + 哈希）、检测位置、检测时间；是恢复启动与审计的输入。
