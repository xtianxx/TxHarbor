## Background, Goals & Scope

### Background

TxHarbor 为交易所、托管平台和 Web3 钱包后台提供可恢复、可审计的链上资产处理能力。第一版保持单部署单链、白名单标准 ERC-20、原生币仅用于 gas，不维护用户余额账本，不承担 KYC、风控审批或冷热钱包调度，本地使用 Anvil。项目章程为 Constitution 1.1.0（`.specify/memory/constitution.md`）。

本规范是 TxHarbor 第 013 号功能规范，目录固定为 `specs/013-reliable-event-infrastructure`（本次新建）。它是章程「架构演进」中 `Go + PostgreSQL + Anvil` → `Redis` → `Kafka / Outbox` 步骤的规格载体：为既有资金关键域引入缓存与限流（Redis）与异步事件投递（Kafka），并以事务性 Outbox 替代双写。本规格只定义 WHAT/WHY 与验收边界，不提前定技术选型、不写 plan/ADR。

前置依赖核验结论（2026-09-23，基线为 `main` tip `99545bf`，工作区干净）：

- **001–011 与 PB（012-007-authorization-carrier）已合并至 main**：状态快照见 `docs/project-context.md`；A-13（011 全链 E2E）已 CLOSED，**T000-P（生产 provider 选型）保持 OPEN**，不在本规范中关闭。
- **上游只读契约（本规范引用而不重新规定）**：
  - **002**：`chain_blocks` 的 canonical 语义（仅表示索引当前认可，不代表确认深度或终局）、`indexer_pause`、checkpoint 与链级暂停；高度不能单独代表区块身份。
  - **003**：ERC-20 Transfer 原始日志稳定身份 `chain_id + block_hash + tx_hash + log_index`（高度不替代 `block_hash`）、日志 checkpoint、`log_pause`（含 `chain_view_changed` / `validation_failed` / `range_incomplete`）、结果数达上限按完整性可疑处理。
  - **004**：充值观察初始 Pending、每条来源日志最多一条观察、独立充值处理进度、暂停与结构性缺口信号、链视图不一致时不提交不推进。
  - **005**：确认阈值 N≥1、单链单一有效策略版本、确认提交受三行暂停与三组版本门禁约束、Confirmed 仅表示达到项目确认策略（不等于上游入账、可能因重组失效）。
  - **006**：恢复期间操作矩阵（FR-26）——确认推进暂停、新提款广播/同字节重播/费用替换暂停、提款请求接收允许幂等持久化且仅接收、查询须表达恢复状态与有效性、结果未知保留对账语义不得重建付款意图；重组失效、Orphaned→Pending 复活（FR-08）与恢复版本约束。
  - **007**：提款创建 receive-only（Accepted 仅表示已接收，不触发 nonce/签名/广播）、认证与逐笔授权双层、`caller_id + idempotency_key` 去重作用域、DB 层原子去重、不维护用户余额账本。
  - **008/009/010**：nonce 持久绑定与不明消耗对账、签名隔离与逐次交付门禁、交易尝试预持久化、结果未知先对账、广播安全矩阵与失格围栏；每次发送前重验当前门禁，前次检查不构成持续许可。
  - **011**：付款意图 `intent_id ↔ request_id` 至多一个、领取/租约/执行资格版本、合法接管不建第二意图、投影仅显示以 010 持久事实为权威、重组修订追踪原意图。
  - **PB**：逐笔授权 scope 载体、受控供给、条件式费用替换复用、普通调用方不可写入。
- **Redis / Kafka / Outbox 属本规格新建能力**：本仓库现状不含其实现（README/CHANGELOG 中「未实现/待实现」字样仅描述规划仓库现状，不用于推断实现仓库进度）；本规范不声称其已实现，不复制上游语义，只定义需求与验收边界。
- **不维护用户余额账本**：本项目只承诺本项目事件身份/版本/投递语义 + 上游消费者幂等契约与可验证边界，不宣称保证外部真实账本的正确性（见 FR-16）。

### Goals

- 在 Redis 故障、Kafka 故障、双故障与恢复追赶五种状态下，资金关键业务按明确矩阵继续/降级/拒绝，PostgreSQL 权威不可动摇、门禁不可绕过。
- 业务状态变化与事件在同一事务原子提交（Outbox 替代双写），发布至少一次，重复与乱序投递可被幂等吸收。
- 事件身份、业务对象版本顺序、链与区块身份、重组修订事件语义明确且可验收。
- 消费者持久幂等、失败重试有界、毒事件隔离、可重放、进度可恢复且可观察；事件版本兼容与契约变更规则明确。
- 缓存失效后的查询行为与分布式 API/RPC 限流失效的处置规则明确（PD-1 已裁决：新提款创建拒绝并返回明确可重试错误，存量资金流程继续，RPC 保持有界控制）；资金写入接口在限流故障时不得无限制放行。
- Kafka 停机期间 Outbox 积压有容量保护，发布器恢复、消费者追赶与再故障行为可验证；超积压业务处置按 PD-2 已裁决（停新保在途、预留恢复容量、链上已发生充值不可拒绝、绝不静默丢弃事件）。
- 可验收的故障演练（关 Redis+Kafka、保 PG+本地链）与观测、基准要求：API/RPC p95/p99/吞吐、Outbox 待发与最老等待、发布失败、事件通道积压与追赶时间；同负载/故障下「仅持久库路径」vs「启用缓存/限流+事件通道路径」对照；无实测数值一律标待测/待裁决，不编造阈值。

### Non-Goals / Out of Scope

- 重定义、放宽或收紧 002–011/PB 已锁定的语义、门禁与状态机；本规范只引用与承接。
- 用户余额账本、KYC、风控审批、冷热钱包调度；「入账」指上游/下游账本动作，本项目不执行也不保证。
- 具体表结构、topic/partition/key、消费组与 offset 载体、缓存键与失效策略、限流算法、重试/退避参数、事件字段命名、迁移编号（留给 plan）。
- 生产 provider 选型（T000-P 保持 OPEN）、Kubernetes、多链调度、真实外部账本入账保证。
- 本步骤已完成 clarify 落盘，不进入 plan/tasks/analyze/implement；ADR 属 plan 交付（FR-25/PD-3），不在本规格内产出；不把架构建议写成已批准规则。

## Clarifications

### Session 2026-09-23

- Q: Redis 分布式限流不可用时，新提款创建与存量资金流程如何分别处置，是否批准替代限流机制？ → A: Redis 分布式限流不可用时，新提款创建拒绝并返回明确的可重试错误，不无限制放行；充值观察、确认、重组恢复和已由 PostgreSQL 接受的提款，继续遵守原有授权、幂等、状态、暂停、nonce、广播及对账门禁。查询可绕过缓存回源 PostgreSQL。已有流程的 RPC 调用仍须有安全的有界控制；若某项调用无法维持该控制，应安全暂停并在恢复后续跑，不能借 Redis 故障绕过门禁。故障矩阵分别验收‘拒绝新提款创建’和‘存量资金流程继续’。本轮不批准资金写入的替代限流机制。
- Q: 事件通道积压接近容量边界时，业务处置与容量保护规则是什么？ → A: 停新保在途，并预留恢复容量。接近容量边界时，先拒绝可控制的新资金写入，降级非关键功能，为已接受的资金流程、必要状态修订及其 Outbox 事件保留容量；业务状态与关键事件仍须原子提交，绝不静默丢弃事件。链上已发生的充值不能拒绝；若无法安全持久化，则从可靠进度暂停处理，容量恢复后补扫，不跳过观察。在途提款遇到无法安全记录或结果未知时，按既有暂停与对账协议恢复，不新建付款意图。软边界、预留量、硬上限和可承受停机时间由后续测量与计划确定，本轮不编造数值。
- Q: Kafka 是否保留在 013 范围内，价值证明与可能的范围调整如何处理？ → A: Kafka 保持在 013 已明确的规划与验证范围内。本轮不预判其性能或可靠性收益，也不以尚未运行的基准取消范围。plan 中用 ADR 写明引入理由、PG-only 替代方案、额外运维和故障成本，并设计可比基准；取得实测证据后报告结果。若结果支持调整 Kafka 范围，须另行提交具体变更供用户决定，不自动删减。
- Q: OQ1–OQ6 中哪些须在本轮规格明确、哪些留 plan（含事件目录与人工重放边界）？ → A: 逐项核对 OQ1–OQ6 与现有 FR。topic/消费组、发布状态机、缓存键与算法、指标测量方法、具体 schema 表示等技术机制留给 plan。事件目录须在本轮明确哪些已提交的资金状态及重组修订需要对外发事件；若现有 FR 已完整规定，引用即可，具体事件清单留 plan。区分自动重试与人工重放：人工重放的授权、审计及不得绕过持久幂等的边界须在规格中明确；是否需要额外审批若现有授权契约没有依据，应提出待用户裁决，不能由 plan 自行决定。其余 OQ 留 plan，不提前锁定实现细节。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 基础设施故障下的资金业务连续性与门禁不被绕过（Priority: P1）

Redis、Kafka 或两者同时故障时，资金关键业务按故障服务矩阵继续/降级/拒绝；PostgreSQL 权威与既有门禁不被绕过；恢复后事件补齐、进度恢复、无重复付款、无权威状态丢失。

**Why this priority**: 故障期间停摆或绕过门禁都会造成不可逆资金风险；PG 权威与门禁继承是章程底线。

**Independent Test**: 在本地环境分别注入仅 Redis 故障、仅 Kafka 故障、双故障（关 Redis+Kafka，保 PG+本地链），按矩阵逐项验证七类操作行为与安全前提；恢复后验证事件补齐、进度恢复、0 重复提款意图与链上付款、0 权威状态丢失。

**Acceptance Scenarios**:

1. **Given** 仅 Redis 故障而 PostgreSQL/RPC 正常，**When** 充值处理、确认、查询与已有提款执行推进，**Then** 按矩阵继续或降级，缓存旁路直读权威数据，门禁与幂等不依赖 Redis，且不返回陈旧财务权威。
2. **Given** 仅 Kafka 故障，**When** 业务状态变化发生，**Then** 业务按 PG 权威继续处理并持久化，事件进入 Outbox 积压且不丢失；「订阅端未收到」不得被解读为业务未发生。
3. **Given** 双故障，**When** 资金关键业务运行，**Then** 按矩阵继续/降级/拒绝，0 次绕过认证/授权/暂停/恢复版本/执行资格门禁；恢复后事件补齐、进度恢复、0 重复提款意图与链上付款。
4. **Given** 任一故障状态，**When** 重复事件投递或积压重放发生，**Then** 0 次新提款意图、0 次 nonce 分配/签名/广播、0 次孤儿充值永久入账。

---

### User Story 2 — 业务状态与事件原子提交、至少一次发布、事件身份与版本顺序（Priority: P1）

每次业务状态变化与其事件在同一事务提交；发布至少一次且不丢失；事件携带稳定身份与版本，重复/乱序投递可被幂等吸收；同身份异内容冲突不静默覆盖。

**Why this priority**: 双写不一致与身份/版本混乱会制造幽灵事件、丢事件与重复财务效果。

**Independent Test**: 注入提交前后崩溃、发布前后崩溃、重复发布、乱序投递与同身份异内容，观察原子性、不丢失、幂等收敛与冲突告警。

**Acceptance Scenarios**:

1. **Given** 一次业务状态变化提交，**When** 事务提交成功，**Then** 对应事件记录同事务存在；提交失败时 0 事件可见；不存在「已提交状态无事件」或「未提交状态有事件」。
2. **Given** 发布器在发布前后崩溃/重启或多实例重复发布，**When** 恢复，**Then** 已提交事件不丢失，重复投递可发生且被消费者幂等吸收（以模拟上游消费者验证）。
3. **Given** 同一事件身份再次出现且内容一致，**When** 再次处理，**Then** 幂等收敛；内容不同时冲突并告警，不静默覆盖。
4. **Given** 同一业务对象多版本事件乱序到达，**When** 消费者处理，**Then** 旧版本不覆盖新版本；版本缺口不被静默跳过（等待、隔离或请求重放）。

---

### User Story 3 — 消费者持久幂等、有界重试、隔离、重放与进度恢复（Priority: P1）

消费者在重复投递、失败重试、重启、rebalance 与重放后收敛到同一持久状态；重试有界；毒事件隔离且可重放；进度持久可观察；未知版本 fail-closed。

**Why this priority**: 消费者幂等是「不重复入账/不重复付款」的最后一道闸；无界重试或静默丢弃都会破坏资金正确性。

**Independent Test**: 重复投递同一事件、注入可重试/不可重试失败、kill 进程后重启、从隔离区与指定位置重放，观察有效应用次数恒为 1、隔离可审计、进度续传与 lag 可观测。

**Acceptance Scenarios**:

1. **Given** 同一事件被重复投递（含跨重启与 rebalance），**When** 消费者处理，**Then** 有效应用恰好一次，0 重复财务效果。
2. **Given** 可重试失败，**When** 重试，**Then** 按有界退避重试；不可重试或超过上限时，事件被隔离并审计告警，不静默丢弃、不无限阻塞其他事件。
3. **Given** 消费者崩溃重启或执行重放，**When** 恢复，**Then** 从持久进度续传，重放幂等，0 重复财务效果，lag 与追赶状态可观察。
4. **Given** 事件 schema 版本未知或不兼容，**When** 消费，**Then** fail-closed 隔离并告警，不误用。

---

### User Story 4 — 重组修订事件与链身份语义（Priority: P1）

重组使旧分叉数据失效时，修订事件表达旧身份、新 canonical 状态/Orphaned 处置、原因与恢复版本；消费者收敛到修订后状态；修订不触发新付款；Orphaned 不再作为有效事实。

**Why this priority**: 修订语义错误会让消费者永久保留孤儿入账，或把更正误读为新付款指令。

**Independent Test**: 构造浅重组影响 Pending/Confirmed 充值、重复/乱序修订投递、同一旧 `block_hash` 再次 canonical、链身份缺失事件，观察消费者状态收敛与 0 新付款意图。

**Acceptance Scenarios**:

1. **Given** 重组使旧分叉区块/日志/充值观察失效，**When** 修订事件发布，**Then** 事件至少携带旧身份、新 canonical 状态或 Orphaned 处置、修订原因与恢复版本；消费者收敛后不再把 Orphaned 数据作为有效 canonical 事实。
2. **Given** 修订事件被重复或乱序投递，**When** 消费，**Then** 幂等收敛；修订不触发新提款意图、nonce 分配、签名或广播；确认修订不表达上游入账。
3. **Given** 同一旧 `block_hash` 再次成为 canonical（006 FR-08），**When** 修订/复活处理，**Then** 复用原观察的复活语义与「新来源观察」清晰区分，不混淆、不重复转换。
4. **Given** 事件缺少链身份或链身份不匹配（仅高度不足以判定归属），**When** 消费，**Then** 拒绝/隔离，不误用。

### User Story 5 — 缓存失效查询行为与限流失效处置（Priority: P2）

权威状态变化后查询不返回陈旧财务权威；缓存故障/miss 直读权威；分布式 API/RPC 限流失效时新提款创建拒绝并返回明确可重试错误，存量资金流程继续（PD-1 已裁决）；资金写入接口不得无限制放行。

**Why this priority**: 陈旧缓存会误导操作与决策；限流失效若默认放行则打开资金与 RPC 滥用窗口。

**Independent Test**: 在权威状态变化后立即查询、注入缓存故障与限流失效，观察陈旧读取次数为 0、新提款创建 0 次无限制放行（拒绝且返回可重试错误）、存量资金流程按原门禁继续、RPC 保持有界且分类/完整性校验不被跳过。

**Acceptance Scenarios**:

1. **Given** 权威状态已变化，**When** 查询受影响键范围，**Then** 不返回陈旧财务权威；缓存不可用或 miss 时直读 PostgreSQL；新鲜度不可确认时明确标注。
2. **Given** 分布式限流不可用（含 Redis 故障），**When** 资金写入接口被调用，**Then** 新提款创建被拒绝并返回明确可重试错误（PD-1），0 次无限制放行；充值观察、确认、重组恢复与已由 PostgreSQL 接受的提款继续遵守原有门禁；查询可绕过缓存回源 PostgreSQL；RPC 调用保持有界控制，无法维持时安全暂停并在恢复后续跑。
3. **Given** 缓存/限流恢复，**When** 流量回升，**Then** 平滑重建，不瞬间放开为无界，不提供已失效的陈旧值。

### User Story 6 — 事件通道停机积压、容量保护、发布器恢复与消费者追赶（Priority: P2）

Kafka 长时间停机期间已提交事件保留在 Outbox 且积压有界、可观测；恢复后发布器从持久状态排空、消费者从持久进度追赶；追赶期间再故障安全重暂停，不丢失、不重复财务效果。

**Why this priority**: 无容量保护的积压会拖垮权威库；无追赶验证的「恢复」可能丢事件或重复副作用。

**Independent Test**: 停机期间观察积压与最老等待指标；恢复后观察排空、追赶与再故障；验证 0 事件丢失、0 重复财务效果、进度可续。

**Acceptance Scenarios**:

1. **Given** Kafka 停机，**When** 业务继续产生事件，**Then** 事件保留在 Outbox（0 丢失），积压量与最老待发等待可观测；容量保护按 PD-2 已裁决：接近容量边界时先拒绝可控制的新资金写入、降级非关键功能，为已接受的资金流程、必要状态修订及其 Outbox 事件预留容量；链上已发生充值不得拒绝；绝不静默丢弃事件。
2. **Given** Kafka 恢复，**When** 发布器与消费者运行，**Then** 发布器从持久状态排空积压（重复发布可接受），消费者从持久进度追赶，追赶时间可观测（数值待测）。
3. **Given** 追赶期间再次故障，**When** 系统重新暂停投递，**Then** 0 丢失、0 重复财务效果，进度可续。
4. **Given** 积压未清空，**When** 查询，**Then** 积压/延迟作为降级信息表达，不伪装为实时。

### User Story 7 — 故障演练、观测与对照基准（Priority: P2）

双故障演练（关 Redis+Kafka、保 PG+本地链）验证关键资金业务与恢复补齐；观测指标与 PG-only vs 全栈对照基准可产出；无实测数值标待测/待裁决；「不重复入账」以模拟上游消费者验证并写明边界。

**Why this priority**: 没有演练与对照证据，可靠性声明与 Kafka 价值证明都不成立（章程 XIII/文档要求）。

**Independent Test**: 在本地确定性环境执行双故障演练并留证；产出观测指标与对照报告；检查验证边界声明与数值标注。

**Acceptance Scenarios**:

1. **Given** 本地确定性环境（Anvil + PostgreSQL + Redis + Kafka + Docker Compose），**When** 执行双故障演练，**Then** 七类关键资金业务按矩阵验证，恢复后事件补齐、进度恢复、0 重复提款意图/链上付款、0 权威状态丢失。
2. **Given** 上游模拟消费者/集成证据，**When** 重复投递下验证入账幂等，**Then** 模拟账本恰好一次入账，且证据明确声明验证边界（不保证外部真实账本）。
3. **Given** 需要评估基础设施价值，**When** 在相同负载与故障场景下运行对照，**Then** p95/p99、吞吐、错误率、资源观测与追赶时间报告产出；无实测数据的数值目标 0 次被表述为已达标。
4. **Given** 观测需求，**When** 检查指标与日志，**Then** 清单齐备且不含密钥/凭据；告警阈值有依据来源（plan/实测）。

### Edge Cases

- Redis 故障瞬间大量缓存击穿直读 PostgreSQL：必须有界保护，不得以无界并发压垮权威库。
- 限流失效时「拒绝新提款创建」与「存量资金流程继续」不冲突：二者针对不同接口类，分别验收（US5/矩阵）；已有流程 RPC 无法维持安全有界控制时安全暂停、恢复后续跑，不借 Redis 故障绕过门禁（PD-1）。
- Kafka 长时间停机导致积压接近/超过容量边界：按 PD-2 已裁决——先拒绝可控制的新资金写入、降级非关键功能、预留恢复容量；链上已发生充值不可拒绝，无法安全持久化则从可靠进度暂停、容量恢复后补扫；业务状态与关键事件仍须原子提交，绝不静默丢弃。
- 在途提款收尾：无法安全记录或结果未知时按既有暂停与对账协议恢复，不新建付款意图（PD-2）。
- 重复投递跨越进程重启与消费组 rebalance：幂等由持久层保证，不依赖内存或单实例。
- 乱序：旧版本事件晚到、修订事件先于原事件到达、跨业务对象顺序不保证；消费者版本守卫必须成立。
- 事件身份冲突（同身份不同内容）：拒绝并告警，不静默覆盖。
- 消费者处理成功但 offset/进度提交失败：重复处理必须幂等收敛。
- 毒事件永久失败：隔离后不得无限阻塞其他事件或分区进度；修复后可重放。
- 重组发生在事件已投递之后：修订事件必须能纠正消费者已应用的状态。
- 同一旧 `block_hash` 再次 canonical（006 FR-08 复活）：修订语义与「新观察」不混淆、不重复转换。
- 恢复追赶期间再次故障：安全重暂停，不丢事件、不重复财务效果。
- 缓存与 PostgreSQL 不一致：PostgreSQL 权威；缓存不得覆盖权威事实。
- 限流恢复瞬间的流量尖峰：不得放开为无界；平滑恢复。
- 未知/不兼容 schema 版本：fail-closed 隔离，不误用。
- 事件发布器多实例竞争：重复发布可接受（至少一次），但不得出现未提交状态的事件。
- PostgreSQL 不可用不在本规格演练定义内（双故障仅指 Redis+Kafka）；PG 故障行为沿用既有阶段契约。
- 日志脱敏边界：错误输出保留链、高度、哈希、事件身份、错误分类、重试次数等非敏感上下文，凭据与无限制原始数据不得输出。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-01**: PostgreSQL MUST 保持唯一权威：Redis、Kafka、缓存与事件通道 MUST NOT 成为任何财务重要状态的唯一来源；其丢失、重启或暂时不可用 MUST NOT 使权威财务状态不可恢复；持久财务决策 MUST 可从 PostgreSQL 与 canonical 链数据重建（章程 III）。
- **FR-02**: Redis 用途 MUST 限于缓存、限流、临时协调、非权威健康状态与性能优化；Kafka 用途 MUST 限于异步事件投递与服务解耦；两者 MUST NOT 被用作资金状态、幂等去重凭据、门禁判定或对账依据的唯一载体（章程 III/XIII）。
- **FR-03**: 本规格引入 Redis 与 Kafka 作为目标能力，MUST NOT 借本规格引入其他新基础设施（Kubernetes 等）；MUST NOT 重定义、放宽或收紧 002–011/PB 已锁定语义与门禁；事件投递 MUST NOT 被解读为执行许可、逐笔授权或链上事实本身。
- **FR-04**: 故障服务矩阵 MUST 按本节表格执行；矩阵中标注 PD-1/PD-2 的处置 MUST 按已裁决条款执行；实现 MUST NOT 静默选择未列明或与已确认约束冲突的处置。矩阵行为与安全前提为一等验收对象（章程 IX）。
- **FR-05**: 门禁继承：任何事件发布、投递、重放或追赶 MUST NOT 绕过 006 恢复暂停与版本、008/009/010/011 的授权/暂停/恢复版本/执行资格门禁、007 认证/授权/幂等契约；重复投递 MUST NEVER 触发新提款意图、nonce 分配、签名、广播或新链上付款。
- **FR-06**: 故障不得导致的不变量：重复提款意图 0；重复 nonce 分配 0；重复广播/重播/替换 0；孤儿充值永久入账 0；权威状态丢失 0；门禁绕过 0；静默事件丢失 0。
- **FR-07**: 业务状态变化与事件记录 MUST 在同一 PostgreSQL 事务内原子提交（事务性 Outbox 或等价机制）；MUST NOT 使用「先写库再直接发布」的双写（章程 VI）；已提交状态 100% 有对应事件记录，未提交状态 0 事件；事件目录 MUST 覆盖资金关键域（至少：充值观察生成与状态转换、确认转换、重组修订、提款请求接收、提款执行关键状态转换），完整事件类型与命名留 plan。
- **FR-08**: 发布 MUST 为至少一次：已提交事件 MUST NOT 丢失；重复发布可发生且 MUST 被消费者幂等吸收；发布器崩溃、重启与多实例竞争后 MUST 从持久状态恢复并收敛；发布成功标记 MUST 持久化；发布尝试 MUST 有界（可重试/不可重试分类、上限、超时、退避，参数留 plan）。
- **FR-09**: 事件身份：每个事件 MUST 携带稳定身份并具 UNIQUE 约束；EVM 日志派生事件 MUST 使用 `(chain_id, block_hash 或 tx_hash, log_index)` 三元组（高度 MUST NOT 单独作为身份）；业务对象事件 MUST 使用不依赖投递尝试的稳定业务身份；同一身份 MUST NEVER 对应不同内容——冲突 MUST 拒绝并告警，MUST NOT 静默覆盖（章程 II）。
- **FR-10**: 版本顺序与链身份：同一业务对象的事件 MUST 携带单调版本，消费者 MUST NOT 以旧版本覆盖新版本；版本缺口 MUST NOT 被静默跳过（等待、隔离或请求重放）；链派生事件 MUST 携带 `chain_id`、`block_number`、`block_hash`（日志另含 `tx_hash`、`log_index`）；跨对象全局顺序 MUST NOT 被假定。
- **FR-11**: 重组修订：旧分叉数据失效时系统 MUST 发布修订事件，至少表达：旧事件/旧区块身份、新 canonical 状态或 Orphaned 处置、修订原因、恢复版本；修订事件 MUST 幂等，MUST NOT 被解读为新充值、新确认或新付款指令；消费者 MUST 收敛到修订后状态，MUST NOT 继续把 Orphaned 数据作为有效 canonical 事实，MUST NOT 因修订触发新提款意图或链上付款；同一旧 `block_hash` 再次 canonical（006 FR-08）时修订语义 MUST 与「新来源观察」区分，不混淆、不重复转换（章程 IV；006 FR-08/FR-11）。
- **FR-12**: 事件 schema 与契约变更：每个事件 MUST 携带 schema 版本；向后兼容变更（新增可选字段等）MUST 保持同版本可用且消费者 MUST 忽略未知字段；破坏性变更（字段删除、语义改变、必填新增）MUST NOT 原地发布——MUST 使用新版本并提供兼容/迁移窗口；消费者遇到未知或不支持版本 MUST fail-closed（隔离并告警），MUST NOT 误用；发布者 MUST NOT 在未声明的版本下改变载荷语义。
- **FR-13**: 消费者幂等 MUST 由持久层保证（UNIQUE 约束、版本守卫或等价机制），MUST NOT 仅依赖内存；重复投递、乱序、重启、rebalance 与重放后 MUST 收敛到同一持久状态；同一事件有效应用次数 MUST 恰好一次；MUST NOT 产生重复财务效果（重复入账、重复意图、重复 nonce、重复广播）。
- **FR-14**: 重试 MUST 有界且有意（可重试/不可重试分类、上限、超时、退避，参数留 plan；章程 IX）；永久失败/毒事件 MUST 被隔离（持久隔离载体、审计、告警），MUST NOT 静默丢弃，MUST NOT 无限阻塞其他事件或分区进度；隔离事件 MUST 在修复后可重放且重放幂等。人工重放与自动重试 MUST 明确区分：人工重放 MUST 有显式授权与审计记录（操作者、范围、理由、结果），MUST NOT 绕过持久幂等、版本守卫、既有门禁或 002–011/PB 契约；是否需要额外审批（如双人复核）无现有授权契约依据，列为 PD-4 待用户裁决，MUST NOT 由 plan 自行决定。
- **FR-15**: 消费者进度 MUST 持久化并可观测；重启后 MUST 从持久进度续传（不得丢失进度，不得把已处理当未处理造成财务重复）；重放（含从隔离区或指定位置）MUST 幂等（人工重放边界见 FR-14）；lag 与追赶状态 MUST 可观察。
- **FR-16**: 「不重复入账」的承诺边界：本项目仅承诺本项目事件身份/版本/投递语义 + 上游消费者幂等契约 + 可验证边界（模拟上游消费者/集成证据）；MUST NOT 宣称保证外部真实账本的正确性；验收证据 MUST 明示验证边界。
- **FR-17**: 缓存查询行为：缓存 MUST 仅承载非权威数据；权威状态变化后受影响键范围的查询 MUST NOT 返回陈旧财务权威；缓存不可用、不可信或 miss 时 MUST 直读 PostgreSQL；缓存恢复后 MUST NOT 继续提供已失效的陈旧值；新鲜度不可确认时 MUST 明确标注（006 FR-18 语义）；缓存故障期间 MUST 有界保护，MUST NOT 以无界并发压垮 PostgreSQL；键设计、失效策略与 TTL 留 plan。
- **FR-18**: 限流失效处置（PD-1 已裁决）：分布式 API/RPC 限流失效（含 Redis 不可用）时，新提款创建 MUST 拒绝并返回明确的可重试错误，MUST NOT 无限制放行；充值观察、确认、重组恢复和已由 PostgreSQL 接受的提款 MUST 继续遵守原有授权、幂等、状态、暂停、nonce、广播及对账门禁；查询 MAY 绕过缓存回源 PostgreSQL；已有流程的 RPC 调用 MUST 保持安全的有界控制，若某项调用无法维持该控制 MUST 安全暂停并在恢复后续跑，MUST NOT 借 Redis 故障绕过门禁；故障矩阵 MUST 分别验收「拒绝新提款创建」与「存量资金流程继续」；本轮 MUST NOT 批准或引入资金写入的替代限流机制（如需受限替代 MUST 另行裁决）；非关键功能 MAY 降级，MUST NOT 因此阻塞关键路径；恢复时 MUST 平滑重建，MUST NOT 瞬间放开为无界。
- **FR-19**: RPC 降级 MUST NOT 破坏既有 RPC 契约（章程工程标准；002/003/004/005/006）：MUST 保留传输失败/超时/限流/无效响应/链不匹配/交易拒绝的分类，MUST NOT 以限流故障为由跳过区块、跳过完整性检查、降低链身份校验或把不完整结果当完整。
- **FR-20**: 事件通道停机积压与容量保护（PD-2 已裁决）：Kafka 不可用期间已提交事件 MUST 保留在 Outbox（0 丢失）；积压量与最老待发等待 MUST 可观测；积压 MUST 有界（容量阈值、告警、硬上限），MUST NOT 无界增长危及 PostgreSQL；接近容量边界时 MUST 先拒绝可控制的新资金写入并降级非关键功能，为已接受的资金流程、必要状态修订及其 Outbox 事件保留恢复容量；业务状态与关键事件 MUST 仍原子提交，MUST NOT 静默丢弃事件，MUST NOT 覆盖未发布事件；链上已发生的充值 MUST NOT 被拒绝，若无法安全持久化 MUST 从可靠进度暂停处理，容量恢复后补扫，MUST NOT 跳过观察；在途提款无法安全记录或结果未知时 MUST 按既有暂停与对账协议恢复，MUST NOT 新建付款意图；软边界、预留量、硬上限与可承受停机时间由后续测量与 plan 确定，本规范 MUST NOT 编造数值。
- **FR-21**: 发布器恢复：Kafka 恢复后发布器 MUST 从持久状态恢复并排空积压；MUST NOT 丢失已提交事件；重复发布可接受（至少一次），MUST NOT 因此产生额外财务效果；恢复期间 MUST 有界（并发、批次、退避留 plan）；发布失败 MUST 可观测并可告警。
- **FR-22**: 消费者追赶与再故障：恢复后消费者 MUST 从持久进度追赶；追赶 MUST 有界且可观测（lag、追赶时间）；追赶期间再次故障 MUST 安全重暂停（0 丢失、0 重复财务效果、进度可续）；追赶 MUST NOT 触发重复财务效果或绕过门禁。
- **FR-23**: 恢复追赶期间缓存与限流重建：缓存 MUST 惰性重建或受控预热，限流 MUST 平滑恢复；重建 MUST NOT 放开无界流量，MUST NOT 以旧缓存覆盖新权威事实；重建进度与降级状态 MUST 可观测。
- **FR-24**: 观测（章程 XII）：MUST 暴露至少——API/RPC p95/p99 与吞吐（按接口类）、Outbox 待发数与最老待发等待、发布失败计数、事件通道积压与消费者 lag、追赶时间、重试/隔离计数、缓存命中/未命中、限流拒绝计数、Redis/Kafka 可用性；结构化日志含事件身份、链身份、业务身份、尝试次数，MUST NOT 含密钥/凭据；告警阈值 MUST 有依据（plan/实测），本规格 MUST NOT 编造数值。
- **FR-25**: 对照基准与价值证明（章程 XIII 与「架构演进」；PD-3 已裁决）：Kafka 保持在 013 已明确的规划与验证范围内，本轮 MUST NOT 预判其性能或可靠性收益，MUST NOT 以尚未运行的基准取消或删减范围；plan MUST 以 ADR 写明引入理由、PG-only 替代方案、额外运维与故障成本，并设计可比基准；MUST 在相同负载与故障场景下产出「仅持久库路径」与「启用缓存/限流 + 事件通道路径」的对照报告，至少含 p95/p99、吞吐、错误率、资源观测与追赶时间；取得实测证据后 MUST 报告结果；若结果支持调整 Kafka 范围，MUST 另行提交具体变更供用户决定，MUST NOT 自动删减；MUST NOT 无实测宣称价值；未测数值 MUST 标待测/待裁决。
- **FR-26**: 故障演练验收：MUST 在本地确定性环境（Anvil + PostgreSQL + Redis + Kafka + Docker Compose；章程 X）执行——双故障（关 Redis+Kafka，保 PG+本地链）下按矩阵验证七类关键资金业务；恢复后事件补齐、消费者进度恢复、0 重复提款意图/链上付款、0 权威状态丢失；入账幂等以模拟上游消费者/集成证据验证并写明验证边界；MUST NOT 依赖公网测试网。
- **FR-27**: 范围与留白：本规格 MUST NOT 锁定表结构、topic/partition/key、消费组与 offset 载体、缓存键与失效策略、限流算法、重试与退避参数、事件字段命名、迁移编号；以上留 plan 并给出初值与理由；MUST NOT 把架构建议表述为已批准规则；本步骤不产出 plan/ADR（ADR 属 plan 交付，见 FR-25）；影响正确性的未决问题 MUST 显式标注。

### Key Entities

- **业务事件（Business Event）**：业务状态变化的事实通知；属性：事件身份、类型、schema 版本、业务对象身份与单调版本、载荷、链身份（适用时）、发生时间；不是执行许可。
- **事件身份（Event Identity）**：稳定去重标识；EVM 日志派生为 `(chain_id, block_hash 或 tx_hash, log_index)`，业务对象事件为稳定业务身份；UNIQUE 约束；同身份异内容 = 冲突。
- **Outbox 记录**：与业务状态同事务持久化的事件记录；含发布状态、尝试计数、发布时间；积压属性（待发数、最老待发等待）。
- **发布器（Publisher）**：至少一次发布；崩溃/重启/多实例竞争下从持久状态恢复；有界重试。
- **消费者（Consumer）**：持久幂等应用、版本守卫、有界重试、fail-closed 版本处理。
- **消费者进度（Consumer Progress）**：持久位置与 lag；重启/重放/追赶的恢复依据；可观测。
- **隔离区（Quarantine）**：毒事件/未知版本的持久隔离载体；审计、告警、修复后重放。
- **缓存条目（Cache Entry）**：非权威；失效范围、新鲜度标注；故障时直读权威。
- **限流策略（Rate Limit Policy）**：按接口类的限流与失效处置规则；资金写入不得无限制。
- **修订事件（Revision Event）**：旧身份 + 新 canonical 状态/Orphaned 处置 + 原因 + 恢复版本；幂等、非付款指令。
- **故障状态与恢复追赶（Failure State & Catch-up）**：五态定义、矩阵行为、积压/进度/缓存重建的可观测状态。
- **演练与基准证据（Drill & Benchmark Evidence）**：双故障演练记录、模拟上游消费者入账幂等证据（含验证边界声明）、对照报告。
