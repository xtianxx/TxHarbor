## ADR-013-01：采用 Redis 承载非权威缓存与分布式限流

### Context

- 013 规格要求：查询在权威状态变化后不得返回陈旧财务权威、缓存故障可回源、限流失效时新提款创建 fail-closed 且存量流程继续（PD-1/FR-17/18/23）。
- 当前仓库为 `Go + PostgreSQL + Anvil`，无缓存与分布式限流载体；单部署多实例的未来形态下，进程内限流无法约束实例总量。
- 章程 XIII：Redis「MUST NOT replace PostgreSQL correctness guarantees」；Redis 只能做非权威用途。

### Decision

引入 Redis 作为**非权威**载体：cache-aside 缓存（epoch 命名空间 + 事件驱动失效 + TTL 兜底 + 新鲜度标注）与分布式限流（原子脚本按接口类）。正确性边界始终在 PostgreSQL：缓存不参与决策、限流不参与授权、Redis 故障不改变门禁与资金状态（[contracts/redis.md](contracts/redis.md)）。

### Alternatives considered

| 替代 | 评估 | 结论 |
|---|---|---|
| 无缓存（纯 PG） | 正确性成立；重复读放大、故障演练与限流矩阵无法实现 PD-1 的分布式语义 | 不足以满足已批准规格 |
| 进程内缓存/限流 | 多实例下总量不可界、失效不可传播，违反 FR-17/18 | 拒绝 |
| PG 承载限流计数 | 权威库承压、热点行争用，且把非权威逻辑压入权威库 | 拒绝 |
| 其他 KV（如 keydb/valkey） | 与 Redis 协议兼容，差异不构成决策要点 | 保留为部署替换选项 |

### Consequences

- **复杂度**：+1 中间件（部署、健康检查、连接管理、版本升级）；缓存失效协议成为新的一致性面（由事件驱动 + epoch + TTL 三层覆盖）。
- **故障成本**：Redis 故障 = 查询降级（回源有界）、新提款创建拒绝（PD-1）；不得影响存量资金流程与门禁。演练必须证明这一点（V-RATELIMIT/V-CACHE）。
- **运维成本**：内存与淘汰策略监控、epoch 轮换、限流策略配置发布。
- **收益假设（待验证，不预判）**：读路径负载下降、限流统一；由 §3 对照基准测量。

### Review triggers

- 对照基准显示缓存/限流未带来可测收益；或故障演练出现任何门禁绕过/陈旧权威；或运维成本超出收益 → 另行提交范围调整提案（不自动删减）。

## ADR-013-02：采用 Kafka + 事务性 Outbox 承载异步事件投递

### Context

- 013 规格要求：业务状态与事件同事务（Outbox 替代双写）、至少一次发布、消费者持久幂等与追赶、重组修订事件、容量保护（FR-07/08/11/13/20/21）。此前仓库没有任何事件通道；002–011 的事件均为 PG 内表，由各自流程读取。
- 章程 VI 明确「database write -> Kafka publish」不得假定原子，要求 transactional Outbox 或等价机制；章程 XIII 要求 Kafka 引入前说明价值，PD-3 要求 ADR + 可比基准，且不预判收益、不自动取消范围。

### Decision

采用**事务性 Outbox（PostgreSQL 权威）+ Kafka 至少一次投递 + 消费者幂等处理**：`internal/events` 提供 `Append`（同事务）、发布器（SKIP LOCKED + 租约 + acks=all）、消费者运行时（inbox/版本/进度/隔离/重放）。明确不宣称跨系统恰好一次；事件通道仅作异步通知，不承担权威。

### Alternatives considered

| 替代（PG-only 方向） | 评估 | 结论 |
|---|---|---|
| 无事件通道，上游继续各自轮询 PG | 正确性可行；解耦/消费位点/隔离/追赶语义需每个消费者自建，多消费者时重复实现与耦合 | 作为**对照基准基线路径**保留 |
| Outbox + 消费者直接轮询 PG（无 Kafka） | 少一个中间件；发布确认、位点、rebalance、隔离、背压全部自建，且轮询放大权威库读；多消费者扩展差 | 基准对照路径；不进默认架构 |
| PG `LISTEN/NOTIFY` | 无持久队列语义（断开即丢通知）、不承担至少一次，需 Outbox 兜底后仍要消费者 | 拒绝为投递载体 |
| Debezium/CDC 读 WAL | 额外运行时依赖；spec/FR-28 明确非本阶段依赖（PD-3 收口） | 显式不引入（§5） |
| 其他 broker（NATS/RabbitMQ） | 语义与生态差异不构成决策要点；Kafka 是规格已批准方向 | 不评估 |

### Consequences

- **复杂度**：+1 中间件 + 发布器/消费者运行时 + 事件目录/版本契约；但换来与已批准规格一致的投递语义。
- **故障成本**：Kafka 停机 = 投递停止、Outbox 积压（容量保护介入，PD-2）；业务继续、0 丢失；恢复后追赶（PD-3 场景验证）。
- **运维成本**：broker 运维、topic/分区/保留策略、消费 lag 监控、重放工具（已设计）。
- **收益假设（待验证，不预判）**：异步解耦、消费者独立扩展与位点管理、权威库读放大下降、故障隔离；由 §3 基准测量。

### Review triggers

- §3 基准结果支持调整 Kafka 范围 → MUST 另行提交具体变更供用户决定，不自动删减（PD-3）；
- 实测显示投递/追赶/容量保护无法满足 SC-09/10 → 报告并进入范围复核；
- Debezium 的引入只可能在后续独立架构决策采纳后评估（§5）。

## 3. 同负载对照基准设计（FR-25/SC-11）

**目标**：在相同负载与相同故障场景下，量化「仅持久库路径（PG-only）」与「启用缓存/限流 + 事件通道路径（全栈）」的差异；不预判结论。

**路径定义**：

- A（PG-only）：PG + Anvil；013 接线关闭（不启 Redis/Kafka；发布器/消费者不运行；查询直读 PG；事件在 outbox 累积但不投递，或按对照配置停发射——仅用于对照实验）。
- B（全栈）：PG + Anvil + Redis + Kafka；缓存/限流/发布器/消费者全开。

**受控变量**：同一主机/同一 PG 实例规格/同一 Anvil/同一数据集与初始状态/同一负载生成器与脚本（速率阶梯与突发模式固定）/同一故障注入时间线（正常 → 仅 Redis 故障 → 仅 Kafka 故障 → 双故障 → 恢复追赶）。

**采集口径**（明细 [verification.md](verification.md) §1）：API/RPC p95/p99 与吞吐（按接口类）、错误率、资源观测（CPU/内存/磁盘 IO/网络/连接数）、Outbox 最老等待与待发量、发布失败、消费积压与追赶时间。

**环境规格记录**：硬件、OS、容器镜像 tag、PG 参数、Kafka 分区/副本、Redis 配置、数据集规模、负载脚本 commit；不满足同构的记录不得作为对照结论。

**报告字段**：路径 A/B × 场景 × 指标（中位数/分位数/方差）、故障期降级行为对比、追赶时间、资源占用、结论与置信限制；未测数值 0 次表述为达标（SC-11）。

**决策规则**：结果只用于「报告 + 是否另行提交范围调整提案」；不自动改动 013 范围（PD-3）。基准脚本与报告作为验收证据留存，属独立 Performance 层（FR-28），不阻塞普通 PR。

## 4. 范围保持（PD-3 边界）

- Kafka **保持**在 013 已明确的规划与验证范围内；本轮不预判其性能/可靠性收益，也不以尚未运行的基准取消或删减范围。
- 取得实测证据后 MUST 报告结果；若结果支持调整 Kafka 范围，MUST 另行提交具体变更供用户决定，**不自动删减**。
- 本 ADR 不改变任何已裁决边界（PD-1–PD-4）。

## 5. Debezium 明确不引入

- Debezium（或等价 CDC）**不是** 013 的运行依赖，也不是测试矩阵的一部分（FR-28 收口）。
- 013 的事件发射采用显式 `Append`（R1）；不读 WAL、不依赖逻辑复制槽。
- 仅当后续独立架构决策实际采纳 CDC 时，才按该决策重新评估其测试矩阵与运维要求。

## 6. 状态与承诺

本 ADR 为设计阶段提案（Proposed）：接受「引入并验证」，拒绝「预判收益」；实现批次固定客户端/镜像 tag 后补记「Accepted/实施记录」；基准结果回填本文件或追加报告并按 PD-3 流程处理范围问题。
