## Background, Goals & Scope

### Background

TxHarbor 为交易所、托管平台和 Web3 钱包后台提供可恢复、可审计的链上资产处理能力。第一版保持单部署单链、白名单标准 ERC-20、原生币仅用于 gas，不维护用户余额账本，不承担 KYC、风控审批或冷热钱包调度，不引入 Redis、Kafka 或其他新增基础设施，本地使用 Anvil，Go + PostgreSQL + EVM JSON-RPC。项目章程为 Constitution 1.1.0（`.specify/memory/constitution.md`）。

本规范是 TxHarbor 第 011 号功能规范，也是执行链的最后一环。上游已交付：007 接收请求、008 预留并绑定 nonce、009 隔离签名、010 管理交易尝试与广播。本规范负责"谁来执行"：对 007 请求做执行准入，创建稳定付款意图，通过领取与租约确定排他执行者，消费受控授权，调用 010 推进广播，对未知结果与重组修订做追踪，并提供请求状态投影。010/011 联合验收在本规格定义需求，不在本步骤执行。

### Goals

- 执行准入只放行同时满足认证、固定权限、有效逐笔授权与当前门禁的 007 请求；Accepted 不等于执行授权。
- 为每个准入请求创建稳定付款意图（`intent_id ↔ 007 request_id`），先于 008 预留持久化；一 request 至多一 intent；重试、崩溃与未知结果复用原意图。
- sender 取自钱包注册表并在准入时固定；沿用原 `chain_id + sender`。
- 领取、续租与执行资格版本确定排他执行者；失格 worker 的写入被拒，其三类发送被 010 侧围栏阻止；合法接管者重验后可恢复，不建第二意图。
- 消费既有受控授权入口的授权；调度职责不授予签发权；授权绑定到唯一 intent。
- 调用 010 推进执行；重试、崩溃与未知结果下复用原意图、nonce 及交易历史。
- 请求状态投影仅用于显示，以 010 持久事实为权威；保留来源版本与更新时间，防止旧版覆盖新版，不明标过期。
- 重组后修订结果并追踪原意图；定义真实全链验收需求。

### Non-Goals / Out of Scope

- 交易构造、签名调用前持久化、签名字节落盘、广播、重播与替换广播（010 职责；011 只调用，不重复实现）。
- 签名生成、密钥持有与签名策略（009 职责）。
- nonce 分配与绑定创建（008 职责）。
- 余额账本、KYC、风控审批、冷热钱包调度；多链调度（v1 单部署单链语义沿 006/007）。
- 具体数据库结构、锁机制、租约算法与模块接口（留给 plan）。
- 生产 provider 选型（T000-P 保持 open）；全链 E2E 执行本身（A-13 保持 open，本规格只定义其需求）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 执行准入与意图创建（Priority: P1）

操作员提交 007 请求进入执行；系统校验认证、固定权限、有效逐笔授权与当前门禁，创建稳定付款意图并持久关联原请求，先于 008 预留。Accepted 但授权缺失的请求不得准入。

**Why this priority**：意图是全链身份根；错误的准入会污染 nonce、签名与广播全链路。

**Independent Test**：以合规请求与缺授权/过期授权/暂停期请求分别驱动准入，断言前者恰建一个意图，后者零意图创建；断言意图先于 008 预留存在。

**Acceptance Scenarios**：

1. **Given** 007 请求 Accepted 且授权有效、无暂停且恢复版本一致，**When** 执行准入，**Then** 创建唯一 `intent_id` 并持久关联 `request_id`，且先于 008 预留。
2. **Given** 授权缺失、过期、撤销、不匹配或不可验证，**When** 执行准入，**Then** 拒绝准入，不创建意图。
3. **Given** 同一 `request_id` 已有关联意图，**When** 重复准入（含并发与重启后），**Then** 复用原意图，不创建第二意图。

---

### User Story 2 — 领取、续租与执行资格版本（Priority: P1）

已准入的执行请求被某 worker 领取并持有有效租约；租约须续展，过期即失格。执行资格随版本推进，旧版本依据不得用于新动作。

**Why this priority**：排他执行是防重复付款的第一道闸；租约是失格判定的唯一依据。

**Independent Test**：双 worker 竞争领取同一请求，断言恰一成功；租约过期后原持有者动作被拒；版本推进后旧版本依据被拒。

**Acceptance Scenarios**：

1. **Given** 执行请求待领取，**When** 两个 worker 并发领取，**Then** 有且仅有一个获得排他执行权，另一方失败且不产生副作用。
2. **Given** worker 持有有效租约，**When** 租约过期前续展，**Then** 执行权延续；过期后未续展，**When** 发起任何执行动作，**Then** 被拒绝。
3. **Given** 执行资格版本已推进，**When** 持旧版本依据发起动作，**Then** 被拒绝。

---

### User Story 3 — 失格与合法接管竞争（Priority: P1）

原 worker 失格时，其数据库写入被拒，其三类发送被 010 侧围栏阻止；合法接管者在重验全部当前门禁后承接原意图与历史继续执行，不建第二意图；已发出者无法撤回，保留事实或未知并对账。

**Why this priority**：失格不停机就等于双执行者；接管不断链就等于断付。两者须同时成立。

**Independent Test**：模拟失格 worker 继续写库与继续请求发送，断言写库被拒且 010 侧发送被拒；模拟接管者重验后恢复，断言原意图延续且历史完整。

**Acceptance Scenarios**：

1. **Given** worker 已失格，**When** 其尝试写入执行状态，**Then** 写入被拒绝。
2. **Given** worker 已失格，**When** 其凭旧租约/旧版本请求 010 发送（含重播与替换），**Then** 010 侧按当前门禁拒绝，不发送。
3. **Given** 合法接管者已重验当前授权、暂停、恢复版本及执行资格，**When** 接管原意图，**Then** 复用原 `intent_id`、原 nonce 与既有尝试历史继续执行，不创建第二付款意图。

---

### User Story 4 — 调用 010：重试、崩溃与未知复用（Priority: P2）

执行 worker 调用 010 推进广播；重试、崩溃重启与结果未知下复用原意图、nonce 及交易历史，不重建付款。

**Why this priority**：未知即重建等于重复付款；崩溃即丢失等于断付。

**Independent Test**：注入调用超时、崩溃重启与未知结果，断言复用同一意图与历史；断言未知结果进入对账而不新建付款。

**Acceptance Scenarios**：

1. **Given** 010 调用超时或响应丢失，**When** worker 重试，**Then** 复用原意图与既有尝试，不新建付款意图。
2. **Given** worker 在执行中崩溃重启，**When** 恢复，**Then** 从持久记录重建执行位置，不重复领取已完成的副作用。
3. **Given** 交易处于结果未知，**When** 继续推进，**Then** 先对账后决策，不以"未知即失败"为由重建付款。

---

### User Story 5 — 请求状态投影与新鲜度（Priority: P2）

查询端展示执行请求状态；投影仅用于显示，以 010 持久事实为权威；保留来源版本与更新时间；旧版不覆盖新版；新鲜度不明标可能过期；任何执行类决策读验当前权威事实。

**Why this priority**：过期显示误导操作员手工干预；显示误作许可等于越权。

**Independent Test**：构造修订滞后与新鲜度不明场景，断言旧版不覆盖新版且标过期；断言决策路径不读取投影缓存。

**Acceptance Scenarios**：

1. **Given** 010 事实已修订而投影滞后，**When** 查询，**Then** 不用旧版覆盖新版，且标记可能过期。
2. **Given** 需做执行/重播/替换决策，**When** 读取状态，**Then** 读验 010 当前权威事实，不以投影为许可依据。

---

### User Story 6 — 重组修订、恢复追踪与全链验收需求（Priority: P2）

重组导致回执失效或确认回退时修订结果并追踪原意图；恢复期间遵守暂停矩阵；本规格定义真实全链验收（HTTP/PG/Anvil）的需求与成功标准，不执行测试。

**Why this priority**：重组后账实不符是资金风险；验收需求是联合验收的合同。

**Independent Test**：本步骤只定义需求；可测性由 FR-14 的场景清单与 SC 保证。

**Acceptance Scenarios**：

1. **Given** 确认后重组致回执失效，**When** 修订，**Then** 按当前恢复版本更新结果、保留修订链并追踪原意图，不建新意图补偿。
2. **Given** 恢复暂停生效，**When** 执行推进，**Then** 新发送类动作暂停，未知保留对账；恢复后按当前门禁恢复。

---

### Edge Cases

- 并发领取：恰一成功；失败方零副作用，可稍后重试领取其他请求。
- 租约中途过期：过期后动作一律被拒；在途未知保留对账，由接管者承接。
- 旧 worker 与接管者竞争：旧者写入与发送均被拒；接管者须重验全部门禁后方可动作。
- 授权在执行中过期/撤销：后续发送被拒；已落盘与已发出事实保留；重播替换同样被拒。
- 暂停在执行中生效：新发送暂停；未知保留；多暂停并存时解除其一不绕过其余。
- 广播未知归属：未知挂在原尝试与原意图下，不新建意图；接管者对账同一未知。
- 旧尝试未知时替换到达：先对账旧尝试；替换与旧尝试共存于同一意图。
- 回执失败/Transfer 不符：记未生效并记录差异；不标记成功，不自动重付。
- 确认后重组：修订链保留；原意图延续。
- 领取后长期无进展：按 FR-04 标记处置（策略待 M3 裁决）；默认不自动丢弃。
- 恢复版本变化：旧版本依据一律失效；新动作须基于当前版本。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-01**：执行准入 MUST 同时满足 007 请求 Accepted、调用方认证、固定接口权限、有效逐笔授权与当前门禁（无阻断性暂停、恢复版本一致）。Accepted MUST NOT 被解读为执行授权；任一不满足 MUST 拒绝准入且不创建意图。
- **FR-02**：准入通过后系统 MUST 创建稳定付款意图：独立 `intent_id` 并持久关联 007 `request_id`，先于 008 预留；一个 `request_id` 至多一个 intent；并发、重试、重启与结果未知 MUST 复用原 intent；MUST NEVER 为同一请求创建第二意图，MUST NEVER 为未知结果或接管创建补偿意图。
- **FR-03**：sender MUST 取自机构控制的钱包注册表/部署配置，在准入时固定并绑定 `intent_id + chain_id`；重试与替换 MUST 沿用原 `chain_id + sender`；调用方声明 MUST NOT 作为权威来源。注册只证明可用性，不构成执行授权。
- **FR-04**：执行请求 MUST 被排他领取；领取 MUST 持有有效租约，租约过期即失格；执行资格 MUST 随版本推进，旧版本依据 MUST NOT 用于新动作。租约续展、版本号的具体取值与载体留 plan；失格判定语义（过期即失格）为本规格锁定。[NEEDS CLARIFICATION: 租约到期后原执行者是否允许重新领取同一请求，还是必须移交接管者——见 M1，影响断点续做与公平语义。]
- **FR-05**：worker 失格后，其执行状态写入 MUST 被拒绝；011 MUST 向 010 提供可核验的当前执行资格及接管语义，配合阻止失格 worker 凭旧租约/旧版本/旧准入结论发起首次广播、重播与替换（Q2）。围栏针对发起时当前资格，不永久冻结原交易；已发出者无法撤回，MUST 保留事实或未知并对账。
- **FR-06**：合法接管者 MUST 在重验当前授权、暂停、恢复版本及执行资格后承接原意图、原 nonce 与既有尝试历史并按既定规则恢复；MUST NOT 创建第二付款意图；接管 MUST 保留完整历史链。
- **FR-07**：每笔执行 MUST 消费既有受控授权入口供给的显式逐笔授权；调度职责 MUST NOT 被解读为签发权；授权 MUST 绑定到唯一 intent；缺失/过期/撤销/不匹配/不可验证 MUST fail-closed。费用替换沿 PB 条件式复用（用途允许且三维费用全满足方可复用，否则新授权），不默认每次重新签发。
- **FR-08**：011 MUST 调用 010 推进广播类动作；重试、崩溃重启与结果未知下 MUST 复用原意图、原 nonce 与交易历史；MUST NOT 为未知结果或接管新建付款；未知 MUST 先对账后决策。010 尝试身份与内容由 010 拥有，011 MUST NOT 另建冲突身份。
- **FR-09**：请求状态投影 MUST 仅用于显示：010 持久事实是唯一权威；投影 MUST 保留来源版本与更新时间；收到重组或修订后更新，MUST NOT 用旧版覆盖新版；无法确认新鲜度时 MUST 明确标记可能过期，MUST NOT 将旧终态呈现为已核验的当前结果；执行、重播、替换或结束恢复追踪的决策 MUST 读取并验证当前权威事实（Q1）。显示延迟的业务时限本次未指定；若确需，提出有依据的建议供用户裁决。
- **FR-10**：重组导致回执失效或确认回退时，系统 MUST 按当前恢复版本修订结果、保留修订链并追踪原意图；MUST NOT 重建意图补偿。[NEEDS CLARIFICATION: 修订动作是否需要新的执行授权，还是原授权延续覆盖修订——见 M2，影响重组后自动修订的合法性。]
- **FR-11**：011 MUST 遵守与 010 同一广播安全矩阵（Q3）：每次发送类推进须当前授权、暂停、恢复版本与执行资格全过；失效后无重播例外或 TTL 宽限；排队、检查通过或发送意图不等于合法在途；可阻止则阻止，否则保留事实或未知对账。多个独立暂停并存时解除其一 MUST NOT 绕过其余；011 MUST 只读观察暂停与恢复行，MUST NOT 解除或清除。
- **FR-12**：执行请求生命周期 MUST 为显式状态机（至少：已准入 → 已领取 → 执行中 → 已完成 / 未知对账中 / 已失败 / 已修订）；非法转换 MUST 拒绝或记为错误；影响持久行为的转换 MUST 在事务边界内（章程 V/VI）。
- **FR-13**：关键操作 MUST 结构化日志与可观察信息（含 request/intent 身份、sender、nonce引用、授权身份与版本、租约与资格版本、恢复版本、重试/尝试引用，不含密钥与凭据）；金额禁用浮点（章程 I/XII）。
- **FR-14**：真实联合验收需求 MUST 覆盖并发领取、租约失效、旧 worker 与接管者竞争、重启、授权失效、暂停/恢复、广播未知、替换、回执失效及确认后重组；MUST 使用真实 HTTP/PG/Anvil 联合环境，mock 与旧机制测试 MUST NOT 代替；010→011 合并顺序保留，必要上游同步先于真实联合验收。本规格只定义验收要求，不执行实现或测试。
- **FR-15**：领取后长期无进展的请求 MUST 被标记并保留完整证据，MUST NOT 静默丢弃或自动重建付款。[NEEDS CLARIFICATION: 处置策略是超时自动回收重排还是仅人工介入——见 M3，影响无人值守语义。]

### Key Entities

- **执行请求（Execution Request）**：已准入的 007 请求的执行形态；属性：归属调用方、`request_id`、`intent_id`、状态（显式状态机）、领取者与租约版本。
- **付款意图（Payment Intent）**：稳定身份 `intent_id`，持久关联 `request_id`，先于 008 预留存在；重试/未知/接管一律复用。
- **领取与租约（Claim & Lease）**：排他执行权及其有期证明；过期即失格；续展与版本号留 plan。
- **执行授权（Execution Authorization）**：受控入口供给的逐笔许可；绑定唯一 intent；调度不等于签发。
- **状态投影（Status Projection）**：仅显示用途的派生视图；权威为 010 持久事实；带来源版本与更新时间。
- **修订（Revision）**：重组后的结果更新链；追踪原意图；不建新意图。
