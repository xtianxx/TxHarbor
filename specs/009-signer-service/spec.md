## Background, Goals & Scope

### Background

TxHarbor 为交易所、托管平台和 Web3 钱包后台提供可恢复、可审计的链上资产处理能力。第一版保持单部署单链、白名单标准 ERC-20、原生币仅用于 gas，不维护用户余额账本，不承担 KYC、风控审批或冷热钱包调度，不引入 Redis、Kafka 或其他新增基础设施，本地使用 Anvil，Go + PostgreSQL + EVM JSON-RPC。

本规范是 TxHarbor 第 009 号功能规范，目录固定为 `specs/009-signer-service`。项目章程为 Constitution 1.1.0（`.specify/memory/constitution.md`）。仓库已存在 `specs/001-project-foundation` 至 `specs/007-withdrawal-creation`。章程原则 VIII 是本节的主导约束：业务服务 MUST NOT 直接拥有或暴露私钥；签名 MUST 在显式签名边界后完成，边界接受结构化签名请求并做策略校验（许可链、来源钱包、目标策略、金额上限、合约/函数白名单、审计日志）；`KeyProvider` 或等价抽象 MUST 隔离签名实现；本地开发仅用一次性测试密钥。

仓库现状（001–007 已交付）：Go 模块、配置、数据库迁移、HTTP 监听、认证辅助、恢复门禁读取辅助、指标与结构化日志已存在；**独立签名服务、密钥提供者、签名请求载体尚不存在**（本规范提出需求，结构与算法留给 plan）。008/009 的并行门禁见 `docs/workflow-008-009-parallel.md`（R1：各自完成 spec/clarify/plan/tasks/analyze 并闭合共同契约后才可并行实现；R2：一次只推进一个 Spec Kit 步骤；R5：009 可独立开发已确定契约下的进程隔离、认证、交易校验与签名核心，真实 nonce/意图绑定与恢复暂停接线等待依赖可用）。

### Goals

- 建立独立签名边界：仅签名服务可访问签名密钥；API / Indexer / Deposit / Withdrawal / Worker / Orchestration 等业务组件不得持有或读取密钥材料（章程 VIII）。
- 只接受结构化交易签名请求（完整交易内容）；禁止任意摘要/消息签名；请求通过完整校验（链、sender、资产与转账内容、收款方、金额、费用策略）。
- 签名请求身份与完整交易内容在持久层强绑定：同 ID 同参幂等收敛，同 ID 异参拒绝；重试、响应丢失、重启下行为确定。
- 仅返回签名与交易哈希；签名服务永不广播、不产生链上副作用。
- 继承上游已批准契约：nonce 绑定（OC-3 已裁决：008 拥有绑定、009 只读消费）、执行授权语义（OC-5 已裁决）、006 恢复暂停与版本隔离（OC-6/OC-7 已裁决 2026-09-16：暂停/撤销后不交付已持久化签名、交付前重验与竞争定界）。
- 测试密钥与部署密钥隔离；密钥材料与原始已签名交易永不进入日志、错误、响应或仓库。
- 失败路径一等且可测：密钥不可用、存储不可用、崩溃重启、重复投递、恢复版本变化。

### Non-Goals / Out of Scope

- nonce 分配、分配恢复与替换策略（008 职责；本规范只要求签名对象携带上游给定 nonce 且签名服务不得自行分配/改写）。
- 交易构造、广播、同字节重播、费用替换广播（010 职责）；本服务只签名、不广播。
- 付款意图创建与身份、交易尝试生命周期、worker 执行与重组后修订（011 职责）。
- 用户余额账本、KYC、风控审批、冷热钱包调度。
- 多链调度（v1 单部署单链语义沿 006/007）。
- Redis、Kafka、Kubernetes 等新增基础设施（章程 XIII）；生产 KMS/HSM 选型与接入（章程 VIII 只要求设计不阻碍迁移）。
- 上游授权/意图记录的供给入口与存储设计（本服务消费其契约，设计留 plan）。
- 表结构、锁机制、密码学库、传输协议、模块接口、字段命名（留给 plan）。
- 生产 provider 选型（T000-P 保持 open）。

## Clarifications

### Session 2026-09-16

- Q: 付款意图由谁、何时创建，如何与 007 请求关联；007 的 Accepted 是否构成意图？（OC-1） → A: 011 在执行准入时创建并持久化付款意图；意图拥有独立、稳定的 intent_id，与 007 request_id 持久关联。007 的 Accepted 不是意图；一个 request_id 至多映射一个意图；意图 MUST 在 008 预留之前持久化。009 的签名请求 MUST 可追溯到意图（请求/尝试身份由 OC-4 裁决）。意图存在 MUST NOT 被解读为持续的执行许可（由 OC-5 裁决）。
- Q: sender 的权威来源是什么，009 如何校验请求 sender 与签名密钥？（OC-2） → A: sender 权威为机构控制的钱包注册表/部署配置。011 在准入时固定 sender，并绑定 intent_id + chain_id；重试与费用替换 MUST 沿用原 chain_id + sender。009 MUST 校验请求 sender 与意图绑定、注册表策略一致，且签名密钥与 sender 匹配，任一不符 MUST 拒绝；sender 未注册、已禁用或注册表不可读取 MUST 拒绝。注册只证明可用性，不构成执行授权（OC-5）。载体与并发机制留给 plan，并与 OC-6/OC-7 保持一致。
- Q: nonce 持久绑定由谁拥有，009 如何消费而不预设？（OC-3） → A: 008 拥有 nonce 持久绑定；009 通过显式只读契约消费，MUST NOT 修改该绑定，MUST NOT 复用 007 行。009 MUST 将 intent/chain/sender/nonce 与可信持久记录核对，MUST NOT 信任调用方声明的预留声明。读契约 MUST 区分五类结果：存在且匹配 / 不存在 / 冲突 / 暂停或对账中 / 读取失败或不确定；除“存在且匹配”外任何结果 MUST NOT 产生签名。绑定不构成授权（OC-5）；只读消费不解决 OC-6/OC-7。载体留给 plan；009 MUST 保持密钥隔离边界。
- Q: 签名请求身份与 010 交易尝试身份由谁分配，如何关联与去重？（OC-4） → A: 可信调用方预分配 signing_request_id。010 MUST 在首次签名调用前持久化 attempt_id、signing_request_id 与完整内容，并关联 intent_id 与 008 绑定。009 以“已认证调用方 + signing_request_id”界定请求身份，并持久绑定完整规范化内容（chain_id、sender、nonce、交易类型、to、value、data、gas limit 及所有适用费用/签名字段）与 intent/binding/attempt 引用。同 ID 同内容 MUST 复用原请求（在途或结果未知 MUST 从持久记录恢复，MUST NOT 以新身份重试）；同 ID 异内容 MUST 拒绝；签名结果 MUST 在成功返回前可靠持久化。一次尝试 = 一个请求身份；费用替换 MUST 使用新 attempt_id + signing_request_id，并隶属原 intent + 绑定。身份不是授权凭据（OC-5/OC-6/OC-7 管辖）。009 MUST 现在定义并校验该输入契约，不要求 010 已实现；符合契约的测试调用方可用。
- Q: 签名前是否必须存在显式逐笔执行授权，由谁签发、凭何校验、与签名请求如何关联？（OC-5） → A: 每笔交易 MUST 存在由指定可信上游业务授权方签发的显式逐笔执行授权；011 消费该授权用于准入，但调度职责本身不授予签发权。授权 MUST 具有稳定身份与可验证真实性，关联原始 007 请求与调用方，约束 chain/sender/资产/收款方/整数金额/费用范围，并具备到期与撤销语义。009 MUST 独立验证授权的真实性、当前有效性，以及 request→intent→binding→attempt→request 关联与内容一致性；MUST NOT 仅凭记录存在或调用方声明放行。授权缺失、过期、撤销、不匹配或不可验证 MUST NOT 产生新签名。授权作用于单一意图；重试 MUST NOT 消耗或延长授权；每个签名请求 MUST 持久绑定其授权身份与版本；费用替换 MUST 需要显式允许该用途的授权，否则 MUST 先取得新授权并使用新身份。授权撤销后签名结果的重放由 OC-6/OC-7 管辖（MUST NOT 默认允许）。首版 MUST 复用 007 已批准的授权载体与语义；缺口 MUST 显式记录，MUST NOT 静默改写 007。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 结构化交易签名请求与任意摘要拒绝 (Priority: P1)

已认证的调用方提交表达完整交易内容的签名请求；服务校验通过后返回签名与交易哈希。任何缺少完整内容、或要求对任意摘要/裸哈希/消息直接签名的请求一律被拒绝，且不产生签名。

**Why this priority**: 这是签名边界存在的理由；任意摘要签名等价于把密钥交给调用方（章程 VIII 安全规则）。

**Independent Test**: 在本地环境提交含 chain、sender、nonce、收款方、金额/转账内容、费用参数的合规请求，断言返回的签名可按同一内容独立验证且哈希与内容一致；再提交裸摘要/消息签名请求，断言无签名、无持久化结果。

**Acceptance Scenarios**:

1. **Given** 调用方通过认证且请求携带完整交易内容，**When** 提交签名请求，**Then** 服务校验通过后返回签名与交易哈希，且签名可由第三方从同一内容独立验证。
2. **Given** 请求仅提供摘要/裸哈希/任意消息、没有可解析的完整交易内容，**When** 提交签名请求，**Then** 服务拒绝且 MUST NOT 返回签名。
3. **Given** 请求缺失任一必需内容字段（链、sender、nonce、收款方、金额/转账内容、费用参数），**When** 提交，**Then** 服务拒绝且不签名（不得以默认值补全改变语义的字段）。
4. **Given** 服务完成签名，**When** 请求结束，**Then** 服务 MUST NOT 广播、MUST NOT 占用或分配 nonce、MUST NOT 产生任何链上或对外副作用（仅返回签名与哈希）。

---

### User Story 2 — 调用方认证与最小权限 (Priority: P1)

只有经过认证且被允许使用签名能力的调用方可提交签名请求；调用方身份由服务端依据凭据判定，不得信任请求体自报字段；未认证或无权限请求被拒绝，且不泄露其他调用方信息。

**Why this priority**: 安全基线；未认证的签名接口等于公开的密钥代理。

**Independent Test**: 以缺失/无效凭据、有效凭据但无签名权限分别提交，断言均被拒绝且零签名；断言响应、日志与错误不含凭据材料。

**Acceptance Scenarios**:

1. **Given** 请求缺失或携带无效/已吊销凭据，**When** 提交签名请求，**Then** 拒绝认证且不产生签名。
2. **Given** 调用方已认证但未被授予签名能力许可，**When** 提交签名请求，**Then** 拒绝授权且不产生签名。
3. **Given** 请求体自报 caller/sender/归属身份与认证身份不一致，**When** 提交，**Then** 服务以服务端判定身份为准，MUST NOT 仅凭自报字段通过校验或建立归属。
4. **Given** 调用方 A 尝试读取或重试调用方 B 的签名请求结果，**When** 提交，**Then** 不得返回 B 的结果内容（响应不泄露归属或存在性）。

---

### User Story 3 — 签名请求身份与内容持久绑定；同 ID 异参拒绝 (Priority: P1)

签名请求拥有唯一身份；该身份与完整交易内容在持久层强绑定。同 ID 同参重试收敛到同一结果；同 ID 异参被拒绝且不签名。

**Why this priority**: 章程 II；身份与内容脱绑会让重试变成"用旧身份签新交易"。

**Independent Test**: 同 ID 同参提交两次（断言第二次返回原结果、可观察签名恰好 1 个）；同 ID 改任一受绑定字段（chain/sender/nonce/收款方/金额/转账内容/费用）再次提交（断言冲突、原结果不变、零新签名）。

**Acceptance Scenarios**:

1. **Given** 请求 R（身份 K、内容 C）已产生签名结果，**When** 以 K 与 C 重试，**Then** 返回原签名结果，不产生第二个签名。
2. **Given** 请求 R（身份 K、内容 C）已产生签名结果，**When** 以 K 与内容 C′（任一受绑定字段不同）提交，**Then** 服务拒绝冲突、原结果不变，MUST NOT 对 C′ 签名；C′ 需要新身份的请求。
3. **Given** 内容 C 的请求已签名，**When** 服务重启后以 K 与 C 重试，**Then** 从持久层返回原结果（确定性不依赖内存状态）。
4. **Given** 两个并发提交使用同 K 同 C，**When** 同时到达，**Then** 有且仅有一个签名结果被持久化，双方得到同一结果（持久层保证，非应用内存检查；机制留给 plan）。

### User Story 4 — 校验矩阵：链、sender、资产/转账内容、收款方、金额、费用 (Priority: P1)

任一校验失败的请求在产生签名前被拒绝，拒绝原因可审计、可分类。

**Why this priority**: 财务正确性入口；校验缺失即把策略执行交给调用方。

**Independent Test**: 逐项构造非法矩阵，断言全部拒绝、零签名、原因分类正确；合法矩阵断言全部通过。

**Acceptance Scenarios**:

1. **Given** `chain_id` 不在许可集合或与本部署服务链不符，**When** 提交，**Then** 拒绝且不签名。
2. **Given** sender 不在许可来源钱包策略内，**When** 提交，**Then** 拒绝且不签名（sender 权威来源见 FR-07：机构控制的钱包注册表/部署配置；OC-2 已裁决 2026-09-16）。
3. **Given** 资产/目标合约不在许可集合，或转账内容（calldata 声明的收款方/金额）与请求声明不一致，**When** 提交，**Then** 拒绝且不签名。
4. **Given** 收款方不符合目标策略（允许/拒绝集合或等价规则）或地址形状不合法，**When** 提交，**Then** 拒绝且不签名。
5. **Given** 金额为零、负数、含小数、非整数表达或超出 uint256 范围，**When** 提交，**Then** 拒绝且不签名；金额与费用比较 MUST NOT 使用浮点。
6. **Given** 费用参数（gas 上限、费用上限/单价）超出策略范围，**When** 提交，**Then** 拒绝且不签名；费用替换类请求在恢复期一律拒绝（US6）。
7. **Given** 各字段单独合法但与已绑定身份的内容冲突，**When** 提交，**Then** 按 US3 拒绝（不得因"字段合法"而签名）。

### User Story 5 — 密钥隔离、测试/部署密钥分离与日志保密 (Priority: P1)

签名密钥只存在于签名边界内；业务服务无法通过任何接口取得密钥；测试密钥与部署密钥配置隔离；密钥材料与原始已签名交易绝不进入日志、错误、响应或仓库。

**Why this priority**: 章程 VIII 与安全规则；密钥泄露即项目失败。

**Independent Test**: 检查业务服务代码路径与配置不含密钥访问能力；以测试/部署配置启动断言互不混用；扫描日志、错误输出与响应断言零密钥材料、零凭据、零原始已签名交易。

**Acceptance Scenarios**:

1. **Given** 业务服务（API/Indexer/Deposit/Withdrawal/Worker）运行，**When** 检查其代码路径、配置与依赖，**Then** 无密钥材料访问；签名仅能通过签名边界发起。
2. **Given** 部署模式配置指向部署密钥、开发模式配置指向一次性测试密钥，**When** 启动或执行签名，**Then** 两套配置互不退回、互不混用；部署模式 MUST NOT 静默使用测试密钥。
3. **Given** 任意签名成功或失败路径，**When** 检查日志、错误响应与审计记录，**Then** 私钥材料、凭据与原始已签名交易字节出现次数为 0。
4. **Given** 代码仓库，**When** 检查提交内容，**Then** 密钥材料出现次数为 0（章程安全规则）。

### User Story 6 — 继承 006 恢复暂停与版本隔离；永不广播 (Priority: P2)

恢复活跃期间不得产生新签名与费用替换签名；基于旧链视图的请求在恢复版本变化后不得提交签名；签名服务不广播、不改变 006 治理。
暂停/撤销生效后已持久化签名不得再交付：首次交付与同 ID 重试均须重验当前授权与暂停门禁，失败时仅返回不含签名材料的状态；008/006 暂停由 009 只读观察、不得清除或代为解除。

**Why this priority**: 006 契约承接（FR-26/downstream.md）；违反即破坏重组恢复安全边界。

**Independent Test**: 模拟恢复暂停（暂停行/活跃恢复行），断言签名一律拒绝并记录原因；在恢复版本变化前后用同一身份请求重试，断言旧版本内容不被签名；断言全流程零广播调用。
模拟授权撤销/暂停且结果已持久化，断言交付与同 ID 重试被拒且仅返回状态类结果；在门禁检查后、签名生成中、落盘后、交付竞争、响应丢失各时点注入暂停/撤销，断言无未经门禁的交付且记录完整；断言 008/006 暂停在 009 侧零清除。

**Acceptance Scenarios**:

1. **Given** 该链存在活跃恢复行或暂停行（006 语义），**When** 提交新签名请求或费用替换签名请求，**Then** 拒绝并记录拒绝原因，MUST NOT 排队为"已批准待恢复后执行"。
2. **Given** 请求内容基于恢复版本 v 的链视图，**When** 恢复版本在签名提交前变化，**Then** 该内容 MUST NOT 提交签名；请求方须以新视图重新构造内容（版本绑定语义沿 006 FR-26）。
3. **Given** 006 解除恢复暂停或其他独立暂停仍存在，**When** 签名服务判定，**Then** MUST NOT 清除或修改任何 006 暂停、恢复行、授权或旧结果隔离规则（只读消费）。
4. **Given** 任意签名结果，**When** 服务返回，**Then** 仅包含签名与哈希等结果事实；广播或链上写副作用出现次数为 0。
5. **Given** 授权已过期/撤销或该链处于恢复暂停，签名结果可能已持久化，**When** 首次交付或同 ID 重试返回，**Then** MUST 拒绝交付签名材料并记录授权版本/暂停依据/原因；仅返回经认证与权限校验、不含原始签名交易或可重构广播材料的状态查询结果；MUST NOT 静默换绑授权，MUST NOT 清除暂停。
6. **Given** 恢复暂停期间存在已持久化签名结果，**When** 调用方以同 ID 重试或查询，**Then** 仅返回不含签名材料的状态与暂停原因；恢复后再次返回仍 MUST 通过当前授权与暂停门禁；多个独立暂停并存时解除其一 MUST NOT 绕过其余；008 绑定事实与 009 签名材料分别表达。
7. **Given** 暂停/撤销在门禁检查后、签名生成中、结果落盘后、交付竞争或响应丢失任一时点生效，**When** 交付准入判定，**Then** 交付准入先于暂停/撤销生效且不可取消时记为在途已准交付（MUST NOT 声称可收回）；否则 MUST NOT 交付并保留请求/绑定/结果/拒绝依据，MUST NOT 重签、MUST NOT 释放 nonce；无法确定是否已交付或已产生副作用时进入结果未知与对账。
8. **Given** 006 或 008 存在独立暂停或对账中绑定，**When** 009 处理签名与状态查询，**Then** 009 只读观察、MUST NOT 清除或修改任何暂停/恢复行；暂停或对账中的 008 绑定读结果 MUST NOT 产生签名；MUST 记录所见暂停依据与拒绝原因；解除权限与释放证据标准以 008 裁决为准，009 MUST NOT 替代决定。

### Edge Cases

- 同身份请求正在处理中（首次尚未持久化）第二次到达：MUST 等待首次结果或返回等价语义，MUST NOT 产生第二个签名（机制留给 plan）。
- 响应丢失后重试：必须返回持久化的原结果；无法确认提交结果时 MUST NOT 声称"确定未签名"；重试必须安全（FR-14）。
- 服务在签名前后任意点崩溃：重启后 MUST NOT 产生与已持久化结果冲突的第二个签名；未产生结果的请求以原身份重试仍安全。
- 密钥提供者（本地/KMS/HSM）不可用或超时：MUST 有界失败、无部分成功；MUST NOT 把"密钥不可用"记为"已签名"。
- 存储不可用：MUST NOT 返回签名成功；已持久结果在存储可读时仍可获取。
- 重复投递（同请求多次到达，含跨进程）：幂等收敛（US3）。
- 请求身份格式非法或从未存在：查询/重试返回未找到语义，不泄露他人信息。
- 已裁决契约项（OC-1–OC-7 均于 2026-09-16 裁决，见 Assumptions 契约项表与 Clarifications）：OC-6 交付前门禁与 OC-7 竞争定界为已决定语义——授权过期/撤销或暂停后不交付已持久化签名、仅状态查询、首次交付与同 ID 重试均重验、多暂停不绕过、008/006 暂停只读观察；暂停/撤销先于交付准入则不得交付、在途已准交付不可收回、不确定转结果未知与对账、后续广播/重播各自门禁。实现 MUST NOT 在裁决之外自行固化额外规则。
- OC-7 竞争窗口：暂停/门禁检查通过与签名产出之间存在窗口；本规范要求提交前重验（FR-17/FR-23）；窗口隔离机制与交付准入先后顺序的具体载体留给 plan（OC-7 已于 2026-09-16 裁决，见 Clarifications）。
- 恢复状态翻转瞬间（恢复释放与签名并发）：以读取序列为准，MUST NOT 基于过期观察签名。
- 任意摘要伪装成"消息"、"哈希"或"待签数据"：一律拒绝（US1）。
- 日志脱敏边界：错误输出保留请求身份、链、sender、阶段、错误分类、重试次数等非敏感字段；凭据、密钥、原始已签名交易 MUST NOT 输出。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-01**: 系统 MUST 建立独立签名边界（独立签名服务/进程）：仅签名边界持有签名密钥访问能力；API、Indexer、Deposit、Withdrawal、Worker、Orchestration 等业务组件 MUST NOT 直接持有、读取或通过后门接口取得密钥材料（章程 VIII/安全规则）。
- **FR-02**: 签名 MUST 仅通过结构化交易签名请求发起；请求 MUST 表达完整交易内容（至少：chain_id、sender、nonce、收款方、金额/转账内容、费用参数）。系统 MUST NOT 接受任意摘要、裸哈希或任意消息作为签名对象；无完整内容的请求 MUST 被拒绝。
- **FR-03**: 服务 MUST 对完整内容签名，MUST NOT 增删、替换或静默补全会改变语义的字段；缺失必需字段 MUST 拒绝（不得以默认值改变签名对象）。
- **FR-04**: 所有签名请求 MUST 先认证；调用方身份 MUST 由服务端依据凭据判定，MUST NOT 信任请求体自报身份；凭据缺失、无效或已吊销 MUST 拒绝；凭据 MUST NOT 出现在日志、错误或仓库中。凭据签发/轮换/吊销与安全存储机制留给 plan。
- **FR-05**: 仅具备签名能力许可的调用方可提交签名请求；已认证但无权限 MUST 拒绝且不产生签名。固定调用方权限 MUST NOT 被表述为对某笔交易的执行授权。（OC-5，2026-09-16 已裁决，全文见 Clarifications）每笔交易签名前 MUST 存在由指定可信上游业务授权方签发的显式逐笔执行授权；011 消费该授权用于执行准入，但调度职责本身不授予签发权。授权 MUST 具有稳定身份与可验证真实性，关联原始 007 请求与调用方，约束 chain/sender/资产/收款方/整数金额/费用范围，并具备到期与撤销语义。009 MUST 独立验证授权的真实性、当前有效性，以及 request→intent→binding→attempt→request 关联与内容一致性；MUST NOT 仅凭记录存在或调用方声明放行。授权缺失、过期、撤销、不匹配或不可验证 MUST NOT 产生新签名。授权作用于单一意图；重试 MUST NOT 消耗或延长授权；每个签名请求 MUST 持久绑定其授权身份与版本；费用替换 MUST 需要显式允许该用途的授权，否则 MUST 先取得新授权并使用新身份。授权撤销后签名结果的重放按 OC-6/OC-7 裁决处理（2026-09-16 已裁决，见 Clarifications；MUST NOT 默认允许，交付门禁与竞争定界见 FR-17/FR-23）。首版 MUST 复用 007 已批准的授权载体与语义；缺口 MUST 显式记录，MUST NOT 静默改写 007。
- **FR-06**: 校验 MUST 覆盖 `chain_id`：必须为本部署服务链或许可集合成员；不匹配 MUST 拒绝且不签名。
- **FR-07**: 校验 MUST 覆盖 sender：sender 权威来源为机构控制的钱包注册表/部署配置（OC-2，2026-09-16 已裁决，全文见 Clarifications）。011 在准入时固定 sender 并绑定 intent_id + chain_id；重试与费用替换 MUST 沿用原 chain_id + sender。009 MUST 校验请求 sender 与意图绑定及注册表策略一致，且签名密钥与 sender 匹配，任一不符 MUST 拒绝；sender 未注册、已禁用或注册表不可读取 MUST 拒绝。注册只证明可用性，不构成执行授权（OC-5）。并发与载体机制留给 plan，并与 OC-6/OC-7 一致。
- **FR-08**: 校验 MUST 覆盖资产与转账内容：资产/目标合约 MUST 在许可集合内；转账语义（收款方、金额）MUST 与内容一致；非许可合约调用或与声明不一致的 calldata MUST 拒绝。策略模型遵循章程 VIII（许可链、来源钱包、目标策略、金额上限、合约/函数白名单），可扩展字段留给 plan。
- **FR-09**: 校验 MUST 覆盖收款方：目标策略（允许/拒绝集合或等价规则）与地址形状（`0x` + 40 位十六进制；大小写等价规则沿仓库既有语义）不满足 MUST 拒绝。
- **FR-10**: 校验 MUST 覆盖金额：必须以整数最小单位表达（MUST NOT 使用浮点，章程 I）；零/负/小数/非整数/超 uint256 MUST 拒绝；策略金额上限 MUST 生效。
- **FR-11**: 校验 MUST 覆盖费用策略：gas 上限、费用上限/单价等 MUST 在策略范围内；超限 MUST 拒绝。费用替换类请求 MUST 额外满足恢复门禁（FR-17）。
- **FR-12**: 策略判定 MUST NOT 可被静默绕过（章程安全规则）；每次签名或拒绝 MUST 记录可审计信息（请求身份、内容身份、策略版本、结论、原因分类、时间）。策略清单的存储与更新入口留给 plan，更新 MUST 受控且可审计。
- **FR-13**: 签名请求身份 MUST 与完整交易内容在持久层强绑定（UNIQUE/等价约束，非应用内存检查）：同身份同内容幂等收敛；同身份不同内容 MUST 拒绝（冲突），MUST NOT 对第二份内容签名。（OC-4，2026-09-16 已裁决，全文见 Clarifications）请求身份由可信调用方预分配的 signing_request_id 界定，作用域为已认证调用方 + signing_request_id；010 MUST 在首次签名调用前持久化 attempt_id、signing_request_id 与完整内容，并关联 intent_id 与 008 绑定。009 MUST 持久绑定完整规范化内容（chain_id、sender、nonce、交易类型、to、value、data、gas limit 及所有适用费用/签名字段）及 intent/binding/attempt 引用。同 ID 同内容 MUST 复用原请求（在途或结果未知 MUST 从持久记录恢复，MUST NOT 以新身份重试）；同 ID 异内容 MUST 拒绝；签名结果 MUST 在成功返回前可靠持久化。一次尝试 = 一个请求身份；费用替换 MUST 使用新 attempt_id + signing_request_id，并隶属原 intent + 绑定。身份 MUST NOT 被视为授权凭据（OC-5/OC-6/OC-7 管辖）。009 MUST 现在定义并校验该输入契约，不要求 010 已实现；符合契约的测试调用方可用。
- **FR-14**: 重试、响应丢失、进程重启 MUST 收敛到同一持久结果：相同身份与内容的再次请求 MUST 返回原签名结果，MUST NOT 产生第二个可观察签名；并发重复 MUST 有且仅有一个有效结果（章程 II）。
- **FR-15**: 签名请求 MUST 使用显式状态机（至少：已接收 → 已校验 → 已签名 / 已拒绝 / 失败）；状态转换 MUST 在持久层守卫，非法转换 MUST 拒绝或记为错误；影响持久行为的转换 MUST 在事务边界内（章程 V/VI）。
- **FR-16**: 成功结果 MUST 至少返回签名与交易哈希（签名对象身份）；服务 MUST NOT 广播交易、MUST NOT 调用任何链上写接口；签名动作除密钥提供者与持久层读写外 MUST 无外部副作用。
- **FR-17**: 服务 MUST 继承 006 已批准暂停语义（006 FR-26 / contracts/downstream.md）：产生签名前 MUST 在一个读取序列内观察 (a) 该链无暂停行（`indexer_pause` / `log_pause` / `deposit_pause`；006 拥有，009 只读）与 (b) 无活跃恢复行（或仅已释放终态）；恢复活跃期间新签名与费用替换签名 MUST 一律拒绝并记录原因，MUST NOT 排队为"已批准"；恢复版本变化后基于旧版本的请求内容 MUST NOT 签名；009 MUST NOT 写入、清除或修改 006 暂停、恢复行与隔离规则。（OC-6，2026-09-16 已裁决，全文见 Clarifications）交付前门禁：授权过期或撤销后 MUST NOT 再交付已持久化签名；首次交付与同 ID 重试返回均 MUST 核验当前授权有效性与暂停门禁，任一失败 MUST 拒绝交付，此时仅允许经认证与权限校验、且不含原始签名交易或可重构广播材料的状态查询。幂等复用 MUST NOT 被解读为永久获取权（不类比 007 still-200）；拒绝交付 MUST 保留结果/绑定/审计历史，MUST NOT 静默换绑授权（身份规则沿 OC-4/OC-5），MUST 记录授权版本、暂停依据与原因；已交付签名不可收回（交付前竞争由 OC-7 定界，见 FR-23）。恢复暂停期间 MUST NOT 交付已持久化签名（含同 ID 重试），仅返回不含签名材料的状态与暂停原因；恢复后返回仍 MUST 通过当前授权与暂停门禁；多个独立暂停并存时，解除其一 MUST NOT 绕过其余。009 MUST 只读观察 008/006 暂停与对账状态、MUST NOT 解除或清除；暂停或对账中的绑定读结果 MUST NOT 产生签名；009 MUST 记录所见暂停依据与拒绝原因，释放证据标准与解除权限以 008 裁决为准，009 MUST NOT 替代决定；008 绑定事实与 009 签名材料在接口与场景中分别表达。恢复门禁与交付准入的具体接线及版本共存载体留给 plan；本 FR 只锁定继承与交付门禁行为。
- **FR-18**: 签名请求 MUST 携带上游（008）给定的 nonce；服务 MUST NOT 分配、递增、替换或改写 nonce；缺失 nonce 或 nonce 不满足请求契约 MUST 拒绝。（OC-3，2026-09-16 已裁决，全文见 Clarifications）nonce 持久绑定由 008 拥有；009 MUST 通过显式只读契约消费，MUST NOT 修改绑定记录，MUST NOT 复用 007 行。009 MUST 将 intent/chain/sender/nonce 与可信持久记录核对，MUST NOT 信任调用方声明的预留声明。读契约 MUST 区分：存在且匹配 / 不存在 / 冲突 / 暂停或对账中 / 读取失败或不确定；除“存在且匹配”外任何结果 MUST NOT 产生签名。绑定不构成授权（OC-5）；只读消费不解决 OC-6/OC-7。载体与集成机制留给 plan；009 MUST 保持密钥隔离边界。
- **FR-19**: Guard：007 的 Accepted 仅表示"请求已被接收并持久化"，MUST NOT 被解读为存在付款意图、执行授权或已获准签名；签名 MUST NOT 由 007 的接收状态自动触发或推定（007 spec FR-08/FR-19、contracts/api.md §3）。付款意图创建与身份（OC-1，2026-09-16 已裁决，全文见 Clarifications）：付款意图由 011 在执行准入时创建并持久化，拥有独立、稳定的 intent_id 并与 007 request_id 持久关联；007 的 Accepted MUST NOT 被视为意图；一个 request_id 至多映射一个意图；意图 MUST 在 008 预留之前持久化；009 的签名请求 MUST 可追溯到意图（请求/尝试身份见 FR-13）。意图存在 MUST NOT 被解读为持续的执行许可（执行授权见 FR-05/OC-5）。
- **FR-20**: 密钥 MUST 通过 `KeyProvider`（或等价）抽象隔离：签名实现细节（本地开发密钥 / KMS / HSM）MUST 可替换而不改变业务逻辑；业务代码 MUST NOT 直接导入密钥材料（章程 VIII）。签名实现 MUST 使用既成密码学库，MUST NOT 自造密码学。
- **FR-21**: 测试密钥与部署密钥 MUST 配置隔离：本地开发 MUST 仅使用一次性测试密钥；部署密钥 MUST 只存在于签名边界/KMS/HSM；部署模式 MUST NOT 静默加载或回退到测试密钥；配置混用 MUST 拒绝启动或拒绝签名。
- **FR-22**: 密钥材料 MUST NOT 写入源码控制、日志、错误响应、审计记录或指标；原始已签名交易字节 MUST NOT 写入日志（章程安全规则、原则 XII）。审计与日志字段 MUST 足以定位（请求身份、阶段、错误分类、重试次数、策略版本），但 MUST NOT 含敏感材料。
- **FR-23**: 失败路径 MUST 为一等行为且有界：密钥提供者不可用/超时、持久层不可用、进程重启、重复投递、恢复版本变化、策略拒绝——每类 MUST 定义可重试/不可重试、重试上限、超时与退避；MUST NOT 无限重试；不可重试失败 MUST NOT 被伪装为成功；已持久化的签名结果 MUST NOT 因失败路径丢失（章程 IX）。（OC-7，2026-09-16 已裁决，全文见 Clarifications）暂停/撤销约束 MUST 覆盖签名准入、结果持久化与最终交付；前次检查成功 MUST NOT 构成持续许可。暂停/撤销先于交付准入生效时 MUST NOT 交付（即使签名结果已生成并持久化），MUST 保留请求/绑定/结果与拒绝依据，MUST NOT 重签、MUST NOT 释放 nonce；交付准入与暂停/撤销之间 MUST 建立明确且可验证的先后顺序（机制留给 plan）。交付准入先行且已不可取消时记为在途已准交付，MUST NOT 声称可收回；受阻未交付 MUST 记录恢复条件；无法确定是否已交付或已产生副作用时 MUST 进入结果未知与对账语义；后续广播/重播 MUST 通过各自门禁。验收 MUST 覆盖门禁检查后、签名生成中、落盘后、交付竞争、响应丢失各时点。
- **FR-24**: 可观测性 MUST 覆盖：签名请求量、拒绝（按原因分类）、签名失败（按类别）、密钥提供者健康与延迟、持久层提交结果、恢复门禁拒绝计数；关键操作 MUST 结构化日志（章程 XII）。指标载体留给 plan。
- **FR-25**: 本阶段 MUST NOT 引入 Redis/Kafka/K8s 等新基础设施作为签名正确性依赖；持久绑定与幂等 MUST 以 PostgreSQL 为真相源（章程 III/XIII）。金额与费用 MUST NOT 使用浮点（章程 I）。
- **FR-26**: 本规范 MUST NOT 锁定表结构、锁机制、密码学库、传输协议、模块接口与字段命名（留给 plan）；影响正确性的未决问题 MUST 显式标注（见 Assumptions 契约项表），MUST NOT 把未裁决假设写成已确定事实（章程 XIV）。

### Key Entities *(include if feature involves data)*

- **签名请求（Sign Request）**：调用方提交的结构化交易签名请求。属性：请求身份（可信调用方预分配的 signing_request_id；作用域：已认证调用方 + signing_request_id，来源见 FR-13/OC-4）、完整交易内容、状态（已接收/已校验/已签名/已拒绝/失败）、调用方归属、时间；身份与内容持久绑定（FR-13）。
- **交易内容（Transaction Content）**：被签名的对象整体（chain_id、sender、nonce、收款方、金额/转账内容、费用参数等）；任何字段变化即不同内容（FR-13）。
- **签名结果（Signing Result）**：签名、交易哈希及其持久化事实与时间；仅结果事实，永不广播（FR-16）。
- **签名策略（Signing Policy）**：许可链、许可 sender、许可资产/合约与函数、收款方策略、金额上限、费用范围；带版本并审计（FR-06–FR-12）。
- **调用方身份（Caller Identity）**：服务端依据凭据判定的签名请求发起者（FR-04/FR-05）；凭据轮换不改归属。
- **密钥边界（Key Material / KeyProvider）**：仅在签名边界内可访问的密钥与抽象提供者；测试密钥与部署密钥隔离（FR-20/FR-21）。
- **恢复门禁状态（Recovery Gate State，源自 006）**：只读消费的链级暂停行、恢复行状态与恢复版本（FR-17）。
- **审计记录（Audit Record）**：签名/拒绝决策、策略版本、内容身份、时间（FR-12/FR-22）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-01**: 100% 的合规结构化请求产生可独立验证的签名与哈希；100% 的任意摘要/裸哈希/消息请求被拒绝且签名产出数为 0；100% 的缺失必需内容请求被拒绝（US1）。
- **SC-02**: 100% 的未认证/无权限请求被拒绝且签名数为 0；自报身份不一致场景 100% 不以自报字段建立身份（US2）。
- **SC-03**: 同身份同内容重试（含并发、响应丢失、重启后；N≥2，plan 定义 N）100% 返回同一持久签名结果，可观察签名恰好 1 个；同身份异内容 100% 冲突且第二签名产出数为 0（US3）。
- **SC-04**: 校验矩阵（链/sender/资产/转账内容/收款方/金额/费用）100% 在签名前拒绝，签名数为 0（US4）。
- **SC-05**: 测试/部署密钥混用 100% 被拒绝或拒绝启动；日志、错误、响应与仓库中密钥材料与原始已签名交易出现次数为 0（US5）。
- **SC-06**: 恢复活跃期间新签名与费用替换签名 100% 被拒绝（0 次签名）；恢复版本变化后旧视图内容 100% 不被签名；签名服务广播/链上写副作用出现次数为 0（US6）。
- **SC-07**: 签名请求状态与决策 100% 可审计（身份、内容身份、策略版本、结论、时间）；错误输出中凭据/密钥出现次数为 0。
- **SC-08**: 失败路径注入（密钥不可用、存储不可用、签名前后崩溃、重复投递）下，100% 无部分成功、无结果丢失、重试收敛；无限重试出现次数为 0。
