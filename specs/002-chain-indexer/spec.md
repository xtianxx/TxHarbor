## Background, Goals & Scope

### Background

TxHarbor 是 EVM ERC-20 充值检测与提款执行后端。第一版为单部署、单链，不维护用户余额账本。

本规范是 TxHarbor 的第 002 号功能规范，名称固定为 `002-chain-indexer`（不得改写为 001）。仓库中已存在 `specs/001-project-foundation`（工程底座：环境变量配置、数据库迁移底座、存活/就绪探针、基础可观测性、优雅退出）与项目章程（Constitution 1.1.0）。本规范不重复 001 的验收结论，只引用实际存在的工程能力；凡 002 需要但 001 未交付的能力，一律列为前置依赖或本规范的新需求，不得声称其已实现。

实际工程能力核查（以仓库现状为准，2026-09-12）：

- 已存在：Go 模块（go-ethereum ethclient 封装，仅实现 `ChainID` / `CheckChainID` 与错误分类 transport/timeout/chain-mismatch/invalid-response）；pgx 连接池（显式池参数、有界 Ping）；goose 基线迁移（刻意零对象，无业务表）；环境变量配置（数据库连接串、RPC 地址、期望 chain_id、HTTP 地址、启动/探测/退出超时、迁移锁超时）；存活探针与就绪探针分离；`/metrics`（仅进程指标、就绪状态、DB/RPC 探测计数）；日志凭据脱敏；优雅退出；Docker Compose 一键启动 PostgreSQL 与 Anvil（Anvil chain-id 31337）。
- 不存在（不得假设已实现）：按高度获取区块头的能力；区块头与 checkpoint 的持久化结构；起始高度配置；扫描循环、重试退避、追头等待；实例竞争协调；扫描进度可观测信息；上述任一能力的验收测试。

### Goals

- 连续按高度同步单链区块头，并持久化可恢复的扫描进度。
- 在重复执行、多实例竞争、进程重启、RPC/数据库故障下，不漏扫、不错误推进。
- 发现疑似链分叉或历史不一致时停止推进并给出可诊断状态，不自动改写历史。

### Non-Goals / Out of Scope

- 事件日志扫描、ERC-20 Transfer 解析。
- 充值识别、确认数跟踪。
- 自动重组回滚与重放（属于后续阶段）。
- 提款逻辑。
- 多链调度。
- 引入 Redis、Kafka、Kubernetes 或其他额外基础设施。

## Dependencies & Assumptions

### Prerequisite dependencies (must hold before or with this feature)

- **D1 — 运行底座（已存在，按 001 验收结论复用）**：环境变量配置加载与校验、数据库连接池、链标识校验能力、存活/就绪探针分离、日志脱敏、优雅退出框架、本地 PostgreSQL + Anvil 一键启动。本规范不重新规定这些行为，只在其上构建。
- **D2 — 持久化结构（缺失，本规范提出需求、plan 阶段设计）**：保存区块头与 checkpoint 的 durable 存储尚未存在。表结构、索引、锁机制、模块接口一律不在本规范中锁定，留给 plan 阶段。
- **D3 — 按高度读取区块头的能力（缺失，本规范提出需求）**：现有 RPC 封装仅支持 chain_id 查询，不支持按高度取块。取块方式、超时、错误分类留给 plan 阶段，但行为需求（校验、重试、不跳块）由本规范锁定。
- **D4 — 起始高度与链配置载体（缺失，本规范提出需求）**：现有配置无起始高度项。配置项命名、格式、默认值留给 plan 阶段。
- **D5 — 可观测载体扩展（缺失，本规范提需求、plan 定载体）**：现有探针与指标不足以表达扫描高度/checkpoint/暂停原因。是否扩展 `/metrics`、新增状态查询或日志字段，留给 plan 阶段。

### Explicit assumptions

- 单部署单链：同一时间只跟踪一条配置链；多实例指同一链的多个相同部署副本竞争，而非多链调度。
- 起始高度是扫描下界：不要求补扫起始高度之前的历史；起始高度本身必须被正常扫描（除非它高于链头，见验收场景）。
- 创世区块无父块可比，其父子哈希校验单独处理。
- 本地验证以 Anvil 为权威链数据源；不依赖公网测试网。
- 重试退避的具体参数（初值、上限、次数、抖动）、追头轮询间隔、RPC 单次超时由 plan 阶段确定并给出理由；本规范只锁定行为语义（可重试错误必须退避重试、不可跳块）。

### Open questions (tracked, not silently assumed; resolved in plan, not in spec)

- **OQ1（正确性相关）**：实例竞争协调与 checkpoint 原子提交的具体机制（行锁 / 乐观并发 / 唯一约束 / 通知协同）——留给 plan，但必须同时满足 FR-07、FR-08、FR-14。
- **OQ2（正确性相关）**："提交结果不确定"（commit 未知态）的恢复核对步骤细节——行为由本规范锁定（从数据库核对 + 幂等继续），具体实现由 plan 给出。
- **OQ3（可观测性）**：扫描高度/checkpoint/暂停原因的暴露载体（指标 / 状态端点 / 日志字段组合）——留给 plan，但 SC 与 FR-15 的可验证性必须保留。

## Clarifications

### Session 2026-09-12

- Q: 起始高度高于当前链头时，系统是否应等待链长到达起始高度，且等待全程不创建任何 checkpoint？ → A: 是。等待期间不写入区块记录、不创建 checkpoint；允许必要的数据库协调及运行状态记录，但这些记录不得表示扫描进度。起始高度 S 出现后，按首块规则在同一事务内保存区块 S 并创建对应 checkpoint.
- Q: 恢复扫描前核对 checkpoint 时，链上暂时查不到该高度区块、RPC 调用报错、明确返回不同哈希这三种情况是否应分别处理为等待、可退避重试、暂停？ → A: 是。空结果时等待并退避重试核对；可重试的 RPC 错误退避重试；明确返回不同哈希时暂停并记录诊断。三种情况均不得推进 checkpoint，只有核对成功后才能继续扫描。不可重试的配置或认证错误应停止扫描并报告原因，不能无限重试。
- Q: 因哈希不一致进入暂停后，暂停状态是否应持久化，使进程重启后仍然阻止推进，且恢复扫描必须以人工介入或后续重组规范为前提？ → A: 是。暂停状态及原因必须持久化，重启后仍禁止推进 checkpoint，本阶段不自动解除。人工处理或后续重组恢复流程解除暂停后，继续扫描前必须重新核验 checkpoint 与链上区块一致；核验失败不得推进。人工处理不得仅清除暂停标记就强制继续，本阶段无需新增管理接口。
- Q: canonical 是否应明确定义为本阶段索引认可的链上记录，而不代表已确认或终局不可逆？ → A: 是。canonical 仅表示索引当前认可的链上记录，不代表已达到确认深度或终局不可逆。发生哈希不一致并暂停时，已有 canonical 标记也不保证仍与实时链一致；本阶段不自动改写，后续重组恢复阶段负责处理。确认数跟踪和终局判断不属于本阶段。
- Q: 无 checkpoint 时，起始高度 S 的首个区块是否免父哈希校验、直接作为扫描边界保存，而后续每个区块都以已保存的前一高度区块为基准校验父子衔接？ → A: 是。无 checkpoint 时，将起始高度 S 的区块作为扫描边界，不要求读取或保存 S-1，也不验证与 S-1 的父子衔接；仍须校验返回高度为 S、必要字段合法，并保存 parent_hash。创世区块按无父块规则处理。后续区块必须满足高度为已持久化 checkpoint 高度加一，且 parent_hash 等于 checkpoint 对应已保存区块的 hash。重启后先完成 checkpoint 核验，再按相同规则继续。首块保存与 checkpoint 创建必须在同一事务内完成。

## User Scenarios & Testing

### User Story 1 — 连续同步区块头并可恢复（Priority: P1）

操作员配置链与起始高度后启动，系统从起始高度（或已有 checkpoint 的下一块）按序同步区块头；进程重启后从数据库恢复，不漏块、不重复推进。

**Why this priority**: 本功能的核心价值；没有它，后续充值/确认/重组都无从谈起。

**Independent Test**: 在 Anvil 上预先生块，从空进度启动，观察到高度单调推进；杀进程重启后从 checkpoint 下一块继续，无跳块。

**Acceptance Scenarios**:

1. **Given** 无 checkpoint 且链头高度为 H（H ≥ 起始高度 S），**When** 启动扫描，**Then** 第一个持久化的区块为高度 S（不读取 S-1、不验证与 S-1 的衔接，但校验返回高度为 S 且必要字段合法），且高度按 S、S+1、… 顺序推进，后续每块高度为前块高度加一且 parent_hash 与已保存前块 hash 衔接。
2. **Given** 已存在指向高度 N（哈希为 Hs）的 checkpoint，**When** 启动或继续扫描，**Then** 下一个处理的高度为 N+1，不重复推进 N，不跳过 N+1。
3. **Given** 扫描已推进到高度 N，**When** 进程被终止后重启，**Then** 恢复后从 N+1 继续，且 N 及之前已提交的区块仍然存在、无缺口。
4. **Given** 配置中的起始高度被修改为 S'（S' ≠ S），且已有 checkpoint，**When** 启动扫描，**Then** 不得静默跳过或重置已有进度，必须拒绝、报错或要求显式的人工处理（不得自动丢弃进度）。

---

### User Story 2 — 故障下不漏扫不误推（Priority: P1）

RPC 超时/连接失败/限流/空结果/非法响应，或数据库写入失败时，系统停留在当前高度重试（有退避），不跳过、不推进 checkpoint；追上链头后安静等待新块。

**Why this priority**: 与主流程同等重要；资金类索引器的正确性全部体现在故障行为上。

**Independent Test**: 分别注入 RPC 中断、DB 写入失败、链头静止，观察高度停滞 + checkpoint 不动 + 错误可观测；故障恢复后自动继续。

**Acceptance Scenarios**:

1. **Given** 当前高度为 N 且 RPC 持续失败，**When** 经过多次重试，**Then** 高度仍为 N，checkpoint 仍指向 N-1（或空），且错误原因可观测。
2. **Given** 当前高度为 N 且数据库写入失败，**When** 重试仍失败，**Then** 高度仍为 N，checkpoint 不推进，不留下"checkpoint 已走但区块缺失"的状态。
3. **Given** 已追上链头（下一高度尚无块），**When** 等待新块，**Then** 不报错、不标记故障，安静等待；新块出现后继续推进。
4. **Given** 起始高度 S 高于当前链头 H，**When** 启动扫描，**Then** 不写入任何区块记录、不创建 checkpoint（checkpoint 保持为空），进入等待链长到达 S 的状态，不视为故障；S 出现后按首块规则在同一事务内保存区块 S 并创建对应 checkpoint。

---

### User Story 3 — 竞争与重复安全（Priority: P1）

同一区块被重复扫描时幂等；两个实例竞争同一条链时，通过数据库协调与一致性约束防止冲突，不只依赖进程内存锁。

**Why this priority**: 单部署多副本是常态；没有数据库层保证，重复与竞争必然产生分叉进度。

**Independent Test**: 同一区块投递两次；双实例同时指向同一链头推进，结束后数据库中同一链同一高度最多一个有效记录，checkpoint 始终指向已保存区块。

**Acceptance Scenarios**:

1. **Given** 高度 N 已保存，**When** 再次扫描高度 N（相同哈希），**Then** 不创建重复有效记录，checkpoint 保持正确，结果收敛到同一 durable 状态。
2. **Given** 两个实例同时尝试推进同一链的高度 N，**When** 并发提交，**Then** 至多一个成功建立有效推进，另一个安全失败并重试或等待，不产生两个有效记录，不推进到错误状态。
3. **Given** 事务提交结果不确定（提交是否成功未知），**When** 恢复后继续，**Then** 先从数据库核对实际状态，再依靠幂等机制继续，不跳块、不重复记账式推进。

---

### User Story 4 — 分叉可疑时暂停而非自动处理（Priority: P2）

恢复前核对 checkpoint 哈希；发现已保存区块哈希或父子哈希不一致时，停止该链推进并记录可诊断的暂停状态；不自动覆盖历史、回滚或选新分叉。

**Why this priority**: 自动选叉是资金风险源；本阶段正确做法是停下来等人看，恢复逻辑留给后续阶段。

**Independent Test**: 构造父哈希断裂、checkpoint 哈希变化两种情形，观察系统停机并输出原因；确认历史数据未被改写。

**Acceptance Scenarios**:

1. **Given** checkpoint 指向 (N, Hs)，**When** 恢复扫描且链上高度 N 的哈希仍为 Hs，**Then** 允许从 N+1 继续。
2. **Given** checkpoint 指向 (N, Hs)，**When** 恢复扫描且链上暂时查不到高度 N 的区块或 RPC 报可重试错误，**Then** 等待并退避重试核对，不推进进度；只有链上返回哈希与 Hs 一致后才允许从 N+1 继续；链上明确返回不同哈希时进入暂停状态（见场景 3）。
3. **Given** 相邻区块父子哈希不衔接，或已保存区块与链上同一高度哈希不同，**When** 检测到，**Then** 停止该链进度推进，持久化暂停状态与诊断信息（链、高度、期望/实际哈希、父子关系），历史记录不被覆盖、不回滚。
4. **Given** 系统已因哈希不一致进入暂停，**When** 进程重启后恢复，**Then** 暂停仍然有效、checkpoint 不推进；人工处理或后续重组恢复流程解除暂停后，继续扫描前必须重新核验 checkpoint 与链上一致，核验失败不得推进。
4. **Given** 链上返回的 chain_id 与配置不一致，**When** 扫描前校验，**Then** 拒绝扫描并报告期望与实际值，不写入任何区块。

---

### User Story 5 — 安全退出与可观察（Priority: P2）

操作员可随时终止；未提交事务不留部分进度；扫描高度、checkpoint、运行/暂停状态与错误原因可观察；日志不泄露 RPC 凭据。

**Why this priority**: 没有可观测的暂停与退出，运维无法区分"追上链头"与"卡住"，也无法安全运维。

**Independent Test**: 在提交中途发终止信号后重启核对；检查状态输出与日志脱敏。

**Acceptance Scenarios**:

1. **Given** 正在处理高度 N（事务未提交），**When** 收到终止信号，**Then** 退出前不留下"checkpoint 已到 N 但区块未保存"的部分进度。
2. **Given** 系统处于运行/等待/重试/暂停任一状态，**When** 操作员查询状态，**Then** 可看到当前扫描高度、checkpoint（高度+哈希）、状态与最近错误原因。
3. **Given** 任意日志输出（含错误详情与 RPC 失败记录），**When** 检查，**Then** 不出现 RPC 凭据明文或可直接还原凭据的等价输出。

### Edge Cases

- 起始高度恰为创世区块：按创世规则处理（无父哈希可比），不得当作父子断裂而暂停。
- 起始高度高于链头：零区块写入、checkpoint 保持为空，等待链长到达起始高度；等待期间的数据库协调及运行状态记录不得表示扫描进度。
- RPC 返回空结果（高度尚无块） vs 非法响应（格式错/高度错）：前者等待重试，后者按失败处理，均不推进。
- RPC 限流：按可重试错误退避，不计为永久失败，不跳块。
- 数据库瞬断后恢复：stuck 在当前高度重试，checkpoint 不动。
- 提交未知态后重启：以数据库为准重建真相，幂等继续。
- 双实例同时启动且均无 checkpoint：至多一个赢得首块写入，另一个收敛。
- checkpoint 哈希在停机期间变化：暂停，人工介入，后续阶段才允许自动恢复。
- chain_id 在运行中发生变化（节点被替换）：拒绝继续并报告。
- 终止信号到达于提交临界点：以数据库实际提交结果为准，不假设成功或失败。
- 日志脱敏边界：RPC URL 中的口令/令牌字段在错误、调试、状态输出中均脱敏，但保留定位所需非敏感上下文（主机、链、高度、哈希、重试次数）。

## Requirements

### Functional Requirements

- **FR-01**：系统 MUST 在扫描开始前校验 RPC 返回的 chain_id 与配置期望一致；不一致时 MUST 拒绝扫描且 MUST NOT 写入任何区块或 checkpoint，并报告期望值与实际值。
- **FR-02**：首次运行（无 checkpoint）时系统 MUST 从配置起始高度开始扫描；已有 checkpoint 时 MUST 从最后成功持久化高度的下一块继续。
- **FR-03**：修改配置起始高度 MUST NOT 静默跳过或重置已有进度；存在 checkpoint 时，新的起始高度 MUST 触发明确拒绝/报错或要求显式人工处理，不得自动丢弃或覆盖进度。
- **FR-04**：系统 MUST 保存每个区块的 chain_id、number、hash、parent_hash、canonical 标记；区块身份 MUST NOT 仅由高度表示；同一链同一高度 MUST 最多存在一个 canonical 区块（由持久层约束保证，而非仅应用层判断）。canonical 仅表示本阶段索引当前认可的链上记录，MUST NOT 被解释为已达到确认深度或终局不可逆；发生哈希不一致并暂停时，已有 canonical 标记 MUST NOT 被视为仍与实时链一致；本阶段 MUST NOT 自动改写 canonical 历史，后续重组恢复阶段负责处理；确认数跟踪和终局判断明确不属于本阶段。
- **FR-05**：系统 MUST 按高度顺序扫描；无 checkpoint 时，起始高度 S 的区块即扫描边界：MUST NOT 要求读取或保存 S-1，MUST NOT 验证与 S-1 的父子衔接，但 MUST 校验返回高度为 S、必要字段合法，并保存其 parent_hash；创世区块 MUST 按无父块规则单独处理，不得误判为断裂。存在 checkpoint 时，后续区块 MUST 满足高度等于 checkpoint 高度加一，且 parent_hash 等于 checkpoint 对应已保存区块的 hash；重启后 MUST 先完成 checkpoint 核验（见 FR-11），再按相同规则继续。起始高度为扫描边界，MUST NOT 要求补扫此前历史。
- **FR-06**：区块持久化与 checkpoint 推进 MUST 在同一数据库事务中完成；首块保存与首个 checkpoint 创建 MUST 在同一事务内完成；checkpoint MUST 同时记录高度和哈希，且 MUST 始终指向已成功保存的区块（不存在"checkpoint 已进但区块缺失"）。
- **FR-07**：重复扫描相同区块（同链同高度同哈希）MUST 幂等收敛到同一 durable 状态，MUST NOT 创建重复有效记录。
- **FR-08**：多实例竞争同一条链时，系统 MUST 通过数据库协调及一致性约束防止冲突，MUST NOT 仅依赖进程内存锁；并发推进同一高度时 MUST 至多一个建立有效推进。
- **FR-09**：RPC 超时、连接失败、限流、空结果、非法响应及数据库失败时，系统 MUST NOT 跳过当前高度；可重试错误 MUST 采用有退避的重试（参数由 plan 确定）；不可重试的配置或认证错误 MUST 停止扫描并报告原因，MUST NOT 无限重试；其他持续失败时 MUST 停留并报告，不得推进。
- **FR-10**：追上链头（下一高度暂无块）时系统 MUST 等待新块，MUST NOT 将其视为故障；起始高度高于链头时系统 MUST 等待链长到达起始高度，等待期间 MUST NOT 写入任何区块记录、MUST NOT 创建 checkpoint（checkpoint 保持为空）；等待期间允许必要的数据库协调及运行状态记录，但此类记录 MUST NOT 被解释为扫描进度；起始高度出现后 MUST 按首块规则在同一事务内保存该区块并创建对应 checkpoint。
- **FR-11**：恢复扫描前系统 MUST 核对 checkpoint 对应的链上区块哈希，三种情形语义分离且任一情形下 MUST NOT 推进 checkpoint：空结果（暂时查不到该高度区块）时 MUST 等待并退避重试核对；可重试的 RPC 错误 MUST 退避重试；链上明确返回不同哈希时 MUST 进入暂停（见 FR-12）；只有核对成功（链上哈希与 checkpoint 一致）后才能继续扫描。不可重试的配置或认证错误 MUST 停止扫描并报告原因，MUST NOT 无限重试。
- **FR-12**：发现已保存区块哈希与链上不一致、或相邻父子哈希不一致时，系统 MUST 停止该链进度推进，并将暂停状态及原因持久化记录（含链、高度、期望/实际哈希、父子关系）；暂停在进程重启后 MUST 仍然禁止推进 checkpoint，本阶段 MUST NOT 自动解除；人工处理或后续重组恢复流程解除暂停后，继续扫描前 MUST 重新核验 checkpoint 与链上区块一致，核验失败 MUST NOT 推进；人工处理 MUST NOT 仅清除暂停标记就强制继续；本阶段 MUST NOT 为解除暂停新增管理接口。MUST NOT 自动覆盖历史、回滚或选择新分叉；自动重组恢复明确属于后续阶段。
- **FR-13**：系统 MUST 支持安全退出；事务未提交时 MUST NOT 留下部分进度；提交结果不确定时，恢复后 MUST 从数据库核对实际状态并依靠幂等机制继续。
- **FR-14**：并发与恢复正确性 MUST 由持久层保证（唯一性、原子性、协调），应用层内存状态 MUST NOT 作为唯一的正确性依据；重启后 MUST 仅以数据库状态重建进度。
- **FR-15**：系统 MUST 提供扫描高度、checkpoint（高度+哈希）、运行或暂停状态及错误原因的可观察信息；日志 MUST NOT 暴露 RPC 凭据等敏感内容（脱敏后仍保留定位所需的非敏感上下文）。
- **FR-16**：系统 MUST NOT 在本阶段实现事件日志扫描、ERC-20 Transfer 解析、充值识别、确认数跟踪、自动重组回滚与重放、提款逻辑、多链调度；MUST NOT 引入 Redis、Kafka、Kubernetes。
- **FR-17**：本规范 MUST NOT 锁定表结构、锁机制、模块接口；实现选择留给 plan 阶段；影响正确性的未决问题 MUST 显式标注（见 Open questions），不得隐藏假设。

### Key Entities & Consistency Invariants

- **链配置 (Chain Config)**：要跟踪的单链标识（期望 chain_id）与扫描下界（起始高度）。起始高度一经存在 checkpoint 即冻结语义，修改不得自动生效。
- **区块头 (Block Header)**：chain_id + number + hash + parent_hash + canonical。身份由（chain_id, hash）或（chain_id, number, hash）共同确定，不只由高度确定。canonical 仅表示索引当前认可的链上记录，不代表确认深度或终局性。
- **扫描进度 / Checkpoint**：始终指向已成功保存区块的（高度，哈希）二元组；空进度表示尚未持久化任何区块。推进与区块保存原子绑定。
- **暂停状态 (Paused State)**：链因哈希不一致进入的持久化停止推进状态，携带诊断信息（链、高度、期望/实际哈希、父子关系、原因分类）；重启后仍然有效并禁止推进 checkpoint；本阶段只能由人工处理或后续阶段的重组恢复规范解除，且解除后继续扫描前必须重新核验 checkpoint 与链上一致；不得仅清除暂停标记就强制继续；本阶段不为解除暂停新增管理接口。
- **一致性不变量（必须始终成立）**：
  - I1：同一链同一高度最多一个 canonical 区块。
  - I2：checkpoint 非空时，其（高度，哈希）必对应一个已保存区块。
  - I3：已保存的非创世区块序列父子哈希连续（除暂停点之后不再推进）。
  - I4：checkpoint 高度单调非递减，且永不指向未保存区块。
  - I5：chain_id 不一致时零写入。
  - I6：任何高度都不可被跳过（失败停留、成功才进）。

## Success Criteria

### Measurable Outcomes

- **SC-01**：从空进度启动，在链头持续产块条件下，100% 从起始高度按序推进，无跳块；停止并重启后 100% 从 checkpoint 下一块继续，无重复有效记录。
- **SC-02**：重复投递同一区块 2 次以上时，有效记录数恒为 1，checkpoint 正确，成功率 100%。
- **SC-03**：RPC 中断（含超时/连接失败/限流）期间 checkpoint 推进次数为 0；故障恢复后 100% 自动从断点继续，无人工干预、无跳块。
- **SC-04**：数据库写入失败期间 checkpoint 推进次数为 0，且无"checkpoint 已进但区块缺失"状态；恢复后 100% 继续。
- **SC-05**：双实例并发推进同一高度时，同一链同一高度的 canonical 有效记录数恒为 1；无冲突丢失、无双推进，成功率 100%（多次重复运行）。
- **SC-06**：父哈希断裂或 checkpoint 哈希变化场景下，100% 停止推进并给出含链、高度、期望/实际哈希的诊断；历史记录零改写、零回滚。
- **SC-07**：chain_id 不一致场景下写入区块数为 0 且拒绝扫描，检出率 100%。
- **SC-08**：追上链头或起始高度高于链头时，零误报故障；新块出现后 100% 自动继续（等待时长界限由 plan 给出可验证阈值）。
- **SC-09**：提交结果不确定后重启，100% 以数据库核对为准继续，不跳块、不双记。
- **SC-10**：安全退出场景下部分进度残留数为 0；全部验收运行的日志归档中凭据明文出现次数为 0；状态查询 100% 可给出扫描高度、checkpoint、运行/暂停与错误原因。

## Assumptions (supplement)

- 重试与轮询参数不在本规范中固定；plan 必须给出初值、上限、次数、抖动与等待间隔，并说明其与"不漏扫、不误推"的对应关系。
- 可观测载体不在本规范中固定；plan 必须说明如何验证 SC-10 的状态查询与日志要求。
- 本次交付仅为需求规范及质量检查；不进入 plan、tasks 或代码实现。

## Acceptance Matrix (must all be covered by plan/tests)

1. 首次扫描（空进度从起始高度按序推进）。
2. 起始高度高于链头（零写入等待，非故障）。
3. 追上链头（等待新块，非故障，复块后继续）。
4. 重复扫描（幂等，单有效记录）。
5. 重启恢复（从 checkpoint 下一块继续）。
6. RPC 中断后恢复（停留当前高度，恢复后继续）。
7. 数据库写入失败（checkpoint 不推进，无部分进度）。
8. 提交结果不确定（恢复后以数据库为准，幂等继续）。
9. 两个实例竞争（单有效推进，无冲突）。
10. 父哈希不一致（停止推进 + 可诊断暂停，不自动处理）。
11. 停机期间 checkpoint 对应区块变化（未经核验不推进；确认变化则暂停）。
12. chain_id 错误（拒绝扫描，零写入，可诊断）。
13. 安全退出（未提交无残留；临界终止以数据库为准）。
