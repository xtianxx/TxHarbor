## Clarifications

### Session 2026-09-28

- Q: FR-036 的 RPO/RTO、备份频率与保留期、可接受数据损失范围是否在本阶段锁定生产数值？ → A: 选 A。本阶段交付可配置恢复目标、明确测量口径、实际演练及约束检查；生产 RPO/RTO、备份频率和保留期数值留部署前裁决，不编造。补充边界：(1) 分开记录数据库恢复时间、核验时间、各能力安全复服时间，不以数据库可连接宣称 RTO 达标；(2) 区分安全门禁与时间目标：证据缺失、恢复点不满足批准要求等阻止受影响能力复服，RTO 超时记录不达标、告警并升级，但不单独成为永久禁止后续安全复服的条件；(3) 未配置必需约束时不得宣称符合生产恢复目标，本地演练参数标注用途；(4) 备份频率≠已证明 RPO，接受恢复点滞后≠批准丢弃已接受请求/付款意图/nonce/签名广播/幂等证据；(5) 本回答不批准任何资金数据损失额度，不授权绕过既有资金门禁。
- Q: FR-023 分级复服的批准角色/权限与审批要求如何裁决（是否需要第二人复核或更高审批）？ → A: 选 A，按边界落规格：(1) 执行恢复、读取核验、批准复服独立权限，不要求三人互斥，恢复执行者可读授权范围内核验结果但不得批准自己执行的恢复实例；(2) 新提款创建、既有提款恢复、向真实下游投递及可产生真实下游业务效果的消费恢复，须两名不同已授权人员共同批准，两人均不得是该恢复实例执行者，不得同一人双账号充数；(3) 其余能力可由一名非执行者授权人员批准+审计，且只能开放所列能力，不得间接启动签名/广播/付款/真实下游副作用，能力依赖须明确；(4) 每次批准绑定恢复实例、能力、范围、证据版本，证据变化或门禁失效后旧批准失效须重核重批；(5) 放行时仍校验全部硬门禁，双人批准不得覆盖缺证/未隔离/未知付款结果等；(6) 仅适用于 015 灾备后复服，不改变正常运行及 014 已批权限，不新增紧急绕过/管理员强制复服入口。
- Q: FR-019 证据无法补齐时的复服边界与业务处置如何裁决？ → A: 选 A（Q3 纠正后确认）：受影响能力保持暂停，可证明独立且证据充分的能力按已裁决复服审批规则放行。补充边界：(1) 暂停范围含缺口直接关联及依赖/可能放大副作用的能力，依赖无法证明时保守纳入暂停，不仅凭不同模块判独立；(2) 独立放行须记录范围、依赖核验、有效证据与批准结果，不得间接启动被暂停的付款/签名/广播/真实下游副作用；(3) 缺口无法补齐时保留 unknown/pending、证据包、责任归属与升级记录，允许有界只读复核，超时/重试耗尽/人工知悉≠缺口闭合或获准复服；(4) 后续证据变化推翻独立性或安全前提时相关批准失效，停止后续执行，在途按既有安全门禁处理，未知结果不视为未执行；(5) 本阶段不交付风险接受后强制复服、损失核销、人工补偿付款或自动补造意图，此类政策另行业务裁决，双人审批不能替代缺失证据。

## User Scenarios & Testing *(mandatory)*

### 最终验收问题（本规格必须正面回答）

> 当 PostgreSQL 被恢复到较早时间点，而链上事实、签名/广播记录及下游状态已经推进时，系统能否识别证据缺口、隔离旧执行者、阻止重复付款或错误事件效果，并且只在明确条件满足后才恢复服务？

**正面回答：能——这是本规格的验收承诺，前提是下列 MUST 全部实现并经演练证明。**

- **识别证据缺口**：US3 / FR-014–FR-020 要求恢复后逐项核验，把无法证明的部分保持为「未知」并产出人工处置证据包，阻塞相应复服项；缺失记录不构成「可重执行」许可，不得假设对账能重建丢失的付款意图（FR-016/FR-017）；缺口无法补齐时保留 unknown/pending 与升级记录，可证明独立且证据充分的能力按已裁决审批规则放行（FR-019）。
- **隔离旧执行者**：US2 / FR-009–FR-013 要求恢复环境默认隔离，旧写入者/调度器/发布者/消费者的停止与隔离必须可验证，未证明隔离不得开启任何写入/发送/投递（继承 000018 禁混跑与检查清单模式）。
- **阻止重复付款或错误事件效果**：FR-016/FR-017/FR-025 明确「缺失≠可重执行」「核验不触发付款」「复服不绕过既有资金门禁」；FR-027–FR-029 覆盖事件重复、inbox/offset 回退、缺失幂等记录与外部效果边界。
- **只在明确条件后恢复服务**：US4 / FR-021–FR-024 要求分级复服、restored/verified/approved 三态区分，以及「权限+范围+理由+证据+审计」的显式放行；批准规则按 2026-09-28 裁决（执行/核验/批准权限独立、高影响能力双人批准、批准绑定证据版本，FR-023）；MUST NOT 存在「一个开关恢复全部」。

若任一前提无法满足（证据缺口无法闭合、旧实例无法证明隔离、备份不可用或不可信），系统 MUST 保持受影响能力关闭并报告人工处置所需证据；仅当依赖可证明独立、证据充分且按 FR-023 获批时，才可放行相应独立能力；旧实例无法证明隔离或备份不可用/不可信时，相关写入/发送/投递 MUST 保持关闭；MUST NOT 选择「先恢复再说」。

### User Story 1 - 备份可恢复性：备份成功不等于恢复成功 (Priority: P1)

操作员获得一个被标记为「成功」的备份，但在把它当作可用恢复点之前，系统必须已经证明它能被实际恢复并核验；损坏、不完整、未验证、不兼容或缺少恢复依赖的备份都必须被拒绝或明确标记，而不是被「尽力恢复」后进入服务。

**Why this priority**: 没有可信的备份与恢复点，后续隔离恢复、核验与复服全部失去地基；「备份存在」与「能恢复且恢复正确」是最容易被高估的差距。

**Independent Test**: 用一组受控备份样本（完整、损坏、截断、未验证、版本不兼容、缺少依赖）验证：只有完成实际恢复验证且兼容且依赖齐备的备份才能被用于恢复与复服；其余全部 fail-closed，无需实现完整复服流程即可演示。

**Acceptance Scenarios**:

1. **Given** 一个备份被标记为成功但尚无恢复验证结论，**When** 系统被要求把它作为可用恢复点，**Then** 该备份标记为「未验证」且不得作为复服依据；直到完成一次实际恢复验证（可读取、结构/约束完整、关键业务状态可用、核验可执行）才可继续。
2. **Given** 备份损坏、不完整、校验失败或与目标 schema/程序版本不兼容，**When** 尝试恢复，**Then** 明确拒绝并给出原因，不得进入核验完成或复服，不得「尽力而为」后继续。
3. **Given** 恢复所需外部依赖或配置缺失（连接/权限/外部事实来源/密钥边界等），**When** 尝试恢复或核验，**Then** 阻塞在明确状态并报告缺失项，不得宣称恢复完成。

### User Story 2 - 隔离恢复与旧实例控制：默认不产生任何外部效果 (Priority: P1)

从备份恢复出的环境默认处于隔离态：不执行提款、不签名、不广播、不向真实下游投递；在任何写入或外部动作恢复之前，旧写入者、调度器、发布者与消费者必须被可验证地停止并隔离，系统能证明新旧不会同时执行。

**Why this priority**: 双执行是灾难恢复场景中造成重复付款与重复事件效果的最大来源；隔离不成立时，任何核验结论都不足以保证安全。

**Independent Test**: 在恢复环境未解除隔离、旧实例状态不明、隔离证据缺失三组条件下，验证所有写入/发送/投递路径均被拒绝；在隔离证据逐项齐备后，仅指定能力可按分级程序开放。无需完整核验流程即可独立演示。

**Acceptance Scenarios**:

1. **Given** 一个刚恢复出的环境，**When** 未显式解除隔离，**Then** 提款创建/执行、签名、广播、真实事件发布/消费与下游投递全部不可执行；进程重启 MUST NOT 自动解除隔离。
2. **Given** 旧写入者/调度器/发布者/消费者无法证明已停止（失联、状态不明、仅口头确认），**When** 请求恢复任一写入或投递能力，**Then** 拒绝并列出缺失的隔离证据，默认视为旧实例仍在运行。
3. **Given** 隔离检查清单逐项核验且证据完整，**When** 解除指定能力的隔离，**Then** 仅该能力按分级复服程序开放，其余保持隔离；全过程审计且可复核。

### User Story 3 - 恢复后事实核验：证据缺口保持未知 (Priority: P1)

PG 恢复到较早时间点后，系统逐项核对本地事实与外部事实（链、签名、广播、Outbox、消费者、014 差异与授权审计）；数据库回退不被解释为外部效果回退，旧备份缺失的记录不被当作「从未发生」，无法证明的项目保持未知并产出人工处置所需证据；受影响能力保持暂停，可证明独立且证据充分的能力按已裁决审批规则（FR-023）放行；缺口无法补齐时保留 unknown/pending、证据包、责任归属与升级记录（FR-019）。

**Why this priority**: 这是本功能的核心价值：在「本地状态」与「外部世界」已经分叉时，系统必须能诚实地分辨哪些可以证明、哪些不能，而不是把回退后的视图当作真相信号。

**Independent Test**: 构造「外部事实领先于恢复点」的受控数据集（链上已确认付款、签名/广播记录已推进、下游已消费、恢复点缺记录），验证核验产出正确的差异/未知清单、零重复付款、零错误事件效果，且受影响能力在缺口闭合或经独立证明并按 FR-023 批准前保持关闭。

**Acceptance Scenarios**:

1. **Given** 恢复点早于链上/签名/广播/下游已推进的事实，**When** 执行核验，**Then** 产出差异与「未知」结论及证据缺口清单，受影响能力保持关闭（仅可证明独立且按 FR-023 批准的能力除外）；不重复付款、不重复广播、不产生错误事件效果。
2. **Given** 恢复点缺少某付款意图、nonce 记录或幂等记录，**When** 核验该对象，**Then** 记录为证据缺口并保持未知；不得当作「从未付款/未消耗/可重执行」，不得新建付款意图或补写幂等记录。
3. **Given** 核验发现无法证明的缺口，**When** 系统准备人工处置材料，**Then** 产出证据包（对象、范围、时间线、现有证据、所需外部证据、受影响复服项）并阻塞对应复服，等待人工裁决。
4. **Given** 证据缺口未闭合、受影响能力保持暂停，但另一能力经依赖核验可证明独立且证据充分，**When** 申请复服，**Then** 仅按 FR-023 审批规则放行该独立能力，并记录范围、依赖核验、有效证据与批准结果，且不间接启动被暂停的付款/签名/广播/真实下游副作用。
5. **Given** 缺口无法补齐，**When** 发生超时、重试耗尽或人工知悉，**Then** 保留 unknown/pending、证据包、责任归属与升级记录，允许有界只读复核；上述事件不得视为缺口闭合或获准复服。

### User Story 4 - 分级复服：三类状态分开，逐项放行 (Priority: P2)

数据库已恢复、核验完成与获准复服是三个不同状态；查询、链扫描、充值确认、既有提款恢复、新提款创建、事件发布、事件消费等能力各自有独立开放条件、授权、范围、理由、证据与审计，不存在一键全开；放行遵守已裁决审批规则（FR-023）：执行恢复、读取核验、批准复服权限独立；新提款创建、既有提款恢复、向真实下游投递及可产生真实下游业务效果的消费恢复须两名不同且均非本恢复实例执行者的授权人员共同批准，其余能力由一名非执行者授权人员批准并审计；放行操作幂等，中断后可安全重入。

**Why this priority**: 恢复后的系统最容易犯的错误是过早恢复资金写入；分级复服把「能读」「能扫」「能付款」「能投递」分开，让风险随证据逐步释放。

**Independent Test**: 在数据库已恢复但核验未完成、核验完成但未获准、获准但范围受限三种状态下，验证各能力开关的独立性与拒绝/放行结果，以及批准规则（双人/单人、非执行者限制）与证据变化导致的批准失效、中断重入幂等；可用桩数据独立演示。

**Acceptance Scenarios**:

1. **Given** 数据库已恢复但核验未完成，**When** 查询状态，**Then** 只报告「已恢复」，不报告「核验完成/获准复服」；所有能力默认关闭。
2. **Given** 某能力核验通过但未获授权放行，**When** 请求开放新提款创建，**Then** 拒绝并审计；**Given** 两名不同且均非本恢复实例执行者的已授权人员共同批准且证据有效，**Then** 仅开放该项并记录授权主体、范围、理由、证据版本与时间，其余能力保持关闭。
3. **Given** 查询、链扫描等其余能力核验通过，**When** 由一名非执行者授权人员批准，**Then** 仅开放该项并记录范围、理由、证据版本与时间，且不得间接启动签名/广播/付款/真实下游副作用；**Given** 仅由本恢复实例执行者本人申请或批准，**Then** 拒绝并审计。
4. **Given** 复服操作在中断后被重复执行，**When** 重入，**Then** 不产生重复副作用、不发生状态翻转；已开放与未开放项可分别观察。
5. **Given** 已批准项所依据的证据发生变化或相关门禁失效，**When** 继续执行或申请后续复服，**Then** 旧批准失效、相关后续执行停止，须重核重批；在途动作按既有安全门禁处理，未知结果不视为未执行。

### User Story 5 - 事件与下游边界：回退后果可检测，不宣称恰好一次 (Priority: P2)

备份回退可能造成事件重复、inbox/offset 回退与历史幂等记录缺失；系统必须能检测并保守处理这些后果，不宣称跨系统恰好一次，也不在未接入真实上游回执时宣称外部账本一致或已恢复。

**Why this priority**: 事件与下游是恢复后副作用最容易外溢的通道；边界说清才能避免把「本地恢复」误报为「外部一切正常」。

**Independent Test**: 注入重复事件、offset 回退、幂等记录缺失三组场景，验证重复被吸收、回退被检测、缺失不被静默处理，以及所有对外结论均限定在本项目可验证范围。

**Acceptance Scenarios**:

1. **Given** 备份回退使事件重复、offset/inbox 回退或历史幂等记录缺失，**When** 消费继续，**Then** 重复被幂等吸收、回退可检测、缺失不被静默补写为「已处理」或据此判定可重执行；可能的外部重复效果被检测并报告。
2. **Given** 未接入真实上游/下游回执，**When** 汇报恢复结论，**Then** 只能声明本项目范围内可验证的结论，不得宣称外部账本一致、已入账或外部效果已恢复。
3. **Given** 重复事件到达下游，**When** 处理与报告，**Then** 提供下游去重所需的稳定身份与检测/处置边界，明确不承诺跨系统恰好一次。

### User Story 6 - 演练、指标与失败路径：隔离环境可复现 (Priority: P2)

在隔离环境用真实恢复流程完成一次可复现演练：恢复、核验、在条件不满足时拒绝不安全复服、在条件满足后分级复服；全程分别记录数据库恢复时间、核验时间、各能力安全复服时间、备份滞后与未覆盖区间，且所有失败路径都有明确、可观察、可重入的结果。

**Why this priority**: 没有演练与指标，「可恢复」只是声明；演练同时是隔离、核验、复服三项能力的联合验收场所。

**Independent Test**: 用受控备份与注入的失败路径独立运行演练脚本/流程，检查时间口径与指标记录（数据库恢复时间、核验时间、各能力安全复服时间、备份滞后、未覆盖区间）与每类失败路径的 fail-closed 结果；不依赖生产环境。

**Acceptance Scenarios**:

1. **Given** 隔离环境与一个已验证备份，**When** 执行演练，**Then** 走通「恢复 → 核验 → 拒绝不安全复服 → 满足条件后分级复服」，并分别记录恢复点、数据库恢复时间、核验时间、各能力安全复服时间、备份滞后与未覆盖区间。
2. **Given** 备份不可用、恢复中断、版本不兼容、外部事实领先、旧实例未隔离等失败注入，**When** 遇到或重演，**Then** 每类收敛到明确的 fail-closed 结果，可观察、可审计、可重入，且不产生重复外部副作用。
3. **Given** 普通 PR 通道，**When** 运行快速检查，**Then** 对恢复/核验/复服的核心不变量给出通过/失败结论；完整灾备演练在独立通道运行，不默认进入普通 PR。

### Edge Cases

- 备份文件存在但不可读、损坏、截断或校验失败：不构成可用恢复点；不得尝试「尽力恢复」后进入核验完成或复服。
- 恢复成功但外部事实（链/签名/广播/下游）比恢复点更新：全部相关项标记差异/未知，相关能力保持关闭；不得把外部领先解释为本地正确。
- 旧实例无法证明停止（网络分区、状态不明、仅口头确认）：默认视为仍在运行，复服阻塞；不得以超时或失联推断已停止。
- 恢复中断/部分完成：不得进入核验通过；重新恢复必须幂等，遗留状态可识别、可清理，不得在同一权威状态上叠加双份或混合状态。
- 备份与程序/schema 版本不兼容：明确拒绝恢复或拒绝复服；不得静默降级或自动改写数据继续。
- 恢复环境意外可达真实下游（RPC/消息/回调）：默认阻断真实投递；任何测试性外发必须显式、可审计、可回收，且不得产生真实资金或外部账本效果。
- 核验发现链上付款已发生而本地无记录：记录为外部事实领先；保留原始意图追踪，不重建、不重复广播、不重复付款；报告证据缺口。
- 事件 offset/inbox 回退：重复消费可能发生；幂等吸收与检测必须成立；不得把「已消费记录缺失」直接当作未消费并自动触发有副作用的处理。
- 备份中缺少部分历史幂等记录：不得以缺失推断可重执行；相应身份按保守（未知）处理。
- 未接入真实上游回执：不得报告外部账本一致或外部效果已恢复。
- 证据缺口无法补齐（超时/重试耗尽/人工知悉）：保留 unknown/pending、证据包、责任归属与升级记录，允许有界只读复核；不得视为缺口闭合或获准复服；风险接受后强制复服、损失核销、人工补偿付款与自动补造意图不在本阶段交付。
- 依赖关系无法证明独立：保守纳入暂停范围；暂停范围包含缺口直接关联及依赖/可能放大副作用的能力；不得仅凭「不同模块」判定独立放行。
- 独立性或安全前提被后续证据推翻：相关复服批准立即失效，停止后续执行；在途动作按既有安全门禁处理，未知结果不得视为未执行；恢复须重核重批。
- 双人批准遇到硬门禁：缺证、未隔离、未知付款结果等情况下，即使两名授权人员共同批准也不得放行或间接启动被暂停能力。
- 同一复服项重复批准/重复执行：幂等，零重复副作用；撤销或回退复服必须再次显式、有授权并审计。
- 演练环境恢复成功但与生产配置/资产不同：只能声明演练范围内结论，不得推广为生产就绪（T000-P 保持 OPEN）。
- 普通 PR 意外触发完整灾备长测：CI 分层保护必须阻止；演练必须在独立通道可独立并行运行。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个备份 MUST 具备可独立识别的身份与元数据，至少包含：覆盖范围、对应恢复点（本地权威状态的时间或位置语义）、生成时间、完整性校验信息、目标 schema/程序版本信息；备份的选择规则 MUST 明确、可复核，MUST NOT 仅依赖文件名或人工记忆挑选，避免选错、选旧或选到互相冲突的「最新」。
- **FR-002**: 备份 MUST 明确声明覆盖范围：至少覆盖 PostgreSQL 权威状态（链同步游标与区块身份、事件与充值/确认状态、提款请求与付款意图、出站交易与签名/广播记录、nonce 分配状态、Outbox 与义务标记、消费者幂等与进度、审计与权限记录、014 差异与授权记录）；MUST 明确声明不覆盖或不由备份承担的状态（Redis/Kafka 等非权威状态、Signer 私钥与真实凭据等）。覆盖范围之外的权威事实 MUST 有恢复来源或被明确标记为缺口，MUST NOT 默认「不存在即无需恢复」。
- **FR-003**: 备份完整性 MUST 可验证；损坏、缺失、截断、部分写入或校验失败的备份 MUST 可被检测，MUST NOT 作为可用恢复点参与恢复或复服；完整性未知等同不可用（fail-closed）。
- **FR-004**: 恢复前 MUST 检查备份与目标 schema/程序的兼容性（含迁移版本与运行程序要求）；不兼容 MUST 明确拒绝恢复或拒绝复服，MUST NOT 静默降级、自动改写或「尽力而为」继续。
- **FR-005**: 恢复所需的外部依赖与配置 MUST 在恢复前明确列出并检查（连接与权限、外部事实来源可达性、下游状态、密钥边界可达性等）；依赖不可用 MUST 阻止进入核验完成或复服，MUST NOT 以恢复「基本完成」为由继续。
- **FR-006**: 备份成功的判定 MUST NOT 等同恢复成功；每个被宣称可用的备份 MUST 至少完成一次实际恢复验证（隔离或等效受控环境），验证必须覆盖可读取、结构与约束完整、关键业务状态可用、核验可执行，而非仅「能读出来」；未经验证的备份 MUST 标记为未验证，MUST NOT 作为复服依据。
- **FR-007**: 私钥、签名密钥与真实凭据 MUST NOT 出现在数据库备份、仓库或证据日志中；签名密钥继续留在 Signer 边界，恢复环境 MUST NOT 为完成恢复而获得业务服务可直接持有的私钥或真实凭据；备份/恢复/核验的证据与日志 MUST 遵守既有脱敏与禁私钥记录要求。
- **FR-008**: 备份与恢复过程的中断、失败与部分完成 MUST 有明确结果；MUST NOT 把部分恢复的状态标记为「已恢复」；重试 MUST 幂等，且不得与未清理的残留在同一权威状态上叠加产生双份或混合状态。
- **FR-009**: 从备份恢复出的运行环境 MUST 默认处于隔离态：默认 MUST NOT 执行提款创建/执行、签名交付、广播、向真实下游投递或真实事件发布/消费；任何不可逆或外部可见动作默认关闭（fail-closed）；解除隔离必须显式、有授权且可审计，进程重启 MUST NOT 自动解除。
- **FR-010**: 在任何写入、发送、广播、发布或消费恢复之前，系统 MUST 能证明旧写入者、调度器、发布者与消费者已停止且不再具备执行能力；停止与隔离 MUST 可验证、可复核（检查清单与证据），MUST NOT 仅凭口头确认、超时或「失联」推断；无法证明隔离时 MUST NOT 开启对应复服。
- **FR-011**: MUST 阻止新旧实例同时执行资金相关流程（重复写、重复付款、重复事件效果）；本要求继承 000018 建立的禁混跑约束与其检查清单模式（旧实现/旧写入者不得与新实现混跑；须逐项核验完成后再恢复调度与人工调用），并扩展到恢复与复服场景；具体核验工具与部署形态留 plan。
- **FR-012**: 隔离与解除 MUST 覆盖所有可能产生外部效果或双写的路径：提款创建与执行、签名、广播、事件发布与消费、下游投递、定时调度与自动任务，以及恢复/核验工具自身的外部写；隔离 MUST NOT 通过削弱或跳过既有资金门禁实现。
- **FR-013**: 恢复与核验期间 MUST 继续遵守私钥隔离、逐笔授权、nonce 与广播门禁等既有约束；恢复环境 MUST NOT 成为绕过既有授权与门禁的通道，MUST NOT 直接重放历史签名或广播。
- **FR-014**: 恢复后 MUST 逐项核验至少以下类别，并记录每项的对象、范围、证据、结论（一致/差异/未知）与时间：PostgreSQL 业务状态 vs 链上事实；提款请求与付款意图；nonce 分配与占用；签名记录与广播结果（含未知）；Outbox 事件与义务标记；消费者幂等记录与进度；014 差异单、处置与授权审计。核验结果 MUST 可审计、可复核。
- **FR-015**: 数据库回退 MUST NOT 被解释为外部付款或消费效果的回退；链上已发生的交易、已产生的签名/广播、下游已消费或已入账的事实 MUST 保持为外部事实；系统 MUST 显式区分「本地回退」与「外部已推进」，并把差异列入核验结论。
- **FR-016**: 恢复点缺失的记录 MUST NOT 被当作「从未发生/从未付款/可安全重执行」；缺失 MUST 作为证据缺口处理（未知 + 待核验），MUST NOT 据此发放许可或重建动作。
- **FR-017**: MUST NOT 假设 014 或任何对账/扫描能力能够重建备份后丢失的付款意图；意图无法证明存在时 MUST NOT 新建、重放或替代产生付款意图；付款继续只走既有授权与门禁路径；无法证明时保持未知并暂停相关能力。
- **FR-018**: 无法证明一致或完整的核验项 MUST 保持「未知」或「差异」状态并阻塞对应复服项；MUST NOT 以默认值、旧状态、时间推断或「大概未发生」填补证据；未知 MUST NOT 被当作通过。
- **FR-019**: 每个未闭合的证据缺口 MUST 产出人工处置所需的证据包（缺口对象与范围、时间线、现有证据、所需的外部证据或人工确认、受影响的复服项与风险）；受影响能力 MUST 保持暂停——暂停范围 MUST 包含缺口直接关联及依赖/可能放大副作用的能力，依赖无法证明独立时 MUST 保守纳入暂停，MUST NOT 仅凭「不同模块」判定独立。可证明独立且证据充分的能力 MAY 按 FR-023 审批规则放行，且 MUST 记录范围、依赖核验、有效证据与批准结果，MUST NOT 间接启动被暂停的付款/签名/广播/真实下游副作用。缺口无法补齐时 MUST 保留 unknown/pending、证据包、责任归属与升级记录，可保留有界只读复核；超时、重试耗尽或人工知悉 MUST NOT 被视为缺口闭合或获准复服。后续证据变化推翻独立性或安全前提时，相关批准 MUST 失效、停止后续执行，在途动作按既有安全门禁处理，未知结果 MUST NOT 视为未执行。本阶段不交付风险接受后强制复服、损失核销、人工补偿付款或自动补造意图（此类政策另行业务裁决）；双人批准 MUST NOT 替代缺失证据。
- **FR-020**: 核验 MUST 与既有对账/恢复/重放能力衔接（复用 006 恢复区间重放、013 隔离重放与消费者进度、014 差异/证据/权限与审计），但 MUST NOT 因复用而绕过各能力的授权与门禁；核验及其触发的动作 MUST NOT 直接触发付款。
- **FR-021**: 复服 MUST 分级且各项独立：查询、链扫描、充值确认、既有提款恢复、新提款创建、事件发布、事件消费（含对真实下游的投递）每一项 MUST 有独立的开放条件、状态与结果；MUST NOT 存在「一个开关恢复全部」的路径。
- **FR-022**: 系统 MUST 区分并显式暴露三种状态：数据库已恢复（restored）、核验完成（verified）、获准复服（approved）；前一状态 MUST NOT 自动蕴含下一状态；每项能力的开放必须显式、有记录、可查询。
- **FR-023**: 每项复服 MUST 记录：授权主体与权限、范围（链/资产/业务类型/能力）、理由、依据的核验证据与证据版本/时效、时间与结果；越权、证据不足或证据过期/失效的复服请求 MUST 被拒绝并审计。批准角色与审批规则（2026-09-28 裁决）MUST 为：执行恢复、读取核验、批准复服为独立权限（不要求三人互斥），恢复执行者可读授权范围内核验结果，但 MUST NOT 批准自己执行的恢复实例；新提款创建、既有提款恢复、向真实下游投递及可产生真实下游业务效果的消费恢复 MUST 由两名不同已授权人员共同批准，两人均 MUST NOT 是该恢复实例执行者，MUST NOT 以同一人双账号充数；其余能力可由一名非执行者授权人员批准并审计，且只能开放所列能力，MUST NOT 间接启动签名/广播/付款/真实下游副作用，能力依赖 MUST 明确；每次批准 MUST 绑定恢复实例、能力、范围与证据版本，证据变化或门禁失效后旧批准 MUST 失效并重核重批；放行时 MUST 仍校验全部硬门禁，双人批准 MUST NOT 覆盖缺证、未隔离或未知付款结果等硬门禁；本条仅适用于 015 灾备后复服，不改变正常运行及 014 已批权限，MUST NOT 新增紧急绕过或管理员强制复服入口。
- **FR-024**: 复服操作 MUST 幂等且可重入：中断后可安全继续或重试，重复批准/重复执行 MUST NOT 产生重复外部副作用或状态翻转；因证据变化或门禁失效而失效的批准 MUST 显式重核重批（重核重批本身幂等）；已开放与未开放项 MUST 可分别观察；撤销或回退某项复服必须再次显式、有授权并审计。
- **FR-025**: 复服、核验与演练 MUST 继续遵守既有资金门禁（链/日志/充值暂停、恢复行、nonce hold、授权范围暂停、容量红线等）与现有授权；开放某项能力 MUST NOT 解锁任何既有门禁，也 MUST NOT 追认或修复过去差异；门禁解除仍走其原有受控路径。
- **FR-026**: 恢复期间与过渡期，系统对外 MUST 诚实报告状态：哪些能力可用、哪些被隔离或暂停、哪些核验未知；查询与健康信号 MUST NOT 把未核验或回退后的数据显示为正常一致，MUST NOT 以健康探针替代资金门禁判权。
- **FR-027**: 备份回退导致的事件重复、inbox/offset 回退与历史幂等记录缺失 MUST 被识别与吸收：重复消费可被幂等去重，offset 回退可被检测，缺失的幂等记录 MUST NOT 被静默补写为「已处理」或据此判定可重执行；可能产生的外部重复效果 MUST 可检测、可报告。
- **FR-028**: MUST NOT 宣称跨系统「恰好一次」；在至少一次投递语义下，重复事件可能导致下游重复效果，系统 MUST 给出下游去重所需的稳定身份与检测/处置边界，并如实标注未验证部分。
- **FR-029**: 未接入真实上游/下游回执时，MUST NOT 宣称外部账本一致或「外部效果已恢复」；只能声明本项目范围内可验证的结论。
- **FR-030**: MUST 在隔离环境完成可复现的演练：实际执行一次恢复（使用真实恢复流程，而非重新初始化空库）、执行核验、在条件不满足时拒绝不安全复服、在条件满足后按分级顺序恢复服务；演练 MUST 可重复且结果可存档。
- **FR-031**: 演练与真实恢复 MUST 记录至少：恢复点、数据库恢复时间、核验时间、各能力安全复服时间、备份滞后（恢复点与最新外部事实/最新本地写入的距离）、未覆盖区间（备份未包含的时间或数据范围）、发现的证据缺口数量与处置状态；上述时间口径 MUST 分开记录且不得混同（不得以数据库可连接代表 RTO 达标）；口径必须明确且可查询，本地演练数值 MUST 标注为测试输入，MUST NOT 当作生产阈值或生产承诺；未配置必需约束时 MUST NOT 据此宣称符合生产恢复目标。
- **FR-032**: 以下失败路径 MUST 有明确、可测、fail-closed 的结果且可观察、可审计、可重入：备份不可用/不可读/不完整/未验证；恢复中断或部分完成；版本或 schema 不兼容；外部事实领先恢复点（链/签名/广播/下游已推进）；旧实例未隔离或隔离无法证明；核验发现无法证明的缺口；复服越权或证据不足/过期。
- **FR-033**: 恢复/核验/复服的核心不变量 MUST 有可在普通 PR 通道运行的快速逻辑/契约检查；完整恢复演练与长流程 MUST 在独立通道运行，普通 Go PR MUST NOT 默认执行完整灾备长测；演练通道可独立并行运行。
- **FR-034**: PostgreSQL 继续作为唯一权威真源；恢复与复服过程 MUST NOT 让 Redis/Kafka/缓存/本地文件成为金融真相；备份仅作为权威状态的恢复载体，恢复后的权威判定仍以恢复出的 PG 状态加链上事实核验为准。
- **FR-035**: 本阶段 MUST 只交付后端能力与可验收程序，不含 Kubernetes、自动主备切换、多地域、具体备份产品/存储厂商/PITR 实现与编排选型（留 plan）；T000-P 保持 OPEN，不宣称生产就绪。
- **FR-036**: 备份/恢复必须支持的目标与保留口径（RPO/RTO、备份频率与保留期、可接受的数据损失范围）MUST 可配置并作为可验收口径，且 MUST 明确测量口径：本阶段交付可配置恢复目标、测量口径、实际演练与约束检查；生产 RPO/RTO、备份频率与保留期数值留部署前业务裁决（2026-09-28），MUST NOT 编造生产数值或默认「允许损失」。数据库恢复时间、核验时间与各能力安全复服时间 MUST 分开记录，MUST NOT 以数据库可连接宣称 RTO 达标；证据缺失、恢复点不满足批准要求等 MUST 阻止受影响能力复服，RTO 超时 MUST 记录不达标、告警并升级，但 MUST NOT 单独成为永久禁止后续安全复服的条件；未配置必需约束时 MUST NOT 宣称符合生产恢复目标，本地演练参数 MUST 标注用途；备份频率 MUST NOT 被当作已证明 RPO，接受恢复点滞后 MUST NOT 解释为批准丢弃已接受的请求、付款意图、nonce、签名广播或幂等证据；本规格不批准任何资金数据损失额度，不授权绕过既有资金门禁。

### Key Entities

- **备份 (Backup)**: 可独立识别的恢复载体；属性含身份、覆盖范围、对应恢复点、生成时间、完整性校验结论、目标 schema/程序版本、验证状态（已实际恢复验证/未验证）。
- **恢复点 (Recovery Point)**: 备份所对应的本地权威状态时间或位置，及其与外部事实的距离（备份滞后、未覆盖区间、不可证明范围）。
- **恢复环境 (Recovery Environment)**: 由备份恢复出的隔离运行环境；默认不具备外部效果能力；核验与分级复服的执行场所。
- **隔离证据 (Isolation Evidence)**: 旧写入者/调度器/发布者/消费者已停止且不再具备执行能力的可复核证明（含 000018 检查清单模式的核验结论）。
- **核验项 (Verification Item)**: 一项本地事实与外部事实的核对；属性含对象、范围、证据、结论（一致/差异/未知）、时间、关联证据缺口。
- **证据缺口 (Evidence Gap)**: 无法证明的项目及所需人工/外部证据，阻塞直接关联及依赖/可能放大副作用的复服项；缺口无法补齐时保留 unknown/pending 与升级记录，可证明独立且证据充分的能力按 FR-023 批准后放行。
- **复服项 (Resumption Item)**: 可独立开放的能力单元（查询/链扫描/充值确认/既有提款恢复/新提款创建/事件发布/事件消费）；属性含状态（restored/verified/approved）、授权、范围、理由、证据与证据版本、时效、审计。
- **演练记录 (Drill Record)**: 演练场景、恢复点、时间线、指标（数据库恢复时间/核验时间/各能力安全复服时间/备份滞后/未覆盖区间）、拒绝与放行结论、失败路径结果。
- **审计轨迹 (Audit Trail)**: 备份/恢复/核验/复服决策的操作记录；只追加、可查询、不可篡改。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 受控备份样本的实际恢复验证通过率 100%，且每个被标为「可用」的备份都有恢复验证记录；「备份成功」被单独当作「恢复成功」的案例为 0。
- **SC-002**: 在「外部事实领先恢复点」的演练场景中，证据缺口识别率 100%，重复付款 0 次、错误事件效果 0 次；缺口直接关联及依赖/可能放大副作用的受影响能力在核验闭合、或经独立证明并按 FR-023 批准前 100% 保持关闭；独立放行项 100% 记录范围、依赖核验、有效证据与批准结果，且 0 次间接启动被暂停的付款/签名/广播/真实下游副作用。
- **SC-003**: 旧实例未停止或隔离无法证明时，复服与写入/投递相关请求 100% 被拒绝；演练证明隔离检查是任何写入/发送/投递恢复的前置，新旧同时执行的可观测窗口为 0。
- **SC-004**: 分级复服覆盖 7 类能力（查询/链扫描/充值确认/既有提款恢复/新提款创建/事件发布/事件消费），每类有独立条件与审计记录；越权、证据不足或证据过期/失效的复服请求 100% 被拒绝并审计；新提款创建、既有提款恢复、向真实下游投递及可产生真实下游业务效果的消费恢复，在缺少两名不同且均非本恢复实例执行者的授权批准时 0 次放行；其余能力在缺少非执行者授权人员批准时 0 次放行；证据变化或门禁失效后旧批准 100% 失效；未获准能力保持关闭。
- **SC-005**: 端到端演练（恢复→核验→拒绝不安全复服→条件满足后分级复服）可在隔离环境按可复现步骤演示；数据库恢复时间、核验时间、各能力安全复服时间与备份滞后、未覆盖区间 MUST 分开记录且可查询（演练场景 100% 覆盖），不得出现以「数据库可连接」宣称 RTO 达标的结论；若配置了时间目标，RTO 超时 MUST 100% 记录为不达标、告警并升级，且不单独成为永久禁止后续安全复服的条件。
- **SC-006**: 7 类失败路径注入（备份不可用/恢复中断/版本不兼容/外部事实领先/旧实例未隔离/证据缺口/越权复服）下，0 次错误开放、0 次重复外部副作用，全部收敛到可观察的 fail-closed 状态并产出明确结果；证据缺口类场景中无法补齐的缺口 100% 保留 unknown/pending 并记录证据包、责任归属与升级，不因超时、重试耗尽或人工知悉而被视为闭合或获准复服；本阶段不交付风险接受后强制复服、损失核销、人工补偿付款或自动补造意图，双人批准亦不得替代缺失证据。
- **SC-007**: 重复执行恢复、核验与复服操作（含中断后重入）10 次，外部副作用与状态翻转 0 次（幂等）。
- **SC-008**: 恢复/核验/复服的快速检查可在普通 PR 通道给出明确通过/失败结论（无需完整灾备长测）；完整演练在独立通道可独立运行且不阻塞普通 PR。

## Assumptions

### 复用声明（引用，不新建）

- **006 恢复区间重放（ReplayRecoveryRange）**与恢复版本/操作矩阵：作为核验后只读追溯与既有恢复的执行基础，不重建。
- **013 隔离重放（quarantine Replay，范围 + operation_id 幂等）**、`consumer_progress` 持久续跑、inbox/版本守卫：作为恢复后重复消费与回退的检测与保守处理基础。
- **014 任务检查点、暂停/恢复、差异身份/证据/权限矩阵与审计**：作为恢复后核验的差异、证据、授权与审计基础；014 的权限与门禁继续有效。
- **幂等矩阵**：`withdrawal_requests` UNIQUE（调用方键与授权唯一）、Outbox 同身份同内容 Noop、`operation_id` UNIQUE、`delivery_admissions` 交付门禁快照——恢复后重复动作的持久幂等基础。
- **append-only 审计表族**（如 `recon_audit`、`event_ops_audit`、`execution_ops_audit`、`signing_request_audit` 等）与 watermark 缺口审计：备份/恢复/核验/复服复用同一审计模式，不新建第二套审计体系。
- **faultdrill 五态矩阵、CollectInvariants、perf harness 与 docs/evidence 证据模式**：作为演练与证据的既有通道。
- **migrate Up/Status/Inspect/CheckCompatibility**：恢复前后的 schema 状态检查复用，不新建迁移检查能力。
- **资金门禁**：`indexer_pause`、日志/充值暂停、重组恢复行、nonce hold、授权范围化暂停、容量红线——复服继续遵守，不绕过。

### 新增范围（本阶段界定）

- 备份身份/manifest 与恢复点语义（覆盖范围、完整性、兼容性、验证状态与选择规则）。
- 隔离恢复产品能力（默认无外部效果的环境与旧实例隔离检查）。
- 分级复服程序（能力清单、restored/verified/approved 三态、授权/证据/审计、幂等重入）。
- 备份/恢复演练定义与 RTO/RPO/完整性口径（可配置；生产数值留部署前业务裁决，见「澄清裁决」）。

### 不确定/需上游确认

- 现状扫描：`compose.yaml`、`Makefile`、CI 工作流均无备份服务引用；若部署环境在仓库外已有外部备份或快照能力，其存在性、覆盖范围与保留策略须由上游确认；本规格不假设其可用，也不依赖它。
- 生产 DownTo 仅测试用：迁移 Down/DownTo 与 schema 回滚不作为恢复手段，恢复一律来自备份/恢复点。
- **000018 清单模式裁定（specify，2026-09-28）**：000018 的升级/回滚检查清单模式（禁混跑：旧写入者退出、版本核验后再恢复调度与人工调用）作为本规格隔离与复服的流程模板沿用；只复用其检查清单结构与纪律，不复用其迁移内容；具体检查项在 plan/tasks 落地。

### 已确认约束（Constitution 与既有契约继承）

- PG 唯一权威；Redis/Kafka 不持金融真相；私钥仅 Signer；幂等落 DB 约束；显式状态机；事务边界；nonce 并发安全；失败路径一等公民；可观测为正确性一部分；测不变量；简单优先。
- 既有资金门禁与授权链（暂停、hold、freeze/范围化暂停、inbox 幂等、版本守卫、发送/执行门禁、unknown 永不作为许可或重建依据）不可绕过。
