# ADR-003: Serialize Restore Writers per PostgreSQL Target

**Date**: 2026-09-29 (revised 2026-09-29) | **Spec**: [spec.md](../spec.md) (FR-008) | **Status**: Accepted for bounded implementation after Oracle Gate 1 (3/3); not production-ready, all prerequisites fail-closed | **Related**: [ADR-001](ADR-001-recovery-control-store.md), [data-model.md](../data-model.md) §1/§4.4/§6/§7, [plan.md](../plan.md), [T019/T020](../tasks.md)

## Context

`ExecuteRestore` (T019) and `ExecuteVerifyBackup` (T020) both invoke `pg_restore` against a target. T019's pre-write `restore_started` marker invalidates old evidence, but neither command currently coordinates target writers. Two operations can overlap, or a child can outlive its parent. Operation IDs and recovery-instance evidence locks do not serialize target databases. T020 currently accepts a request target so long as it is not the control database; that does not establish the required trusted isolated target. This ADR closes that gap. T019's existing explicit production-main declaration/reason policy remains unchanged.

## Decision

1. **One shared target lock domain.** Both `ExecuteRestore` and `ExecuteVerifyBackup` acquire the same PostgreSQL *session-level advisory lock* through a dedicated connection to the independent recovery control store before invoking any target-writing `pg_restore`. The lock key is derived from the canonical credential-free tuple `(host, port, database)`. Role, command kind, actor, operation ID, and target declaration are excluded: restore and verification of the same target conflict, as do different roles targeting it. Lock derivation uses a stable versioned encoding/hash; hash collision may conservatively serialize unrelated targets, never permit concurrent writers. PostgreSQL releases a session advisory lock when its owning session disconnects; this releases only the live lock, not the separate durable guard. Failure to connect to or acquire the control-store lock is fail-closed.

2. **Supported identity boundary.** Canonicalization is limited to the parsed endpoint spelling: lowercase host, parsed numeric port, and exact database name. Credentials and DSN options are excluded. The supported guarantee is for commands that address the same endpoint spelling under this canonicalization. DNS aliases, IP/hostname equivalence, PostgreSQL clusters reached through different names, proxies, or other alias normalization are not promised or inferred. Existing `DSNTarget` parsing/fingerprinting is the basis; do not represent its fingerprint as DNS-normalized identity.

3. **Durable authoritative target binding and guard inventory.** An additive recovery-control-store migration after applied `0001` (never edit `0001`) adds a role-independent canonical target key binding on each recovery instance, captured at instance-open from trusted, deployment-owned configuration for the authoritative data target. Persist the exact supported `(host, port, database)` identity/key and the existing role-sensitive target fingerprint; the binding is immutable for that instance. Never derive it from a command DSN, caller-supplied isolation label, mutable data DB contents, or guessed DNS normalization. The guard table is a durable inventory keyed by the role-independent target key, not merely rows for currently running operations; absence of a row is `unknown`, never `clean`. A row stores credential-free endpoint/key and role-sensitive fingerprint(s) as applicable, operation and actor references, process/application identity, active-writer state, target disposition, and timestamps; no DSNs or credentials.

   Binding and guard lookup/initialization happen under the target advisory lock as part of instance-open. Open refuses if trusted authoritative target identity is absent/ambiguous, target binding cannot be captured, or an existing guard is inconsistent/active/dirty. If no guard row exists for a newly encountered trusted target, create it as `unknown` (never clean by absence) and require controlled rebuild/baseline verification before target writes, gate admission, or close. Once created, instance target binding cannot be edited; a different endpoint requires the existing explicit new-instance/supersede governance, not in-place rebinding. Persisting an endpoint spelling is not proof that aliases are distinct; ambiguity means refuse. The canonicalization/identity limits in Decision 2 remain.

   The guard separately models `active_writer` (writer may still be running) and disposition (`clean`, `rebuild_required`, `unknown`). After any child launch attempt, default disposition is `unknown`; child exit and no-session quiescence may set active-writer false but MUST NOT by itself set disposition clean. Any probe failure, evidence/publication failure, nonzero exit, interruption, lock loss, or ambiguous post-launch result leaves `rebuild_required` (or `unknown`, which blocks identically). Ordinary invocation refuses dirty/unknown disposition. Only a controlled, audited rebuild may establish clean, with positive completion evidence under the target lock. A role-independent key prevents role changes from bypassing serialization; role-sensitive fingerprints remain for instance/restore-target matching and audit.

4. **Supported child and liveness proof are deliberately narrow.** Support only Linux, direct locally supervised `pg_restore` in a dedicated process group. Docker, remote execution, shell wrappers, or any process topology that cannot be proven to remain under that local supervisor is unsupported and cannot clear a guard. Set a per-attempt unique PostgreSQL `application_name` via the libpq connection string passed to `pg_restore` (for example, its `--dbname` conninfo); enforce that value on all child PostgreSQL connections. Keep the value within PostgreSQL's application-name storage limit so it cannot be silently truncated (at most 63 encoded bytes for PG18's 64-byte fixed field including terminator); validate the observed value in `pg_stat_activity`. `application_name` is an attribution tag, not an authenticated session identity: do not treat it alone as proof that a backend belongs to this child or that no child backend remains. The guarantee is bounded to cooperative 015 processes and the supported local supervision/configuration boundary; arbitrary clients can spoof a tag and are excluded by the external-writer isolation assumption.

   After child exit or termination, execute a bounded target-side `pg_stat_activity` quiescence check for the exact application name, while also establishing that the supervised process group has exited. The observer must see full details for sessions owned by other roles. For PostgreSQL 18, the configured observer role must have `pg_read_all_stats` (or be superuser); deployment should grant the least-privilege monitoring role capability needed for this check rather than require superuser. Missing privilege, incomplete results, timeout, or any matching backend means quiescence is unproven and fails closed. Do not require or assume `pg_terminate_backend`; process-group supervision and externally demonstrated isolation are the specified controls.

   On cancellation, lock loss, or observed child failure, terminate the entire local process group and wait. If the parent receives SIGKILL, it cannot perform cleanup: the durable guard remains; every successor invocation refuses. SIGKILL recovery requires demonstrated external isolation (operator stops/isolates the target writer path), followed by the controlled reconciliation/rebuild process; a stale PID, absent advisory lock, or apparent process exit is not proof. Do not automatically steal locks or clear guards. Following a lock loss, reacquire the same target lock before controlled reconciliation; inability to reacquire or prove isolation/quiescence leaves the guard unresolved.

5. **Atomic restore acceptance, gate, and close.** `ExecuteRestore` must match the open instance's immutable role-independent target key and the role-sensitive target fingerprint where the established data-target contract requires it; mismatch, absent binding, or ambiguous identity refuses before target writes. After probes pass and child drain/quiescence is proven, accept T019 `restore_probe` evidence and transition the bound guard to clean/resolved in the same control-store transaction, retaining evidence-generation/token validation and row locking. Evidence insertion, generation/hash update, and guard transition commit together or not at all. A failed transaction leaves no accepted restore evidence and the guard dirty/unknown.

   Every recovery-gate evaluation and instance close/supersede precondition must resolve the instance's persisted target key and its guard row. Missing binding, missing guard row, key/fingerprint disagreement, active writer, or any dirty/unknown disposition is fail-closed; no-match is never interpreted as clean. Gate refuses capability admission; close refuses to close the instance. Atomic restore evidence/guard commit is the only path that makes successful restore evidence and clean disposition visible together. This adds no capability release or bypass of existing gates.

   For `verify-backup`, keep the guard unresolved through probes and manifest publication. Publish the final manifest atomically only after the child is drained and probes pass; only after successful file publication, atomically insert the existing DG-2 control-store evidence and transition the target guard to clean/resolved in one control-store transaction. If publication fails, no evidence is accepted and guard becomes/remains rebuild-required. If the DB transaction fails after file publication, the manifest's `verified` flag alone remains non-authoritative (restore still requires matching control-store evidence), and the guard remains blocking/rebuild-required. A rejected verification after launch also leaves rebuild-required; rejection before child launch does not. This ordering acknowledges the file and PostgreSQL control store cannot participate in one atomic transaction and fails closed in either crash window.

6. **Controlled rebuild / re-entry.** Ordinary restore and verify-backup invocations never clear unresolved guards. A dedicated controlled recovery action acquires the target advisory lock, proves/isolation-records that no writer can continue, runs the supported target rebuild under the same local supervision and application-name/session-observation rules, verifies completion/quiescence, and records the rebuild plus `clean` transition and audit. If the action itself is interrupted or any proof fails, retain rebuild-required/unknown. For SIGKILL or unsupported process topology, external isolation is required before this action; never infer clean from draining alone. This recovery mechanism does not alter backup selection, approval, evidence semantics, or ADR-001 control-store rollback policy.

7. **Before-first-write vs post-launch failure.** Failures proven before launch are `not_started`; after proving no child was launched, the prepared guard may be resolved without rebuilding. Once launch is attempted, any nonzero exit, interruption, lock loss, failed probe, failed evidence acceptance, or failed manifest publication is `rebuild_required`, even after the process group exits and quiescence is proven. Record separately `active_writer=false` and `target_disposition=rebuild_required`: quiescence means no identified writer remains, not that the target is clean. Do not claim `restored`/`verified`; retain T019's already-committed pre-write invalidation marker. T019's documented rebuild-and-rerun requirement applies; verification target must likewise be rebuilt before ordinary re-entry. Only the controlled, recorded rebuild above can clear this disposition.

## Verify-backup interplay

`verify-backup` requires a deployment-trusted isolated target binding. Concrete source: an access-controlled, deployment-owned recovery configuration loaded by trusted startup/configuration code (not a CLI argument or caller-supplied `isolated` label) contains the authoritative data target identity and the dedicated isolated verification target identity/credentials. The configured verification target must differ from both (a) the trusted authoritative data DB and (b) every current open instance's persisted target key and role-sensitive fingerprint as applicable. Compare supported canonical identities; if authoritative identity is missing, an open instance lacks its binding, any target is ambiguous, or a possible alias cannot be ruled out by trusted deployment topology evidence, refuse before any target write. Do not infer distinctness from two different DSN spellings and do not claim general DNS alias normalization.

The CLI gets the trusted binding only from that protected configuration; optional `--target-dsn` is merely an assertion and must match configured target/role identity. Core `ExecuteVerifyBackup` itself requires the trusted binding object and must route restore and probes only through its bound DSN; direct callers without it, mismatches, or missing/ambiguous authoritative/open-instance identities refuse before writes. Provisioning and protection of this configuration are deployment prerequisites. This is enforcement of the existing isolation requirement, not a new risk-acceptance policy.

   Since verification writes a target, it must durably invalidate that target's prior cleanliness before launching the child. It does not write T019's instance `restore_started` evidence-generation marker: instead the target guard is the pre-write invalidation fact, and recovery gate checks it. On successful verify, preserve DG-2's manifest-level/unbound versus instance-bound evidence semantics and atomically accept evidence with guard resolution only after safe file publication as above. No authoritative `verified` result exists from a request-supplied target or manifest flag alone. A post-launch rejected/failed verification remains rebuild-required; a pre-launch validation rejection has no target write and needs no rebuild.

## Ordered execution contract

1. Perform read-only argument, DSN, manifest/artifact, compatibility, and applicable control-store checks. Resolve authoritative configured target identity, immutable open-instance binding(s), and (for T020) protected isolated-target binding. Refuse missing, inconsistent, possibly aliased, or ambiguous identities; verify-backup target must differ from authoritative DB and every current open-instance target. A request-supplied isolation label is never evidence of isolation.
2. Derive canonical target key; connect to independent control store; acquire shared session advisory lock. Refuse on any error; do not start a child.
3. Read durable guard under the lock. If unresolved, take only the explicit recovery path above; ordinary invocation refuses.
4. Resolve the target's durable inventory row and immutable instance binding. For T019, require target key and applicable role fingerprint to match the open instance. For T020, require its trusted target to differ from the authoritative DB and all open-instance targets. Persist guard with active-writer expected and target disposition unknown before launch. For T019, commit `restore_started` marker before first target write. For T020, this guard is its pre-write cleanliness invalidation; do not accept an authoritative result until resolved.
5. Persist launch intent and unique application name, then start only the supported Linux locally supervised `pg_restore` process group with that application name enforced on every child connection. Unsupported wrappers/topologies refuse.
6. Monitor process and advisory lock. On failure/lock loss, terminate group and wait; then run the bounded, visibility-complete target `pg_stat_activity` check. If parent was SIGKILLed or proof is incomplete, ordinary successor refuses; controlled external isolation/rebuild is required.
7. After child success and quiescence, run existing probes. Any post-launch probe/publication/evidence failure sets/preserves `rebuild_required`, even if active-writer is false. For T020, publish final manifest before DB evidence/guard transaction; file-write failure means no evidence and rebuild-required.
8. For T019, atomically accept restore evidence plus clean/resolved guard in the evidence-generation transaction. For successful T020, atomically insert DG-2 evidence plus clean/resolved guard after manifest publication. Failure of either transaction leaves guard blocking; verify-backup manifest flags without matching control-store evidence remain non-authoritative.
9. Release advisory lock only after durable transition. Any operation after launch that did not reach the atomic successful transition leaves a rebuild-required guard; only explicit controlled rebuild can clear it. Gate evaluation refuses on any matching unresolved target guard.

## Required test matrix (contract tests plus PostgreSQL integration)

| Scenario | Setup / ordering | Required result |
|---|---|---|
| A — late writer arrives first | Start restore or verify-backup; pause after target lock/guard and before or during delayed `pg_restore`; invoke the other command for the same host/port/database, even with another role. | Second invocation blocks only within the configured bounded acquisition policy or refuses; it never launches a writer. First finishes/drains before a later retry can proceed. |
| B — first writer arrives second | Start two invocations concurrently with controlled barriers so either can win the advisory lock; include restore-vs-verify and verify-vs-restore. | Exactly one owns the target at a time; loser does not launch until prior guard is resolved. Both orderings preserve evidence and manifest rules. |
| Lock loss / parent SIGKILL | Drop lock during child; separately SIGKILL parent with child active. | Handled lock loss attempts process-group termination; SIGKILL leaves durable guard and successor refusal. Neither quiescence nor absent sessions clears rebuild-required. External isolation + controlled rebuild required. |
| Post-launch failure after drain | Make probe, evidence transaction, or manifest publication fail after child exits and all child sessions disappear. | `active_writer=false`, disposition remains `rebuild_required`; ordinary invocation and gate refuse until recorded controlled rebuild. |
| Trusted verify target and negative bindings | Call core/CLI with request-supplied isolated label, missing authoritative config, target equal to authoritative DB, equal to any open instance target, distinct spelling but unresolved possible alias, missing open-instance binding, and valid distinct configured target. | Only protected configured target proven distinct from authoritative and every open target proceeds. All missing/mismatched/ambiguous cases refuse before `pg_restore`; no label or no-match path defaults to clean. |
| Instance target binding / compatibility | Open instance with missing/ambiguous target config; mutate binding; remove guard row; use restore target with same role-independent key but wrong role fingerprint, then matching identity; gate and close under each guard state. | Open rejects absent/ambiguous identity; persisted binding is immutable; missing row/binding or active/dirty/unknown guard blocks gate and close. Restore requires key and applicable role fingerprint match. Existing open legacy rows are not auto-bound. |
| Cross-instance / cross-command | Two open instances or commands target same role-independent endpoint with differing roles; verify target collides with one open target; restore and verify race across commands. | Role change cannot bypass shared guard key; T020 refuses any open-instance target collision; bound keys prevent cross-instance no-match. Serialization and evidence/gate outcomes remain fail-closed. |
| Child session visibility | Observer lacks `pg_read_all_stats` (and is not superuser), query is incomplete/times out, or a matching backend remains; also test overlong application name. | Quiescence proof fails closed; guard remains unresolved/rebuild-required. Validate observer capability and enforce a non-truncated application name. |
| Different target | Run commands against distinct canonical host/port/database tuples; include different db and port, while varying role on same tuple separately. | Distinct tuples can proceed independently; role variation on same tuple serializes. Do not assert alias normalization. |
| Interrupted re-entry | Kill parent at each durable boundary (prepared, launch-intent, child active, after child before evidence/manifest publish, during guard transaction); retry. | No automatic lock steal or stale-guard clearing; pre-launch proven failure may resolve without rebuild; after launch the guard remains rebuild-required even after drain, and only explicit recorded controlled rebuild permits re-entry; unresolved/ambiguous cases refuse. |

## Consequences and boundaries

- The guarantee covers cooperative 015 commands sharing the same independent stable control database and supported canonical endpoint spelling. It does **not** serialize direct `pg_restore`, application writes, other operators/tools, aliases, or independent control stores. External writers must be excluded by operator isolation. The trusted verify target is a deployment binding, not a request claim.
- The control database must remain independent and available throughout execution. Control-store loss is not permission to proceed; the durable guard plus target isolation are the recovery boundary. A control-store rollback remains governed by ADR-001 and is not detected by this ADR.
- T019 target rebuild requirement remains and now explicitly applies after every post-launch failed/uncertain restore or verification; quiescence alone never clears rebuild-required. No production-main policy is relaxed.
- Implementation dependencies/uncertainties: exact trusted deployment-config source/protection and proof that isolated target differs from authoritative DB and all open-instance targets without alias normalization; representation/immutability enforcement of instance binding; migration and fail-closed compatibility treatment for existing open instances lacking a binding (no automatic backfill); Linux supervisor behavior and process-group lifecycle; enforcement and observed validation of non-truncated unique `application_name`; bounded `pg_stat_activity` query and observer `pg_read_all_stats`/superuser visibility; process termination/wait proof; additive migration versioning; atomic evidence/guard integration; audit/idempotency design; and manifest publication durability. Any unresolved identity or compatibility condition refuses; any runtime proof failure leaves the guard blocked.

## PostgreSQL 18 documentation basis

The PostgreSQL 18 official documentation basis supplied for this revision is: [libpq connection strings](https://www.postgresql.org/docs/18/libpq-connect.html) (`application_name`), [`pg_restore`](https://www.postgresql.org/docs/18/app-pgrestore.html) (`--dbname` connection string), [monitoring statistics](https://www.postgresql.org/docs/18/monitoring-stats.html) (`pg_stat_activity` visibility and `pg_read_all_stats`), and [explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html) (session-level advisory-lock lifecycle). `application_name` is used only as a bounded cooperative correlation tag, not as proof of backend identity.
