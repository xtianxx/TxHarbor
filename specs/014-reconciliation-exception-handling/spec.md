# Feature Specification: Reconciliation and Exception Handling

**Feature Branch**: `014-reconciliation-exception-handling`

**Created**: 2026-09-26

**Status**: Draft

**Input**: User description: "对账与异常处置：复用已有链上对账、提款恢复、事件审计能力，明确现有覆盖与新增缺口；定义链上事实、PG 业务状态、事件交付/消费结果之间的持续对账；上游账本处理回执作为明确契约边界，未接入不得宣称外部入账正确；支持有范围、有检查点、可中断恢复的对账任务；明确扫描完整性与数据新鲜度，避免把扫描中的暂时差异当成确定异常；对差异建立稳定身份、去重、证据、分类、告警及处置生命周期；定义操作员查询、认领、处置、验证闭合所需的权限和审计；区分只告警、复用已有恢复机制和需要新增修复规则的情况；自动修复不得未经设计就改写权威事实或触发付款；验收覆盖漏处理、重复事件、链重组、未知交易结果、扫描中断、并发状态变化，以及重复处置不产生重复副作用。约束：PG 继续作为权威业务状态，TxHarbor 不自建用户余额账本；继承现有授权、签名隔离、幂等、重组与恢复门禁；对账发现差异不直接等于可以重新付款；不把额外审批、自动修复策略等建议当成已批准业务规则；本阶段先定义后端能力，不同时扩展完整管理控制台、灾备或多主机部署；对账必须有资源预算，普通 PR CI 保持分层；T000-P 保持 OPEN。"

## Clarifications

### Session 2026-09-26

- Q: 在 014 对账中，哪些处置允许自动执行而不经操作员逐条触发？ (FR-023) → A: 以有界只读复核为限：允许自动重查链上/上游结果、刷新对账证据、重试只读比对，可持久化自身任务检查点、差异记录和审计记录，受资源预算、退避和取消控制约束；不得自动改写权威业务事实或自动触发重组恢复、事件重放/解阻、重新付款等处置，需操作员显式触发已批准能力并继承其门禁/幂等/审计；不批准新增修复规则；仅约束 014 新增处置权限，不改变 001–013 既有自动流程；“复核一致”仅在证据完整新鲜且满足一致性规则时自动标记，扫描失败/证据不足/上游未接入不得视为已解决；“复核一致”是否等于工单最终闭合留生命周期问题单独明确。
- Q: 查看、启动/暂停扫描、认领、处置和验证闭合分别允许谁操作，是否需要额外审批？ (FR-024) → A: 分层最小权限：查看需认证+范围读取权限并按权限脱敏，无匿名查询；启动/暂停扫描需对账扫描管理权限，仅影响获授权范围内 014 任务，不得暂停上游资金流程；认领需对应范围异常处理权限，仅表责任归属，不授予处置权限；处置需具体动作执行权限并记录范围理由证据结果，调用既有恢复能力须同时满足其原有授权与资金门禁，填写字段本身不构成授权；验证闭合需闭合权限+系统复核证据，不得将不完整/过期/未知/仍有差异强制标一致，风险接受须另行状态；本阶段不统一要求第二人审批，既有更严审批保留，新增高风险另行裁决；逻辑边界不要求新建身份系统，复用方式留 plan，越权拒绝可测并审计。
- Q: 持续对账的独立暂停、故障隔离与资源预算需要哪些可验收要求，是否锁定独立进程或复用 worker？ (FR-025) → A: 不锁定形态，只锁定验收要求：可按授权范围暂停/恢复 014 扫描且不影响充值确认提现恢复流程，暂停后不领新工作、在途有界完成或取消；检查点仅覆盖已完成且已持久化范围，取消超时失败不得越过未完成区间，恢复可重扫但不漏扫、不重复处置副作用；扫描错误依赖超时重试不得传播为资金停机或无界资源占用，须经故障注入与并发资金负载验证，机制留 plan；并发配额与单次范围时长有界，耗尽停新工作并进入可观察等待/暂停，不忙循环不无界重试；记录暂停原因、最后检查点、未覆盖区间与新鲜度，暂停或不完整不得显示全量一致，新增数据缺口可见；plan 明确暂停响应、资源上限、资金影响的测量方法与测试预算，本地值不得直宣生产阈值；形态若不满足要求须在 plan 回报调整，不得削弱验收，取舍记技术计划必要时补 ADR。
- Q: 至少一次投递下，被幂等吸收且无业务效果分歧的重复应记为异常吗？ (FR-009) → A: 仅业务分歧建单：同一身份内容一致且幂等记录与效果证据证明无分歧的重复（含版本守卫忽略的合法旧版本）仅指标及必要审计，不建异常单；重复导致或揭示业务分歧（同身份不同内容、重复业务效果、重复提款意图、违反版本规则）才建单并按稳定身份去重；证据不足标待核验/覆盖不完整，不认定已安全吸收也不断言已重复付款，按有界复核与升级规则处理；判断依据为事件契约幂等记录与业务效果，不因来源降低标准；未接入上游处理证据时仅判断本项目范围重复效果，不宣称外部无重复入账；正常重复率升高可作运行告警，与资金差异单分离。
- Q: 处置完成与验证闭合应如何区分，并发变化、重组及差异再次出现时应如何重验证？ (FR-010) → A: 处置完成仅表动作执行完毕，不证明差异消失；须经系统复核（证据完整新鲜且满足一致性）标记复核一致，最终闭合由具闭合权限操作员确认并审计；闭合仅对记录的范围区块身份业务版本与证据时点有效，不免疫后续重组变化；影响结论的并发变化重组或新证据自动使验证失效转待验证，同一差异确认再现重开原单，保留历次闭合重开原因与证据，无关写入不重开；重验证期间状态再变不得以过期结果闭合，有界重试或保持待验证，超时不完整不可用证据不足不得视为一致；同一身份沿用原单追加，不同身份可建关联单，身份规则机制留 plan，不得因重组或重扫丢失关联或无限建单；自动重验证仅做已批准只读复核与 014 自身记录更新，不重执行恢复重放或付款，再处置须操作员显式授权并满足既有门禁。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 持续对账发现漏处理与重复交付 (Priority: P1)

操作员（或定时任务）对一个明确范围（链范围、高度区间、业务类型）发起一次对账，系统比对链上事实、PG 业务状态、事件交付/消费结果三方，输出差异清单；漏处理的业务记录和重复交付的事件都能被发现，且扫描中的暂时不一致不被当作确定异常上报。

**Why this priority**: 这是本功能的核心价值：把今天散落在单点探针（单 tx_hash 查询、单 intent 轮询、事件 watermark 比对）里的能力收敛为可持续、可复核的兜底网。不做这一片，后续任何自动修复都没有可信输入。

**Independent Test**: 仅实现三方比对 + 范围/检查点/完整性语义，即可在受控数据集上验证漏处理与重复事件两类差异的检出率与误报率，交付独立价值。

**Acceptance Scenarios**:

1. **Given** 链上已确认的交易在 PG 无对应业务记录，**When** 对账任务覆盖其范围并完成扫描，**Then** 产生一条稳定身份的漏处理差异，附证据且只告警、不触发生成付款。
2. **Given** 同一有效事件被重复投递/消费且无业务效果分歧（幂等吸收），**When** 对账任务完成，**Then** 不产生异常单，仅指标及必要审计；**Given** 重复导致或揭示业务分歧，**When** 对账任务完成，**Then** 产生一条重复交付差异并按稳定身份去重，业务状态收敛且不产生重复副作用。
3. **Given** 对账扫描尚未完成（检查点未闭合），**When** 查询差异视图，**Then** 扫描中区间标记为不完整，暂不输出确定异常结论。

---

### User Story 2 - 差异的去重、分类、告警与处置闭环 (Priority: P2)

操作员查询差异、认领一条差异、执行处置（只告警确认 / 触发已有恢复机制 / 按新增修复规则处理）、验证后闭合；同一差异重复出现不产生重复工单，重复处置不产生重复副作用，全程留审计轨迹。

**Why this priority**: 发现差异只是起点；没有身份、去重、认领、闭合，差异会淹没操作员或被重复处理。这是把“事实表”升级为“工作流”的关键切片。

**Independent Test**: 可用一组固定差异（含重复出现）验证身份稳定、去重、认领互斥、闭合审计，无需先实现自动修复规则即可演示。

**Acceptance Scenarios**:

1. **Given** 同一差异在多次扫描中重复出现，**When** 再次检出，**Then** 归并到同一差异身份，不新增工单，证据追加。
2. **Given** 操作员 A 已认领某差异，**When** 操作员 B 尝试认领或处置，**Then** 拒绝并提示归属，审计记录该尝试。
3. **Given** 已闭合差异的处置被重复执行，**When** 再次触发，**Then** 幂等返回已闭合结果，不产生新的状态变更或外部动作。

---

### User Story 3 - 重组、未知结果与中断下的保守语义 (Priority: P3)

链重组、交易结果未知、扫描中断、并发状态变化发生时，对账保持保守语义：孤块来源不形成永久结论、未知结果保留并持续观察、中断可从检查点恢复、并发写入不导致误判或重复修复。

**Why this priority**: 这是资金安全的高风险分支：重组/未知/中断处理不当会把暂时状态固化为永久结论或触发错误付款。该故事独立验证保守语义。

**Independent Test**: 通过重组、未知回执、 kill/重启中断、并发更新四组故障注入，验证结论收敛正确且无错误付款。

**Acceptance Scenarios**:

1. **Given** 某差异证据来自孤块数据，**When** 重组确认其已 orphaned，**Then** 差异结论撤销或转为待复核，不形成永久业务结论。
2. **Given** 交易执行结果未知（超时/回执缺失），**When** 对账观察到未知，**Then** 标记为未知并持续观察，不记成功、不记失败、不触发重付。
3. **Given** 对账任务在扫描中被中断，**When** 从检查点恢复，**Then** 已覆盖区间不重报、未覆盖区间继续，不遗漏不重复。

---

### Edge Cases

- 上游账本处理回执未接入时，系统不得输出“外部入账正确”结论，只能输出“未验证/不可判定”。
- 扫描覆盖为空（范围无数据）时，输出“覆盖为空且完整”，而非“无异常”。
- 数据新鲜度过期（来源落后于容忍窗）时，差异结论降级为“待复核”，不触发自动修复。
- 分类器遇到未知差异形状时，落入保守默认分类（只告警），不得静默丢弃。
- 资源预算耗尽（时间/条数/扫描配额）时，任务按检查点暂停并明确标记未覆盖区间。
- 操作员权限不足时的查询/认领/处置/闭合一律拒绝并审计。
- 额外审批链、自动修复策略的具体业务规则未批准前，相关处置路径保持关闭或仅 dry-run。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供有范围的对账任务能力，范围至少包含链标识、高度/时间区间、业务类型集合，任务可指定、可复现。
- **FR-002**: 系统 MUST 在一次对账中比对三方：链上事实、PG 业务状态、事件交付/消费结果，并输出差异或“一致且覆盖完整”的结论。
- **FR-003**: 系统 MUST 为对账任务维护检查点，支持中断后从检查点恢复，已覆盖区间不重报、未覆盖区间可继续；检查点仅覆盖已完成且结果已持久化的范围，取消/超时/失败不得越过未完成区间；在途工作暂停后须在有界时间内完成或取消。
- **FR-004**: 系统 MUST 明确扫描完整性语义，未闭合的扫描区间不得输出确定异常结论，只能标记为不完整/待复核。
- **FR-005**: 系统 MUST 明确数据新鲜度语义，来源落后超过容忍窗时结论降级，不得触发自动修复。
- **FR-006**: 上游账本处理回执未接入的范围，系统 MUST NOT 输出外部入账正确结论，只能输出未验证/不可判定。
- **FR-007**: 每条差异 MUST 拥有稳定身份，同一根因重复检出归并同一身份并追加证据，重复出现 MUST NOT 产生重复工单；确认再现 MUST 重开原单；确属不同身份可新建关联单；MUST NOT 因重组或重复扫描丢失关联或无限建单，身份规则与机制留 plan。
- **FR-008**: 每条差异 MUST 附带证据包（来源、快照、比对输入、扫描覆盖与新鲜度），证据可审计、可复核。
- **FR-009**: 系统 MUST 对差异做机读分类，至少区分：漏处理、重复交付（仅业务分歧）、状态不一致、未知结果、覆盖不完整/待复核；幂等吸收零副作用的重复（含版本守卫忽略的合法旧版本）MUST NOT 建异常单，仅指标及必要审计；证据不足 MUST 标待核验/覆盖不完整；未知形状落入保守默认分类。
- **FR-010**: 系统 MUST 为差异提供处置生命周期：待认领 → 已认领 → 处置中 → 待验证 → 已闭合（含驳回/转人工路径），非法跳转 MUST 被拒绝；处置完成 MUST NOT 等同验证闭合，待验证 MUST 凭系统复核证据（完整新鲜且满足一致性）标记复核一致，最终闭合由具闭合权限操作员确认；闭合结论仅对记录的范围区块身份业务版本与证据时点有效；影响结论的并发变化、链重组或新证据 MUST 自动使验证失效转待验证，同一差异确认再现 MUST 重开原单并保留历史；无关写入 MUST NOT 触发重开；重验证期间状态再变 MUST NOT 以过期结果闭合；同一身份沿用原单追加，不同身份可建关联单，身份规则机制留 plan。
- **FR-011**: 查询、启动/暂停扫描、认领、处置、验证闭合 MUST 按分层最小权限授权：查看需认证+范围读取权限并按权限脱敏（无匿名查询）；启动/暂停扫描需对账扫描管理权限且仅影响获授权范围内 014 任务；认领需对应范围异常处理权限且仅表责任归属；处置需具体动作执行权限；验证闭合需闭合权限+系统复核证据；越权操作 MUST 被拒绝并审计；认证与授权机制复用方式留 plan，但越权拒绝 MUST 可测。
- **FR-012**: 每次认领、处置、验证、闭合 MUST 写审计轨迹（含操作员、时间、依据、处置内容与结果）。
- **FR-013**: 系统 MUST 区分三类处置：只告警确认、复用已有恢复机制（重组恢复/未知恢复/重放/解阻等）、新增修复规则；三类在差异上可区分、可统计。
- **FR-014**: 014 自动执行 MUST 限于有界只读复核（重查链上/上游结果、刷新对账证据、重试只读比对）及自身任务检查点、差异记录和审计记录的持久化，受资源预算、退避和取消控制约束；任何自动改写 PG 权威事实或触发付款类外部动作 MUST NOT；自动触发重组恢复、事件重放/解阻、重新付款等处置 MUST NOT；默认只告警。
- **FR-015**: 对账发现差异 MUST NOT 被直接解释为重新付款许可；付款仍只走现有授权与门禁路径。
- **FR-016**: 重复处置同一已闭合差异 MUST 幂等收敛，不产生新的状态变更或外部副作用。
- **FR-017**: 链重组场景下，源自孤块的差异结论 MUST 可撤销或转待复核，不得形成永久业务结论。
- **FR-018**: 交易结果未知场景下，系统 MUST 保留未知并持续观察，不得记成功/失败，不得触发重付。
- **FR-019**: 对账任务 MUST 有资源预算（扫描并发、PG/RPC 请求、单次扫描范围与执行时间有界），超预算或耗尽时停止新增工作并进入可观察的等待或暂停状态，按检查点标明未覆盖区间；MUST NOT 忙循环或无界重试；须记录暂停原因、最后完成检查点、未覆盖区间和证据新鲜度。
- **FR-020**: 对账能力 MUST 继承现有授权、签名隔离、幂等、重组与恢复门禁；健康/观测信号不得替代资金门禁判权。
- **FR-021**: 系统 MUST NOT 自建用户余额账本；PG 继续作为权威业务状态，事件消费结果不得被当作权威余额。
- **FR-022**: 本阶段交付 MUST 为后端能力（任务、差异、证据、处置、审计、观测），不含完整管理控制台、灾备、多主机部署。
- **FR-023**: 014 自动处置范围已裁决（2026-09-26）：仅有界只读复核可自动执行；改写权威事实、触发恢复/重放/解阻/重付的处置一律需操作员显式触发已批准能力；不批准新增修复规则，未设计的新增修复路径保持关闭或仅 dry-run；本限制仅约束 014 新增处置权限，不改变 001–013 既有自动流程。额外审批链是否需要单独裁决见 FR-024 权限澄清。
- **FR-024**: 权限模型已裁决（2026-09-26）：分层最小权限如 FR-011；调用既有恢复能力须同时满足其原有授权与资金门禁，填写 operator/理由/证据本身不构成授权；不得将扫描不完整、证据过期、结果未知或仍存在差异强制标为“已验证一致”，风险接受须另行状态；本阶段不统一要求第二人审批，既有更严审批保留，新增高风险处置另行裁决。
- **FR-025**: 承载形态已裁决（2026-09-26）：不锁定独立进程或复用 worker，只锁定可验收要求——可按授权范围暂停/恢复 014 扫描且不影响资金流程，暂停后不领新工作、在途有界完成或取消；检查点仅覆盖已完成且已持久化范围；故障隔离须经故障注入与并发资金负载验证，机制留 plan；并发配额与单次范围时长有界，耗尽停新工作进入可观察等待/暂停；状态诚实记录原因/检查点/未覆盖区间/新鲜度；形态不满足要求须在 plan 回报调整，取舍记技术计划必要时补 ADR。

### Key Entities

- **对账任务 (Reconciliation Task)**: 一次有范围的比对工作；属性含范围（链/高度或时间/业务类型）、检查点、完整性状态、新鲜度、资源预算、执行状态。
- **差异 (Discrepancy)**: 三方比对不一致或不可判定的结论；属性含稳定身份、分类、证据包、生命周期状态、认领人、处置记录。
- **证据包 (Evidence Bundle)**: 差异的判定依据；含三方快照、回执接入状态、扫描覆盖、数据新鲜度、时间。
- **处置 (Disposition)**: 对差异的处理决策与执行；含类型（只告警/复用恢复/新增修复）、执行者、结果、幂等键。
- **审计轨迹 (Audit Trail)**: 认领/处置/验证/闭合的操作记录；含操作员、时间、依据、结果，不可篡改、可查询。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在受控数据集上，漏处理与重复业务分歧两类差异的检出率达到 100%，幂等吸收的正常重复零异常建单，且扫描未完成区间零确定误报。
- **SC-002**: 同一根因差异在 3 次重复扫描中只形成 1 条工单，证据追加无重复建单。
- **SC-003**: 重组、未知结果、扫描中断、并发变化四组故障注入下，零错误付款、零永久误结论，全部收敛到已定义的保守状态。
- **SC-004**: 重复处置已闭合差异 10 次，业务状态与外部动作零新增副作用，审计完整可查。
- **SC-005**: 越权操作员的认领/处置/闭合请求 100% 被拒绝并审计；授权操作员端到端闭环可在可复现步骤内完成。
- **SC-006**: 超预算任务 100% 按检查点暂停且未覆盖区间明确可查；恢复后无遗漏无重复。

## Assumptions

- 复用假设：已有单点能力（单 tx 探针、per-intent 轮询、事件 watermark 比对、quarantine、nonce 对账循环、checkpoint 校验）作为比对原语；本规格新增的是任务编排、完整性语义、身份去重、处置生命周期四层，不重复建设单点探针。
- 部署假设：默认单机后端能力先行；多主机、灾备、完整控制台明确不在本阶段范围。
- 测试假设：普通 PR CI 保持分层，对账重载（大扫描/故障注入/长基准）走独立标签或 Fault/Perf 通道，不新增普通 PR 长测。
- 口径假设：人工验收、生产部署、生产阈值裁决分别记录，不以未部署推断人工验收未完成；历史基准绑定实测提交与适用前提；历史双进程接管超时保持未知；T000-P 保持 OPEN。

### 已确认约束（Constitution 与既有契约继承）

- PG 唯一权威；Redis/Kafka 不持金融真相；金额禁用浮点；幂等落 DB 约束；显式状态机；事务边界；nonce 并发安全；私钥仅 Signer；失败路径一等公民；可观测为正确性一部分。
- 上游只读、授权载体版本相等性、发送/执行双门禁、unknown 永不作为许可或重建依据、事件不是许可、容量红线不放宽门禁。
