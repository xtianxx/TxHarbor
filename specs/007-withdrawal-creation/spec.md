# Feature Specification: 007 Withdrawal Creation & Query (Receive-Only)

**Feature Branch**: `007-withdrawal-creation`

**Created**: 2026-09-15

**Status**: Draft

**Input**: 007 需求输入（见任务指令 §三）：提供受认证、授权的幂等提款创建与查询，持久化请求，暂不执行交易。端点 POST /withdrawals、GET /withdrawals/{id}。单部署单链，Go/PostgreSQL/EVM/Anvil，不引入新基础设施。

**阅读对象**：本规格面向 API 调用方集成者、审计者（追溯请求接收证据）与下游阶段设计者（008–011）。链上术语含义见 Key Entities（Accepted = 请求已被接收并持久化，不表示已执行/已付款/已扣减；幂等键 = 调用方提供的去重标识，与 caller_id 共同确定去重作用域，具体格式见 FR 澄清标记）；技术载体（表结构、锁、算法、模块接口）一律留给 plan，上游技术引用仅出现在溯源说明中。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 正常创建与本人查询（Priority: P1）

已认证且具业务授权的调用方提交合规提款请求，系统持久化后返回请求标识；同一调用方随后凭标识查询到该请求。

**Why this priority**: 核心价值；没有"创建—持久化—本人可查"的闭环，本阶段不存在。

**Independent Test**: 在 Anvil + PostgreSQL 本地环境，以具授权身份提交一组有效参数（合规 chain_id、白名单资产、合法收款地址、正整数最小单位金额字符串），断言返回请求标识且持久化可见；随后以同一身份查询该标识，断言返回内容与提交一致。

**Acceptance Scenarios**:

1. **Given** 调用方已通过认证且具备业务授权，**When** 提交参数全部合规的创建请求，**Then** 系统持久化该请求并返回其请求标识，且状态语义为"已接收"（Accepted），不表示已执行、已付款或已扣减。
2. **Given** 请求已持久化，**When** 同一调用方查询该请求标识，**Then** 返回该请求且归属校验通过，内容与提交时的规范化参数一致。
3. **Given** 请求已持久化，**When** 查询返回，**Then** 金额以十进制字符串表达（非浮点），且范围遵守章程 uint256 约束。

---

### User Story 2 — 未认证、无业务授权、越权查询（Priority: P1）

系统区分"认证身份"与"业务授权"：未认证、无业务授权、冒用他人标识的请求一律被拒绝；调用方只能查询自己的请求。

**Why this priority**: 安全基线；身份与权限混淆将导致越权创建或越权读取，直接违反章程安全规则。

**Independent Test**: 分别以缺失/无效认证凭证、无业务授权身份、调用方 A 查询调用方 B 的请求标识三种方式请求，断言均被拒绝且不持久化任何新请求（查询场景）或不创建请求（创建场景）。

**Acceptance Scenarios**:

1. **Given** 请求缺失有效认证凭证或凭证无效，**When** 提交创建或查询，**Then** 系统拒绝该请求，不创建、不返回任何请求内容。
2. **Given** 调用方认证通过但无本业务授权，**When** 提交创建，**Then** 系统拒绝创建，不持久化。
3. **Given** 请求 R 归属调用方 B，**When** 调用方 A（已认证）查询 R 的标识，**Then** 系统拒绝返回 R 的内容，且不得通过错误信息泄露 R 是否存在之外的归属信息（见 FR-15；区分"不存在"与"无权访问"的可观察差异见 [NEEDS CLARIFICATION: 未找到与无权访问的可观察区分策略未定，见 FR-15]）。
4. **Given** 客户端自报 `caller_id` 与认证身份不一致，**When** 提交创建，**Then** 系统以认证身份为准建立归属，MUST NOT 仅凭客户端自报字段建立身份或权限。

---

### User Story 3 — 参数校验失败（Priority: P1）

错链、非白名单资产、非法地址、零/负数/小数/超范围金额一律在持久化前被拒绝。

**Why this priority**: 财务正确性入口；非法参数一旦持久化即污染下游执行基础。

**Independent Test**: 逐项提交非法参数矩阵（错 chain_id、非白名单资产、非法地址、"0"、负数、带小数点、超 uint256 上限），断言全部被拒绝且无持久化。

**Acceptance Scenarios**:

1. **Given** `chain_id` 与本部署服务链不一致，**When** 提交创建，**Then** 拒绝且不持久化。
2. **Given** 资产非白名单标准 ERC-20，**When** 提交创建，**Then** 拒绝且不持久化。
3. **Given** 收款地址非法（非 EVM 地址形状或校验失败），**When** 提交创建，**Then** 拒绝且不持久化。地址等价表示（大小写/校验和）的规范化规则见 [NEEDS CLARIFICATION: 地址等价与规范化规则未定，见 FR-07]。
4. **Given** 金额为 "0"、负数、含小数点、非纯十进制整数字符串或超出 uint256 范围，**When** 提交创建，**Then** 拒绝且不持久化。`decimals` 仅用于展示，不参与金额数值语义。

### User Story 4 — 幂等语义（Priority: P1）

同调用方同键同参返回原请求，同键异参返回冲突；不同调用方使用同键互不干扰。

**Why this priority**: 重试安全的核心；幂等失败即重复提款意图，直接违反章程原则 I、II。

**Independent Test**: 同一调用方先后提交同键同参（断言第二次返回原请求标识且无新增持久化）、同键异参（断言冲突且原请求不变）、不同调用方同键同参（断言互不干扰，各自独立）。

**Acceptance Scenarios**:

1. **Given** 调用方 C 以键 K 提交参数 P 成功并得标识 R，**When** C 以键 K 与参数 P 再次提交，**Then** 系统返回原请求 R，不创建新请求。
2. **Given** 调用方 C 以键 K 与参数 P 成功创建 R，**When** C 以键 K 与异参 P' 提交，**Then** 系统返回冲突，原请求 R 不变，不创建新请求。参与比较的参数集合与规范化规则见 [NEEDS CLARIFICATION: 幂等比较参数集与规范化未定，见 FR-10]。
3. **Given** 调用方 C1 以键 K 创建成功，**When** 调用方 C2 以相同键 K 提交，**Then** 两者互不干扰（去重作用域含调用方），C2 的请求独立处理。
4. **Given** 幂等键缺失或格式非法，**When** 提交创建，**Then** 拒绝且不持久化。键格式与长度约束见 [NEEDS CLARIFICATION: 幂等键格式未定，见 FR-09]。

---

### User Story 5 — 并发、响应丢失、重启与持久化失败（Priority: P1）

并发重复、响应丢失后重试、进程重启后重试均不得创建重复请求；持久化失败不得返回已接受。

**Why this priority**: 真实故障下的正确性；仅覆盖串行 happy path 的幂等是虚假保证。

**Independent Test**: 并发提交同键同参 N 次（断言仅一个请求被创建）、持久化成功后模拟响应丢失再重试（断言返回原请求）、重启后重试（断言返回原请求）、注入存储不可用（断言不返回已接受）。

**Acceptance Scenarios**:

1. **Given** 调用方并发提交同键同参多次，**When** 请求同时到达，**Then** 仅创建一个请求，其余返回同一原请求（DB 层去重保证，不依赖应用内存检查；具体机制留给 plan）。
2. **Given** 请求已持久化成功但响应丢失，**When** 调用方以同键同参重试，**Then** 返回原请求，不创建新请求。
3. **Given** 进程重启，**When** 调用方以同键同参重试，**Then** 返回重启前已持久化的原请求（保证基于持久层，重启动态不丢失）。
4. **Given** 存储不可用或持久化失败，**When** 提交创建，**Then** 系统 MUST NOT 返回已接受；返回存储不可用语义且无部分持久化可见（原子边界留给 plan，行为要求见 FR-12）。

### User Story 6 — 恢复期间创建、查询与无副作用（Priority: P2）

恢复期间合规请求仍可接收并幂等持久化；查询表达可信状态；全程无 nonce/签名/广播副作用。

**Why this priority**: 006 契约承接；违反即破坏重组恢复安全边界。

**Independent Test**: 在模拟恢复活跃状态下提交合规创建（断言持久化成功且无 nonce/签名/广播副作用）、查询请求（断言结果携带恢复状态表达且不把混合链视图包装成完整有效结果）、验证恢复前已发出但结果未知的外部请求仍保留未知语义。

**Acceptance Scenarios**:

1. **Given** 链处于恢复活跃状态（006 恢复行存在且非释放终态），**When** 提交认证、授权、参数均合规的创建请求，**Then** 允许幂等持久化（仅接收），且 MUST NOT 触发 nonce 分配、新签名或任何广播（含重播与费用替换）。
2. **Given** 链处于恢复活跃状态，**When** 查询已持久化请求，**Then** 返回请求事实（持久化请求本身）与未来链上执行状态的边界明确表达：请求事实可信，执行状态未知，不得把恢复中的混合链视图包装成完整有效结果（有效性标注语义沿用 006 FR-18：none/recovering/paused_reconcile/released × valid_unaffected/provisional_replaying/unknown_paused 的适用子集，具体映射见 FR-16）。
3. **Given** 恢复暂停生效前已发出的外部请求结果未知，**When** 本阶段处理相关查询，**Then** 保留未知语义，不得靠重建付款意图"补偿"。
4. **Given** 恢复暂停生效中，**When** 任何创建或查询路径执行，**Then** 不得改变恢复暂停、解除授权、独立暂停原因或旧结果隔离规则（006 拥有）。

### Edge Cases

- 幂等键保留期到期后重用同键：到期保留时长与到期后重复付款风险见 [NEEDS CLARIFICATION: 保留期与到期语义未定，见 FR-11]；到期前 MUST NOT 因时间推移改变去重结果。
- 金额字符串 "+123"、前导零 "00123"、空字符串、超长数字：是否接受及规范化见 [NEEDS CLARIFICATION: 金额字符串规范化未定，见 FR-06]；超 uint256 上限一律拒绝（章程约束，无需澄清）。
- 地址大小写混写（EIP-55 校验和大小写）是否视为同一地址：见 [NEEDS CLARIFICATION: 见 FR-07]。
- 同键请求正在处理中（首次尚未完成持久化）第二次到达：第二次 MUST 等待首次结果或返回等价语义，MUST NOT 创建第二个请求（机制留给 plan）。
- 查询标识格式非法或从未存在：返回未找到语义，不泄露他人信息。
- 存储超时 vs 明确失败：调用方无法区分时按"未知，需重试"处理，重试仍满足幂等（US5-2）。
- 恢复状态翻转瞬间（恢复释放与创建并发）：创建路径观察到的恢复状态以其读取序列为准，不得基于过期观察执行被暂停动作；读取序列要求沿用 006 downstream.md 三项前置检查的适用子集（见 FR-16）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-01**: 系统 MUST 提供创建端点 `POST /withdrawals` 与查询端点 `GET /withdrawals/{id}`，均要求认证。未认证请求 MUST 被拒绝。
- **FR-02**: 系统 MUST 分别定义认证身份（谁在调用）与业务授权（是否允许使用提款创建业务），两者缺一不可。MUST NOT 仅凭客户端自报 `caller_id` 建立身份或权限；请求归属 MUST 以认证身份为准。
- **FR-03**: 认证方式、身份来源字段、业务授权的证明形式与校验边界见 [NEEDS CLARIFICATION: 认证机制（API key / mTLS / JWT / 其他）、身份来源字段名、授权证明载体与校验方均未定；上游无已批准依据。本规格不预设具体机制]。
- **FR-04**: 系统 MUST 在持久化前校验 `chain_id` 与本部署服务链一致；不一致 MUST 拒绝且不持久化。本部署为单链（章程架构演进约束）。
- **FR-05**: 系统 MUST 在持久化前校验资产为白名单标准 ERC-20；白名单来源与更新机制沿用 003/004 已批准策略，本规格不重定义。非白名单 MUST 拒绝且不持久化。
- **FR-06**: 金额 MUST 为十进制整数字符串（纯 `[0-9]+`，非空），MUST 拒绝零、负数、小数、非数字字符；数值范围 MUST 遵守 uint256 约束（0 < value ≤ 2²⁵⁶−1）；`decimals` 仅用于展示，MUST NOT 参与金额数值语义。前导零、"+" 前缀、空字符串、超长输入的接受与规范化见 [NEEDS CLARIFICATION: 金额字符串规范化规则未定（如前导零是否接受、是否规范化后再比较）；拒绝类（零/负/小数/超范围）无需澄清]。
- **FR-07**: 收款地址 MUST 为合法 EVM 地址形状；非法 MUST 拒绝且不持久化。大小写/校验和等价表示的规范化规则见 [NEEDS CLARIFICATION: 地址等价与规范化规则未定（如是否 EIP-55 规范化后比较、比较是否大小写不敏感）；非法形状的拒绝无需澄清]。
- **FR-08**: 系统 MUST 持久化 Accepted 请求及审计记录。Accepted 的语义 MUST 仅表示"请求被接收"，MUST NOT 被表达为已执行、付款成功或余额已扣减。查询与日志中的状态措辞 MUST 遵守此边界。
- **FR-09**: 幂等键 MUST 由调用方提供；缺失或非法 MUST 拒绝且不持久化。键格式、字符集、长度上下限见 [NEEDS CLARIFICATION: 幂等键格式未定；上游无已批准依据]。
- **FR-10**: 去重作用域 MUST 为 `caller_id + idempotency_key`（不同调用方同键互不干扰）。同键同参 MUST 返回原请求；同键异参 MUST 返回冲突且原请求不变。参与比较的参数集合（chain_id/asset/to/amount 及其规范化形式）与等价判定见 [NEEDS CLARIFICATION: 幂等比较参数集、规范化顺序（金额前导零、地址大小写）未定；作用域本身无需澄清]。
- **FR-11**: 幂等记录保留期、到期清理策略及到期后同键重用的重复付款风险声明见 [NEEDS CLARIFICATION: 保留期时长、清理触发条件、到期后重用语义未定；上游无已批准依据。到期前语义无需澄清]。
- **FR-12**: 持久化与去重判定 MUST 在持久层原子边界内完成（DB UNIQUE 约束，非应用内存检查；具体表结构、约束定义与事务划分留给 plan）。存储不可用或持久化失败时 MUST NOT 返回已接受，且 MUST NOT 留下部分可见的持久化。
- **FR-13**: 并发同键同参请求 MUST 收敛到单一请求（有且仅一个被创建，其余返回同一原请求）；进程重启后重试 MUST 返回重启前已持久化的原请求。并发算法与锁机制留给 plan，行为保证在本规格。
- **FR-14**: 创建、重复返回、冲突、验证失败、未授权、未找到、存储不可用的行为语义 MUST 按 US1–US6 区分；各语义对应的确切响应编码（HTTP 状态码、错误码/错误体形状）见 [NEEDS CLARIFICATION: 响应编码映射未定（如冲突用 409、重复返回是否与首次同码）；行为语义本身已定，无需澄清]。
- **FR-15**: 查询 MUST 校验请求归属：仅归属调用方可读。越权查询 MUST 被拒绝，且 MUST NOT 通过响应泄露他人请求内容。未找到与无权访问的可观察区分（是否可区分、何种编码）见 [NEEDS CLARIFICATION: 404 vs 403/404 归一化的选择未定，涉及信息泄露与调试便利的权衡，需业务决策]。查询返回的字段语义（标识、归属、链、资产、收款地址、金额字符串、状态、时间）见 Key Entities；确切字段名与序列化形状留给 plan，但 MUST 包含归属可验证信息且 MUST NOT 包含签名/密钥材料。
- **FR-16**: 恢复期间行为 MUST 承接 006 已批准约束（来源：006 spec FR-26、contracts/downstream.md 2026-09-14）：合规创建允许幂等持久化且仅接收；MUST NOT 触发 nonce 分配、新签名或任何广播（含重播与费用替换）；查询 MUST 表达恢复状态与结果有效性（沿用 006 FR-18 标注语义的适用子集：请求持久化事实 vs 未来链上执行状态的边界）；MUST NOT 改变恢复暂停、解除授权、独立暂停原因或旧结果隔离规则。创建路径 MUST 观察 006 downstream 前置检查适用子集（暂停行、活跃恢复行；本阶段无自有 nonce/签名门禁可供检查），观察失败 → 拒绝触发后续动作（本阶段本就无后续动作）并记录原因。
- **FR-17**: 恢复前已发出的外部请求若结果未知，MUST 保留未知语义（继续查询、记录证据），MUST NOT 靠重建付款意图补偿。本阶段不创建、不修改任何外部请求结果记录（008–011 职责）。
- **FR-18**: 上游负责余额预留与业务授权判定所需的信息供给；本项目 MUST NOT 维护用户余额账本。本阶段 MUST NOT 扩展 KYC、风控审批或冷热钱包调度。余额不足时的拒绝语义（如有）取决于上游供给，见 [NEEDS CLARIFICATION: 上游余额/授权信息供给方式未定；本阶段不自建账本无需澄清]。
- **FR-19**: 本阶段 MUST NOT 分配 nonce、签名、广播；MUST NOT 创建 008/009/010/011 的执行模块、状态机或业务表。008 nonce、009 signer、010 交易尝试、011 worker 在本规格中仅记录为下游职责（见 Downstream Handoff）。
- **FR-20**: 金额、地址、哈希等财务与链上量值 MUST NOT 使用浮点（章程原则 I、工程标准）；金额内部语义为整数（最小单位），字符串仅为传输表示。日志 MUST NOT 包含私钥或密钥材料（章程安全规则）。
- **FR-21**: 关键操作 MUST 使用结构化日志（含 caller 身份标识、请求标识、chain_id、资产、重试标识等字段，不含密钥）；失败路径（验证失败、冲突、未授权、存储不可用、恢复期行为）为一等行为，plan 阶段 MUST 为其设计可测覆盖（章程原则 IX、XII）。

### Key Entities

- **Withdrawal Request（提款请求）**：调用方提交的付款意图记录。语义属性：归属调用方（以认证身份为准）、幂等键、chain_id、资产标识（白名单 ERC-20）、收款地址、金额（十进制整数字符串，语义为最小单位整数）、状态（Accepted 仅表示已接收）、创建时间。技术载体（表名、列、索引）留给 plan。
- **Caller Identity（调用方身份）**：经认证机制确认的调用者。来源机制见 FR-03 澄清标记；归属判定 MUST 以此为准，而非客户端自报字段。
- **Business Authorization（业务授权）**：调用方被允许使用提款创建业务的证明。证明形式与校验边界见 FR-03 澄清标记；上游负责授权判定所需信息供给（FR-18）。
- **Idempotency Key（幂等键）**：调用方提供的去重标识，与归属调用方共同确定作用域。格式、比较参数集、规范化、保留期见 FR-09/FR-10/FR-11 澄清标记。
- **Accepted 状态**：请求已被接收并持久化。明确边界：不表示已执行、付款成功或余额已扣减（FR-08）。
- **Recovery State（恢复状态，源自 006）**：查询表达用的链恢复状态，沿用 006 FR-18 标注语义适用子集。006 拥有其定义与转换；本阶段只读消费。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-01**: 100% 的合规创建请求在存储健康时被持久化并返回请求标识，且可由同一调用方查询到内容一致的请求（US1）。
- **SC-02**: 100% 的未认证、无业务授权请求被拒绝且无持久化；100% 的越权查询被拒绝且不泄露他人请求内容（US2）。
- **SC-03**: 参数非法矩阵（错链、非白名单资产、非法地址、零/负/小数/超范围金额）100% 被拒绝且无持久化（US3）。
- **SC-04**: 同调用方同键同参重试 100% 返回原请求且持久化计数不变；同键异参 100% 返回冲突且原请求不变；不同调用方同键 100% 互不干扰（US4）。
- **SC-05**: N 路并发同键同参提交收敛到有且仅 1 个持久化请求（N≥2，plan 阶段定 N）；响应丢失后重试与重启后重试 100% 返回原请求；存储不可用时 0 次返回已接受（US5）。
- **SC-06**: 恢复活跃期间合规创建 100% 仅接收（持久化成功）且全程 0 次 nonce 分配、新签名与广播副作用；查询 100% 表达请求事实与执行未知的边界，无混合链视图被标为完整有效（US6）。
- **SC-07**: 恢复前已发出且结果未知的外部请求在本阶段处理中 0 次被转为"失败后重付"或新建付款意图（US6-3/FR-17）。
- **SC-08**: 金额表达 100% 为十进制整数字符串往返一致；全链路 0 次浮点金额；日志与响应 0 次密钥材料（FR-20）。

## Assumptions

- 单部署单链：`chain_id` 校验以部署配置为准，多链支持不在本阶段（章程架构演进约束）。
- 白名单标准 ERC-20 策略沿用 003/004 已批准定义，本规格不重定义资产清单。
- 上游（余额预留与业务授权信息供给方）按 FR-18 提供判定所需信息；供给方式待澄清，但"本阶段不自建账本"已定。
- 测试环境沿用 Anvil + PostgreSQL + Docker Compose（章程原则 X）；确定性本地测试要求在 plan 阶段落实。
- 008（nonce）、009（signer）、010（交易尝试/广播）、011（worker/执行）尚无规范，本规格仅记录其为下游职责，不创建其规范，不宣称双向核对。

## Non-Goals（范围排除）

## Downstream Handoff（下游待承接契约，不创建未来业务表与状态机）

- **008（nonce 分配）**：本阶段创建的 Accepted 请求不携带 nonce；nonce 分配时机、去重与恢复暂停的共存语义由 008 设计。本规格不预设 nonce 字段。
- **009（签名隔离）**：本阶段不产生签名请求；签名策略绑定内容版本（恢复版本变化后不得提交基于旧链视图的内容，006 FR-26 约束）由 009 承接。
- **010（交易构造与广播）**：恢复期间不得新广播（含重播与费用替换）；结果未知先对账；同一意图多尝试的允许条件由 010 设计，006 只锁定暂停边界。
- **011（提款执行/worker）**：重组后修订结果并追踪原付款意图；不得重新创建付款"补偿"（含未知结果情形）；过期 worker 隔离语义与 006 版本约束同构，011 设计时复用该模式。
- 本规格与 008–011 之间**未做双向核对**（对方尚无规范），上述为单向待承接声明。
